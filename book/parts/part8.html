Cost, Context & Self-Correction

A capable agent is not automatically an economical or dependable one. It must spend model capacity where it matters, keep long conversations within limits, learn when extra examples help, and recover when its own decisions go wrong. This part turns those concerns into explicit routes, budgets, checks, memories, and rollback points that can be measured in both Python and TypeScript.

Dual-domain map for this part: the same cost-and-adaptation controls apply to Eunomia and Skill Reporter.

  • Eunomia domain: model-routing budgets, local-quantized fallbacks, context reuse and compaction, adaptive examples, image/tool workflows, graph-safe correction, hierarchical memory, and rollback controls.
  • Skill Reporter domain: the same model-routing, quantization, context, examples, multimodal/tool, graph-correction, memory, and rollback controls for report-generation workloads.

Lesson 11

Multi-Model Router & Semantic Cache

The problem: if Eunomia sends every savings question to the most expensive model, routine requests become too costly and too slow. Exact-text caching misses many equivalent customer questions with different wording. Skill Reporter has the same inefficiency when semantically similar report requests are not reused safely.

A model router (a decision-maker that sends each request to the cheapest and fastest model capable of answering it safely) makes model choice part of the application rather than a permanent setting. Start with a baseline that sends every request to one expensive model and records cost, response time, and answer quality. Then classify each incoming question by complexity, required tools, and risk. Routine low-risk work may fit a small local model, ordinary cloud work may fit a lower-cost model, and complex or sensitive requests can still reach the highest-capability model.

The second saving comes from a semantic cache (a store that can reuse an earlier answer when a new question has the same meaning even if the wording differs). Each question is turned into an embedding (a list of numbers representing the meaning of a piece of text), then compared with stored questions. A similarity threshold (the minimum meaning-match score required before a cached answer may be reused) prevents a merely related question from being treated as identical. An uncertain match means no cached answer is reusable: the router should make a fresh model call rather than force reuse.

from collections.abc import Awaitable, Callable
from dataclasses import dataclass

@dataclass(frozen=True)
class CacheEntry:
    customer_id: str
    account_version: str
    permission_scope: str
    source_version: str
    expires_at: float
    vector: list[float]
    answer: str

async def semantic_lookup(question: str, customer_id: str, account_version: str,
                          permission_scope: str, source_version: str, now: float,
                          embed: Callable[[str], Awaitable[list[float]]]) -> str | None:
    query = await embed(question)
    scoped = (
        entry for entry in CACHE
        if entry.customer_id == customer_id
        and entry.account_version == account_version
        and entry.permission_scope == permission_scope
        and entry.source_version == source_version
        and entry.expires_at > now
    )
    best = max(scoped, key=lambda entry: cosine(query, entry.vector), default=None)
    return best.answer if best and cosine(query, best.vector) >= 0.92 else None

  customerId: string;
  accountVersion: string;
  permissionScope: string;
  sourceVersion: string;
  expiresAt: number;
  vector: number[];
  answer: string;
}

async function semanticLookup(
  question: string,
  scope: Omit<CacheEntry, "vector" | "answer" | "expiresAt"> & { now: number },
  embed: (text: string) => Promise<number[]>,
): Promise<string | undefined> {
  const query = await embed(question);
  const scoped = cache.filter(
    (entry) =>
      entry.customerId === scope.customerId &&
      entry.accountVersion === scope.accountVersion &&
      entry.permissionScope === scope.permissionScope &&
      entry.sourceVersion === scope.sourceVersion &&
      entry.expiresAt > scope.now,
  );
  const ranked = scoped.map((entry) => ({ entry, score: cosine(query, entry.vector) }));
  const best = ranked.sort((a, b) => b.score - a.score)[0];

}

CHECK SCOPE → SEARCH BY MEANING → REUSE ONLY A SAFE MATCH; OTHERWISE ROUTE TO THE LEAST EXPENSIVE CAPABLE MODEL → VALIDATE, CACHE, STREAM, AND MEASURE

Meaning alone is never enough to make reuse safe. Cache entries need hard boundaries for customer identity, account state, permissions, time-sensitive facts, and tool results. Balance questions, changing interest rates, and requests whose answer depends on the current time should usually bypass reuse or have precise invalidation rules. Every decision should record the selected route, similarity score, reuse decision, cost, and response time as structured measurements.

Build the same controlled request set in Python and TypeScript and compare selected models, reuse decisions, and invalidation. The implementations should agree not just when reuse is allowed, but when it is refused. That comparison exposes language-specific defaults without pretending that a reused answer is automatically correct.

A real bug to test for: a cache key that omits customer or permission scope can offer a semantically similar private answer to the wrong user. Both implementations must prove that scoped keys and metadata filters block the candidate before its similarity score can authorize reuse.
In the capstone: Eunomia's routing becomes a reviewed policy table: routine savings questions are answered by templates with no model at all, and only questions that need wording reach the model gateway. A semantic answer cache is not used in the first release, because every answer is rebuilt from that customer's fresh, frozen evidence. Skill Reporter applies the same budgeted routing policy for routine versus complex report requests.
Lesson 16

Local Model Integration & Quantization

The problem: routing every Eunomia request to remote models can violate cost targets, latency goals, or data-boundary policy. Local models reduce that dependency, but raw model sizes can exceed available hardware. Skill Reporter faces the same trade-off when report workloads must stay in controlled infrastructure.

A local model (an AI model running on hardware controlled by the application owner rather than through an outside cloud request) should first be measured on its own. Record memory use, startup time, response time, and answer quality before connecting it to the agent. The act of producing answers is called inference (running a trained model to produce an answer), and its practical cost includes loading the model as well as generating each token (a small unit of text processed or produced by a model).

Quantization (reducing the numerical precision of a model so it uses less memory and often runs faster) can make local inference practical on smaller hardware, but the trade-off must be measured rather than assumed. Run the lower-precision model behind a local model server—a program on controlled hardware that accepts model requests—and compare model size, memory use, speed, and answer quality with the unmodified version.

CHECK TASK, IMPACT, AND DATA-EGRESS POLICY → USE THE LOCAL QUANTIZED MODEL WHEN SUITABLE → USE CLOUD ONLY WHEN REMOTE PROCESSING IS APPROVED → FAIL CLOSED FOR LOCALITY-RESTRICTED WORK → VALIDATE, STREAM, AND MEASURE

Put local and cloud providers behind one interface so the rest of the agent workflow does not care which one answered. Protect the local path with a health check (a probe that reports whether a service can accept work), request time limits, bounded retries (repeated attempts capped at a fixed count), and a circuit breaker (a guard that temporarily stops requests to a repeatedly failing service). A fallback (a backup route used when the preferred model is unavailable or unsuitable) may use the approved cloud model only when policy permits the prompt to leave the controlled environment. Locality-restricted requests must fail closed or use another approved in-boundary provider; high-impact or complex requests are a separate category and may use cloud only under the same data-egress policy.

A local endpoint removes one network boundary; it does not remove the need for timeouts, privacy controls, answer validation, or an approved fallback.
An honest performance finding: the local server’s first request is often far slower than later requests because it must load the model into memory. Report cold-start performance (speed before the service and model are fully loaded) separately from steady-state performance (speed after startup work is complete); averaging them together gives neither operators nor customers a useful expectation.
In the capstone: Eunomia's provider chain can include a smaller quantized local model as one adapter behind the model gateway, with an approved fallback for difficult savings questions. Lesson 22

Context Caching & Prompt Compression

The problem: Eunomia repeatedly re-sends fixed instructions and long prior turns, increasing token spend and latency until context limits are hit. Skill Reporter has the same growth problem as report conversations and artifacts accumulate unless reusable context is separated from per-turn state.

A model’s context window (the maximum amount of text and other input a model can consider in one request) has to hold system instructions, policy text, tool descriptions, retrieved documents, conversation turns, and the current question. A token budget (the planned limit on the small text units sent to and generated by a model) assigns space to those parts before one of them silently crowds out another.

Separate stable instructions from changing customer content. The stable prefix (the unchanged opening portion of a prompt) can then use context caching (reusing the model provider’s earlier processing of a repeated prompt prefix). Measure request size, reported cache hits and misses (whether reusable work was found or a fresh request was needed), response time, and cost for both cached and uncached calls; a provider-reported hit does not guarantee a meaningful saving if the prefix is small or the rest of the request dominates.

CACHE THE STABLE PREFIX → COMPRESS OLD HISTORY WITH FACT CHECKS → ASSEMBLE IT WITH RECENT TURNS AND THE CURRENT QUESTION → LOOP UNTIL THE PROMPT FITS → REQUEST, STREAM, AND MEASURE

Prompt compression (shortening input while preserving the facts and instructions needed for the current task) should follow a policy, not an improvised “summarize this” request. Keep recent turns verbatim, summarize older turns, retain unresolved tasks and durable preferences, and protect amounts, dates, account constraints, consent decisions, and safety instructions from lossy summarization (shortening that discards some original information). Rebuild the prompt in a fixed order: stable prefix, compressed history, recent messages, then the current question.

from collections.abc import Awaitable, Callable

async def build_prompt(stable: str, turns: list[str], question: str,
                       protected: list[str],
                       summarize: Callable[[list[str]], Awaitable[str]],
                       budget: int = 4_000, output_reserve: int = 800) -> str:
    input_limit = budget - output_reserve
    if input_limit <= 0:
        raise ValueError("Output reserve must be smaller than the token budget")
    recent = turns[-4:]
    compressible = turns[:-4]
    separator = chr(10) * 2
    for _ in range(3):
        compressed = await summarize(compressible) if compressible else ""
        if compressed and not preserves(compressed, protected):
            raise ValueError("Compression removed protected content")
        sections = [stable, compressed, *recent, question]
        prompt = separator.join(section for section in sections if section)
        if token_count(prompt) <= input_limit:
            return prompt
        if not recent:
            break
        compressible.extend(recent[:2])
        recent = recent[2:]
    raise ValueError("Protected prompt content cannot fit within the token budget")
async function buildPrompt(
  stable: string,
  turns: string[],
  question: string,
  protectedFacts: string[],
  summarize: (turns: string[]) => Promise<string>,
  budget = 4_000,
  outputReserve = 800,
): Promise<string> {
  const inputLimit = budget - outputReserve;
  if (inputLimit <= 0) throw new Error("Output reserve must be smaller than the token budget");
  let recent = turns.slice(-4);
  const compressible = turns.slice(0, -4);
  const separator = String.fromCharCode(10, 10);
  for (let round = 0; round < 3; round += 1) {
    const compressed = compressible.length ? await summarize(compressible) : "";
    if (compressed && !preserves(compressed, protectedFacts)) {
      throw new Error("Compression removed protected content");
    }
    const prompt = [stable, compressed, ...recent, question].filter(Boolean).join(separator);
    if (tokenCount(prompt) <= inputLimit) return prompt;
    if (!recent.length) break;
    compressible.push(...recent.slice(0, 2));
    recent = recent.slice(2);
  }
  throw new Error("Protected prompt content cannot fit within the token budget");
}

Report actual request size, cache usage, response time, cost, and any information lost during compression rather than presenting token reduction alone as success.

A real bug to test for: a changing request identifier or timestamp placed inside the supposedly stable prefix invalidates the provider’s context cache on every call. Move changing data after the stable prefix, then verify that reuse returns instead of trusting the prompt’s visual similarity.
In the capstone: Eunomia can reuse its stable operating instructions, the prompt pinned by hash in each run manifest, so repeated turns stay affordable and fast. Compressing older customer dialogue is deferred: in the first release each turn is built from its own frozen evidence, not from a growing transcript. Skill Reporter uses the same instruction reuse, and context compaction for long report threads.
Lesson 31

Dynamic Few-Shot Prompt Calibration

The problem: static examples can improve Eunomia behavior for some requests but degrade others by adding irrelevant tokens and biasing responses. Skill Reporter has the same issue when one fixed few-shot set is applied to every report type regardless of context.

Few-shot examples (a small set of sample questions and good answers placed in the prompt) should come from an approved library, not from raw customer conversations or unreviewed model output. Each entry needs an identifier, question, approved answer, topic, risk level, tool requirements, and version. Establish both a no-example baseline and a fixed-example baseline before building anything more elaborate.

Dynamic selection (choosing examples at request time rather than always using a fixed list) represents the current question and candidate examples by meaning, then filters by safety, topic, and required capabilities. Select a small, diverse set instead of several near-duplicates, enforce a strict token budget for examples, and use no examples when no candidate is relevant enough. That no-example branch is a designed success path, not a retrieval failure.

from dataclasses import dataclass
@dataclass(frozen=True)
class Example:
    id: str
    topic: str
    risk: str
    required_capabilities: frozenset[str]
    tokens: int
    score: float
    approved: bool
def select_examples(candidates: list[Example], risk: str,
                    capabilities: frozenset[str], budget: int = 500) -> list[Example]:
    selected: list[Example] = []
    used_topics: set[str] = set()
    for item in sorted(candidates, key=lambda x: x.score, reverse=True):
        incompatible = item.risk != risk or not item.required_capabilities <= capabilities
        if incompatible or not item.approved or item.score < 0.82 or item.topic in used_topics:
            continue
        if sum(example.tokens for example in selected) + item.tokens > budget:
            continue
        selected.append(item)
        used_topics.add(item.topic)
    return selected[:3]
type Example = {
  id: string; topic: string; risk: "low" | "high";
  requiredCapabilities: string[];
  tokens: number;
  score: number;
  approved: boolean;
};
function selectExamples(
  candidates: Example[],
  risk: "low" | "high",
  capabilities: Set<string>,
  budget = 500,
): Example[] {
  const selected: Example[] = [];
  const usedTopics = new Set<string>();
  let spent = 0;
  for (const item of candidates.toSorted((a, b) => b.score - a.score)) {
    const unsupported = item.requiredCapabilities.some((name) => !capabilities.has(name));
    if (item.risk !== risk || unsupported || !item.approved || item.score < 0.82 || usedTopics.has(item.topic)) continue;
    if (spent + item.tokens > budget) continue;
    selected.push(item);
    usedTopics.add(item.topic);
    spent += item.tokens;
    if (selected.length === 3) break;
  }
  return selected;
}

FILTER THE APPROVED LIBRARY → SEARCH BY MEANING → ENFORCE DIVERSITY AND BUDGET → INCLUDE EXAMPLES ONLY WHEN USEFUL → MEASURE THE RESULT AGAINST THE NO-EXAMPLE PATH

Calibration (adjusting examples and decision rules so the model behaves consistently on the current kind of question) requires evidence. Implement identical selection rules in Python and TypeScript and compare chosen example identifiers, prompt size, response time, cost, and evaluated quality. Use an evaluation set (a saved collection of test questions and expected properties used to measure whether a change helps), including held-out questions (test questions not used to tune the selector). Otherwise the selector may simply learn the known test cases.

Examples are not free guidance. They are extra input that must earn their place through measured improvement.
An honest finding: this pattern may not help as much as expected. For simple or already well-instructed questions, example retrieval can cost more time and money than a small or inconsistent quality gain is worth. Enable dynamic few-shot prompting only for question types where evaluation shows a real benefit.
In the capstone: Eunomia can choose only the examples relevant to the customer’s present savings question—and skip them when they add no measured value—rather than paying to send the same examples every time. Skill Reporter applies the same adaptive example policy to report prompts.
Lesson 38

Streaming Multimodal Tool Calls with Vision

The problem: Eunomia customers may submit screenshots or scanned statements instead of clean text. That adds multimodal context, tool decisions, and streamed progress states, while image text must never become automatic execution authority. Skill Reporter encounters the same multimodal risk when report evidence arrives as images or scans.

A multimodal model (a model that can work with more than one kind of input, such as text and images) can receive customer text alongside a vision input (an image supplied to a model for inspection). The upload path must enforce supported file types, byte limits, image dimensions, and access controls. Store accepted files in short-lived controlled storage and pass image data onward only when the current customer is authorized to access it.

While the model examines the image, streaming (sending parts of a response as they become available rather than waiting for the complete answer) can carry safe progress events. Those events should say what stage is happening without exposing hidden reasoning or presenting an unverified observation as fact. If the model proposes a tool call (a structured request asking application code to perform an allowed action), validate its arguments against a strict schema (rules specifying the allowed fields and value types) and check the customer’s permissions before execution.

CHECK TEXT AND IMAGE ACCESS → STREAM SAFE PROGRESS → VALIDATE ANY PROPOSED TOOL CALL → RETURN THE CHECKED RESULT TO THE MODEL → EMIT ONE FINAL ANSWER OR A CLEAR REFUSAL

Observation and action are separate powers. Reading an amount or instruction in an image must never authorize a transfer, account change, or other consequential operation. After an approved tool finishes, feed its checked result back to the model and continue the same response stream. The stream needs an explicit event order so progress, tool request, tool result, final answer, and completion cannot arrive in an impossible sequence.

Lesson 41

Autonomous Graph Schema Evolution

The problem: Eunomia knowledge graphs only encode relationships they already define. New financial entities or links can be misclassified if forced into old schemas, but uncontrolled schema rewrites can corrupt downstream retrieval. Skill Reporter has the same schema-evolution risk for reporting entities and relationships.

A knowledge graph (a store of facts represented as things and the relationships between them) is governed by a schema (the rules defining which kinds of things and relationships may be stored). When a new fact does not fit, the correct response is neither silent coercion nor immediate mutation. The agent should create a structured proposal containing a relationship name, source type, target type, precise meaning, evidence, and examples.

Schema evolution (a controlled change to those graph rules as new information appears) begins with deterministic checks (checks whose result follows fixed rules rather than model judgment) for registered identifiers, inverse identifiers, and compatible source and target types. A canonical identifier (the one stable identifier assigned to a relationship meaning) plus explicit inverse and direction metadata makes “product offers rate” recognizably the same conceptual path as “rate is offered by product.” Subtle overlap between different meanings still requires model and human review; string normalization alone cannot prove equivalence.

STORE FACTS THAT FIT → PROPOSE RELATIONSHIPS THAT DO NOT → CHECK FOR DUPLICATES → EVALUATE AND GATE → MIGRATE A NEW VERSION → VALIDATE BEFORE ACTIVATION OR ROLL BACK

An evaluator agent (a separate model-based reviewer that checks a proposal against explicit acceptance rules) should assess necessity, clarity, evidence, privacy risk, and compatibility. Model review is not enough for high-impact changes, so deterministic checks and human approval remain in the path. Proposal, approval, migration, and activation are separate states; approval alone never alters production data.

Lesson 42

Agentic Self-Compaction & Hierarchical Memory Summarization

The problem: long Eunomia conversations eventually exceed context windows. Trimming old turns blindly can drop prior commitments, corrections, and unresolved tasks; keeping everything is too expensive. Skill Reporter faces the same memory-loss versus cost trade-off across long report lifecycles.

Self-compaction (the agent’s process for replacing older detailed history with a shorter representation) must begin before the context limit is reached, not after a request fails. Divide state into recent verbatim turns, compacted summaries, durable customer preferences, unresolved tasks, and references to tool results. Each category has different retention rules; an unresolved task should not disappear merely because its original message is old.

A hierarchical summary (memory organized at several levels, such as individual exchanges, conversation stages, and a whole-session summary) compacts small groups of turns into chunks, combines chunks into stage summaries, and maintains one top-level session view. Recent turns remain exact while older material becomes progressively smaller.

COMPACT RECENT TURNS INTO STAGES AND STAGES INTO A SESSION VIEW → VALIDATE FACTS, CORRECTIONS, AND SOURCES AT EACH STEP → KEEP DURABLE FACTS CONNECTED TO EVERY LEVEL → BUILD THE NEXT CONTEXT

A memory invariant (a fact or rule that must remain true through every round of summarization) protects confirmed amounts, deadlines, consent choices, correction history, and promises made to the customer. async function compact(memory: Memory, tokenLimit: number): Promise<Memory> {
  let next = structuredClone(memory);
  if (tokenCount(next.recent) >= tokenLimit * 0.75) {
    const sourceTurns = next.recent.slice(0, -4);
    const text = await summarizer.summarize(sourceTurns, next.invariants);
    if (preserves(text, next.invariants)) {
      const stage = { id: stableSummaryId(sourceTurns), text };
      next.stages.push(stage);
      next.sources[stage.id] = sourceTurns.map(turnId);
      next.recent = next.recent.slice(-4);
    }
  }
  const stageText = next.stages.map((stage) => stage.text);
  if (tokenCount(stageText) >= tokenLimit * 0.5) {
    const inputs = next.session ? [next.session.text, ...stageText] : stageText;
    const text = await summarizer.summarize(inputs, next.invariants);
    if (preserves(text, next.invariants)) {
      const sourceIds = [next.session?.id, ...next.stages.map((stage) => stage.id)].filter(
        (id): id is string => id !== undefined,
      );
      const session = { id: stableSummaryId(sourceIds), text };
      next.sources[session.id] = sourceIds;
      next = { ...next, stages: [], session };
    }
  }
  return next;
}

Lesson 43

Autonomous Agent Self-Reflection & Multi-Turn State Rollbacks

The problem: one unsupported Eunomia assumption can cascade through later tool calls and recommendations. Retrying only the latest step preserves the original bad state, while full restart may repeat valid or external actions. Skill Reporter has the same rollback challenge when an early wrong premise contaminates later report stages.

Self-reflection (a structured check in which the agent evaluates whether recent decisions still satisfy the goal and rules) works only when the state is explicit. Represent each turn with the goal, plan, known facts, tool results, completed actions, and unresolved questions. Trigger reflection on meaningful signals—contradictory evidence, repeated tool failure, a violated constraint, or a failed result check—not after every ordinary turn.

A checkpoint (a saved snapshot of the agent’s internal state at a known stage) should be written before important decisions and before any tool that may change the outside world. Reflection identifies the earliest unsupported decision and chooses a specific checkpoint. A rollback (restoring internal state from an earlier checkpoint) then discards dependent reasoning while preserving evidence that was already valid.

An idempotency key (a stable request identifier used to recognize a repeated operation) belongs in a durable action ledger (a store recording each external operation and its outcome). Where reversal is possible, record a compensation step (a separate operation that counteracts an earlier side effect). These controls protect external actions while reflection repairs internal state.

SAVE CHECKPOINTS → REFLECT ONLY ON FAILURE SIGNALS → IDENTIFY THE EARLIEST INVALID DECISION → RESTORE THE LAST VALID INTERNAL STATE → REVISE THE PLAN WHILE THE EXTERNAL ACTION LEDGER PREVENTS DUPLICATES

A side effect (a real-world change outside the agent’s internal memory, such as updating a record or sending a message) is not undone by restoring memory. The durable ledger must atomically reserve a key with a fingerprint of the intended request before execution, reject reuse with a different payload, and mark the original result after completion. The external provider should also honor the key so a crash after execution but before ledger completion can be reconciled without blindly repeating the action. Human approval remains necessary where correction is consequential.

The snippets below illustrate checkpoint and replay primitives, not the complete reflection policy. A production state machine must still detect a stated trigger, identify the earliest unsupported decision, cap rollback depth, choose the last valid checkpoint, and create a revised plan. The in-memory checkpoint maps are teaching-only; the action ledger interface represents a durable store with an atomic reservation operation.

type State = { goal: string; facts: string[]; plan: string[] };
const checkpoints = new Map<string, State>();
function checkpoint(name: string, state: State): void {
  checkpoints.set(name, structuredClone(state));
}
function rollback(name: string): State {
  const saved = checkpoints.get(name);
  if (!saved) throw new Error(`Unknown checkpoint: ${name}`);
  return structuredClone(saved);
}
async function runOnce(key: string, toolName: string, args: unknown): Promise<unknown> {
  const fingerprint = requestFingerprint(toolName, args);
  const claim = await actionLedger.reserve(key, fingerprint);
  if (claim.status === "completed") return claim.result;
  if (!claim.acquired) return actionLedger.waitForCompletion(key, fingerprint);
  try {
    const result = await tools.execute(toolName, args, { idempotencyKey: key });
    await actionLedger.complete(key, fingerprint, result);
    return result;
  } catch (error) {
    await actionLedger.markOutcomeUnknown(key, fingerprint);
    throw error;
  }
}
