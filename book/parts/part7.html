Lesson 7

OpenTelemetry & Agent Tracing

The problem: when Eunomia returns a slow, incorrect, or surprising savings answer, teams need to know exactly which model and tool steps ran and where delay or error started. Plain logs rarely reconstruct that full execution path. Skill Reporter has the same blind spot when report outputs are late or wrong and the team cannot trace where the pipeline diverged.

OpenTelemetry (a shared standard for creating and exporting operational records from software) gives the request a structured history. A trace (the complete structured record of one request as it moves through a system) begins at the incoming API call. Inside it, each span (one timed operation inside a trace, such as a model call or tool call) records a named piece of work, its duration, and whether it succeeded.

CUSTOMER REQUEST → API SPAN → AGENT SPAN → ORDERED MODEL AND TOOL CHILD SPANS → EXPORTER → INSPECTABLE TRACE STORE

The parent agent span owns child spans for the first model call, the savings-data lookup, and the final model call. Each span can carry safe operational details such as the operation name, model or tool name, elapsed time, and success state. It should not carry the customer's message, account number, balance, or any other private value. The completed trace must be inspected, not merely emitted, to confirm that its parent-child links match the order that really ran.

from collections.abc import Awaitable, Callable
from opentelemetry import trace
from opentelemetry.trace import Status, StatusCode

tracer = trace.get_tracer("eunomia.agent")

async def run_agent(call_tool: Callable[[], Awaitable[str]]) -> str:
    with tracer.start_as_current_span("agent.run") as agent_span:
        agent_span.set_attribute("agent.version", "savings-v3")
        with tracer.start_as_current_span("tool.savings_lookup") as tool_span:
            try:
                result = await call_tool()
            except Exception as exc:
                tool_span.set_attribute("tool.success", False)
                tool_span.record_exception(exc)
                tool_span.set_status(Status(StatusCode.ERROR))
                raise
            tool_span.set_attribute("tool.success", True)
        return result
import { SpanStatusCode, trace } from "@opentelemetry/api";

const tracer = trace.getTracer("eunomia.agent");

export async function runAgent(
  callTool: () => Promise<string>,
): Promise<string> {
  return tracer.startActiveSpan("agent.run", async (agentSpan) => {
    agentSpan.setAttribute("agent.version", "savings-v3");
    try {
      return await tracer.startActiveSpan("tool.savings_lookup", async (toolSpan) => {
        try {
          const result = await callTool();
          toolSpan.setAttribute("tool.success", true);
          return result;
        } catch (error) {
          toolSpan.setAttribute("tool.success", false);
          toolSpan.setStatus({ code: SpanStatusCode.ERROR });
          if (error instanceof Error) toolSpan.recordException(error);
          throw error;
        } finally {
          toolSpan.end();
        }
      });
    } finally {
      agentSpan.end();
    }
  });
}

Context propagation (passing the trace identity from one operation to the next so related spans remain connected) matters when work crosses an asynchronous boundary (a point where work pauses or continues in another task). Python and TypeScript can export the same trace shape, but their libraries may manage the current span differently while work is paused and resumed. A test must therefore prove that later tool work remains beneath the correct request rather than assuming it does.

Tracing is diagnostic support, not part of the customer's transaction. Use an asynchronous batch exporter with a bounded queue and timeout; if capacity is exhausted or export fails, drop or report telemetry separately rather than blocking the customer request.
A real finding worth knowing: side-by-side Python and TypeScript implementations can both show successful tool spans while one language has silently disconnected those spans from the parent request during asynchronous work. Explicit context-propagation checks are required; a green tool span alone proves only that the tool ran.
In the capstone: Eunomia will use OpenTelemetry to connect every API request, model call, and capability call into one inspectable trace across its monorepo (one repository containing the service, its quality checks, its probes and its web client). Skill Reporter will publish the same trace shape so cross-domain investigations use one workflow.
Lesson 10

Evaluation-Driven Development

The problem: Eunomia can look convincing in demos while still failing common, ambiguous, or risk-sensitive customer requests. Without versioned expectations, prompt and policy tweaks become guesswork instead of measurable improvement. Skill Reporter has the same risk: report quality can drift silently unless every change is measured against saved evaluation cases.

Evaluation-Driven Development, or EDD (defining automated quality checks before or while building an AI feature) starts with user failures the team wants to prevent. Each desired behavior becomes an eval case (one saved input with explicit criteria for judging the resulting answer): the input, facts that must appear, behavior that is forbidden, and a scoring rule an engineer can explain.

EXPECTED BEHAVIOR BECOMES A VERSIONED DATASET → BOTH AGENTS RUN THE SAME CASES → SHARED SCORERS PRODUCE ONE COMPARISON REPORT → FAILURES DRIVE THE NEXT CHANGE

A dataset (a versioned collection of eval cases) should cover normal questions, ambiguous requests, unavailable tools, unsafe requests, and attempts to expose private information. The first cases should fail before the missing behavior is implemented. That failure proves the check can detect the problem; making it pass then becomes the feature's acceptance evidence.

from dataclasses import dataclass

@dataclass(frozen=True)
class EvalCase:
    prompt: str
    required: tuple[str, ...]
    forbidden: tuple[str, ...]

def score(case: EvalCase, answer: str) -> bool:
    normalized = " ".join(answer.lower().split())
    has_required = all(term.lower() in normalized for term in case.required)
    has_forbidden = any(term.lower() in normalized for term in case.forbidden)
    return has_required and not has_forbidden
interface EvalCase {
  prompt: string;
  required: string[];
  forbidden: string[];
}

export function score(testCase: EvalCase, answer: string): boolean {
  const normalized = answer.toLowerCase().trim().replace(/\s+/g, " ");
  const hasRequired = testCase.required.every((term) =>
    normalized.includes(term.toLowerCase()),
  );
  const hasForbidden = testCase.forbidden.some((term) =>
    normalized.includes(term.toLowerCase()),
  );
  return hasRequired && !hasForbidden;
}

A scorer (code or a model that turns an answer into a result such as pass, fail, or a numeric score) should match the quality being measured. Required text, valid structure, and forbidden disclosures suit deterministic code. Clarity and relevance need judgment-based scoring. Both Python and TypeScript runners should receive identical cases and write a common report shape, while the readable case descriptions preserve the reason each test exists.

An eval suite is a product specification written as executable examples. If nobody can explain why a case exists, its failure will not guide a useful change.
A real finding worth knowing: the same visible answer can receive different results across language runners when one trims whitespace, parses structured output, or treats a missing field differently. Shared report schemas and normalization rules must be tested as carefully as the agent behavior.
In the capstone: Eunomia will be developed against a versioned eval suite that defines acceptable savings guidance before each feature is considered complete. Skill Reporter will use the same versioned-suite discipline for report-quality expectations.
Lesson 17

Logfire & Distributed Tracing

The problem: one Eunomia request can cross browser, API, agent runtime, and savings tools. Service-local logs may all be correct yet still fail to show which records belong to the same customer interaction or where latency accumulated. Skill Reporter has the same cross-service visibility problem across UI, orchestration, and reporting components.

A distributed trace (one connected record of a request that crosses multiple services or processes) extends the parent-child structure from Lesson 7 across network boundaries. Every service propagates the same trace ID (the shared identifier that links all spans belonging to one request) as part of W3C Trace Context (the standard HTTP headers used to connect tracing spans across services), usually in traceparent. Each hop creates a new span ID for its own work and forwards updated context. Browser-to-API propagation also requires tracing instrumentation and permission to send the cross-origin trace header.

FRONTEND → API → AGENT → SAVINGS TOOL, PROPAGATING W3C TRACE CONTEXT AND EXPORTING THEIR SPANS INTO ONE CROSS-SERVICE TIMELINE

Logfire (an observability platform used to collect, search, and visualize traces and related records) acts as the telemetry backend (the service that stores and displays traces, measurements, and structured logs). Python and TypeScript services export compatible OpenTelemetry data into it while preserving the relationships already created inside each process. One timeline can then separate frontend delay, API processing, model latency (the time an operation takes), and tool latency.

import httpx
from opentelemetry import propagate, trace

tracer = trace.get_tracer("eunomia.api")

async def fetch_savings(url: str) -> dict[str, object]:
    with tracer.start_as_current_span("savings.request"):
        headers: dict[str, str] = {}
        propagate.inject(headers)
        async with httpx.AsyncClient() as client:
            response = await client.get(url, headers=headers)
            response.raise_for_status()
            return response.json()
import { context, propagation, trace } from "@opentelemetry/api";

const tracer = trace.getTracer("eunomia.api");

export async function fetchSavings(url: string): Promise<unknown> {
  return tracer.startActiveSpan("savings.request", async (span) => {
    try {
      const headers: Record<string, string> = {};
      propagation.inject(context.active(), headers);
      const response = await fetch(url, { headers });
      if (!response.ok) throw new Error(`tool returned ${response.status}`);
      return await response.json();
    } finally { span.end(); }
  });
}

Searchable fields should describe operations, versions, timings, and outcomes. Customer messages, account details, and other private data do not belong in the backend. Successful and failed requests can still be compared by status, error category, tool name, and duration without turning observability into a second customer-data store. Use an asynchronous batch processor with a bounded queue and export timeout. When the queue is full or the backend is unavailable, drop or separately report telemetry instead of blocking or failing the customer request.

A real finding worth knowing: if an outgoing request omits or corrupts W3C trace context, the receiving service may silently start a new trace. Both halves look valid in isolation, but the expected single timeline becomes two unrelated ones. Context propagation must therefore be verified at every HTTP (web request) and tool boundary.
In the capstone: Eunomia will send connected traces from its web client, service, model gateway, and capabilities through OpenTelemetry and its masking trace sink, so one savings conversation can be inspected as a single timeline. Logfire is one possible backend for the Python tooling; the TypeScript service exports plain OpenTelemetry. Skill Reporter will emit the same multi-package trace continuity for end-to-end report journeys.
Lesson 19

LLM-as-a-Judge Benchmarking

The problem: exact-text checks cannot judge whether Eunomia guidance is relevant, clear, and evidence-grounded for nuanced customer questions. Human review can judge this, but not at the pace of every code change. Skill Reporter has the same scaling issue when qualitative report quality needs continuous scoring.

LLM-as-a-judge (using a second language model to score another model's answer) provides a repeatable first pass. The judge receives the user's request, the evidence available to the agent, the candidate answer, and a rubric (a written scoring guide that defines what each score means). The rubric must describe observable qualities rather than vague goals such as “be good,” and the result must contain a structured score plus a short reason tied to evidence.

REQUEST + RELEVANT EVIDENCE + CANDIDATE ANSWER + RUBRIC → JUDGE MODEL → STRUCTURED RESULT → COMPARE WITH TRUSTED HUMAN LABELS → ACCEPT OR REVISE THE JUDGE SETUP

A benchmark (a fixed set of cases used to compare quality across versions) needs clear passes, clear failures, and difficult boundary cases. It must also probe order bias, preference for longer answers, leaked reference answers, and preference for wording similar to the rubric. The judge must not receive hidden hints about the expected score, because that would test hint-following rather than answer quality.

Calibration (checking automated scores against trusted human labels to learn whether the judge is reliable) happens before the judge is trusted in automation. Python and TypeScript judge clients run the same labelled examples and normalize their structured outputs into one report. In these abbreviated clients, prompt is assembled beforehand by a separately validated builder from the user request, relevant evidence, candidate answer, and rubric. Direct checks for safety, privacy, and required facts remain separate: a high clarity score can never cancel a prohibited disclosure.

import json
from collections.abc import Awaitable, Callable
from dataclasses import dataclass

@dataclass(frozen=True)
class JudgeResult:
    score: int
    reason: str

async def judge_answer(call_judge: Callable[[str], Awaitable[str]], prompt: str) -> JudgeResult:
    value = json.loads(await call_judge(prompt))
    if not isinstance(value, dict):
        raise ValueError("judge result must be an object")
    score = value.get("score")
    reason = value.get("reason")
    if type(score) is not int or not 1 <= score <= 5:
        raise ValueError("judge returned an invalid score")
    if not isinstance(reason, str) or not reason.strip():
        raise ValueError("judge returned an invalid reason")
    return JudgeResult(score=score, reason=reason.strip())
interface JudgeResult {
  score: number;
  reason: string;
}

type JudgeClient = (prompt: string) => Promise<string>;

export async function judgeAnswer(callJudge: JudgeClient, prompt: string): Promise<JudgeResult> {
  const value: unknown = JSON.parse(await callJudge(prompt));
  if (typeof value !== "object" || value === null) throw new Error("invalid judge result");
  const { score, reason } = value as Record<string, unknown>;
  if (typeof score !== "number" || !Number.isInteger(score) || score < 1 || score > 5) {
    throw new Error("invalid score");
  }
  if (typeof reason !== "string" || !reason.trim()) throw new Error("missing reason");
  return { score, reason: reason.trim() };
}
A real finding worth knowing: a judge may reward a longer answer even when length is absent from the rubric. Calibration cases with equally correct short and long answers expose this verbosity bias, allowing the rubric or judge prompt to be corrected before the score becomes a gate.
In the capstone: Eunomia will use a calibrated judge model to score qualities such as relevance and clarity while retaining direct checks for required safety and privacy behavior. Skill Reporter will follow the same hybrid judge-plus-deterministic-check model.
Lesson 25

CI/CD Eval Gates

The problem: Eunomia evals do not protect production if they run only manually or inconsistently. Every proposed change needs the same automatic gate, and meaningful quality loss must be blocked before merge. Skill Reporter requires the same CI discipline so reporting regressions never ship by accident.

CI/CD (the automated process that builds, tests, and delivers software changes) runs the relevant checks for every pull request (a proposed set of code changes submitted for review before merging). An eval gate (an automated pass-or-fail decision based on evaluation results) turns the report into an enforceable decision instead of an optional attachment.

PULL REQUEST → BUILD → START CONTROLLED SYSTEM → RUN EVALS → REPORT → QUALITY DECISION, WITH INFRASTRUCTURE FAILURE KEPT DISTINCT FROM A PRODUCT PASS

The workflow first builds affected packages, starts the controlled test system, and selects cases based on the changed files. High-risk changes still take the full-suite path. It produces machine-readable results (structured data that software can parse reliably) for automation and a readable artifact for reviewers, including every failed case. New results are compared with an accepted baseline (a trusted earlier result used as the point of comparison) and a threshold (the minimum acceptable score or maximum permitted regression).

Average quality is not enough: one critical safety failure blocks the change even if every ordinary case passes. Model outages, network failures, and broken test infrastructure are reported as inconclusive (unable to establish product quality because the evaluation did not complete reliably) rather than mislabeled as product regressions or, worse, quality passes. Any exception requires an explicit recorded approval; the threshold is never quietly weakened to make a build green.

from typing import Literal, TypedDict

class EvalReport(TypedDict):
    complete: bool
    average_score: float
    critical_failures: list[str]

GateDecision = Literal["pass", "fail", "inconclusive"]

def decide_gate(report: EvalReport, minimum_score: float) -> GateDecision:
    if not report["complete"]:
        return "inconclusive"
    if report["critical_failures"] or report["average_score"] < minimum_score:
        return "fail"
    return "pass"
interface EvalReport {
  complete: boolean;
  averageScore: number;
  criticalFailures: string[];
}

type GateDecision = "pass" | "fail" | "inconclusive";

export function decideGate(report: EvalReport, minimumScore: number): GateDecision {
  if (!report.complete) return "inconclusive";
  const belowThreshold = report.averageScore < minimumScore;
  if (belowThreshold || report.criticalFailures.length > 0) return "fail";
  return "pass";
}
A real finding worth knowing: one language's eval command may exit successfully after recording failed cases while the other returns a failure code. The pipeline must derive its decision from the validated report and its critical-case results, not from command completion alone.
In the capstone: every Eunomia pull request will run the relevant evals automatically and will be blocked when savings-answer quality or a critical safety case falls below its required threshold. Skill Reporter pull requests will use equivalent blocking gates for report correctness and safety.
Lesson 26

Playwright End-to-End Verification

The problem: unit tests can prove isolated Eunomia functions while the real customer journey still fails at authentication, API wiring, streaming, or tool connectivity. The missing proof is a full browser-to-result path. Skill Reporter has the same end-to-end risk unless report-generation journeys are exercised through the actual UI and backend chain.

Playwright (a browser-automation tool that can click, type, and inspect a real web page) runs an end-to-end test, or E2E test (a test that exercises the complete user journey across the frontend and backend). The test starts the frontend, API, supporting services, and controlled model or tool dependencies, opens the actual chat page, and submits a savings question through the same field a customer uses.

PLAYWRIGHT DRIVES A REAL BROWSER THROUGH FRONTEND → API → AGENT AND TOOLS, THEN COLLECTS VISIBLE, NETWORK, SCREENSHOT, AND TRACE EVIDENCE

A locator (a stable rule for finding an element on a page) should use accessible roles (labels such as button or textbox exposed to assistive technology) or deliberate test identifiers (stable names added for automation), not screen coordinates or styling classes. The test waits for a visible completion state rather than sleeping for a guessed number of seconds. It then checks the final answer, tool-derived details, error states, and absence of private internal information. Where both agent variants exist, the same journey runs against the Python-backed and TypeScript-backed systems.

from playwright.async_api import Page, expect

  await page.getByRole("textbox", { name: "Message" }).fill(

When a test fails, screenshots, console errors, failed network requests, and a trace artifact (a saved browser timeline containing actions, page state, and network evidence from a test run) make the failure reproducible. A small critical journey set belongs on pull requests; a broader suite can run on a schedule so feedback remains fast without abandoning coverage.

A real finding worth knowing: a streamed-answer test can pass locally and fail in automation when it waits a fixed number of seconds. Waiting for the page's real completion state takes more care to implement, but it remains reliable when machines, models, or networks run at different speeds.
In the capstone: Eunomia applies this lesson's principle — prove the real running system from outside — through an independent Python probe suite that calls the public HTTP routes instead of driving a browser. A probe submits a savings question, reads the complete typed event stream, checks that it ends with exactly one ending event, and uses the stub upstream's call counts to confirm the expected backend work. Skill Reporter will run the same outside-in proof for report workflows.
Lesson 30

Unified Monorepo Orchestration

The problem: when Eunomia frontend, API, tools, and evals drift across disconnected commands or package boundaries, one package can pass while silently breaking a dependent package. Local developer setups can mask these breakages until clean builds fail. Skill Reporter has the same integration fragility without unified monorepo contracts and shared verification steps.

A monorepo (one repository containing several related software packages) keeps the connected system under one versioned change. A workspace (the package-manager configuration that links local packages and manages their shared installation) defines the package boundaries and their declared dependencies. Source, tests, and build output stay inside the package that owns them; only genuinely common configuration belongs at the root.

ONE EUNOMIA MONOREPO → A SHARED TASK GRAPH ORDERS FRONTEND, API, TOOLS, AND EVAL WORK → LOCAL AND CI COMMANDS USE THE SAME GRAPH AND SAFE CACHE

A task graph (a map showing which build, test, and eval tasks depend on other tasks) compiles (translates source code into runnable output) shared tools before the API or eval runner imports them (loads their exported code). It can run only affected work for quick feedback while retaining one complete verification command. Local development and CI/CD use the same top-level commands, so the automation does not exercise a different system from the developer.

import asyncio
from graphlib import TopologicalSorter

TASKS = {
    "domain:build": set(),
    "service:build": {"domain:build"},
    "quality:test": {"domain:build", "service:build"},
}
COMMANDS = {
    "domain:build": ("pnpm", "--filter", "@eunomia/domain", "build"),
    "service:build": ("pnpm", "--filter", "@eunomia/service", "build"),
    "quality:test": ("pnpm", "--filter", "@eunomia/quality", "test"),
}

async def run_task(name: str) -> None:
    process = await asyncio.create_subprocess_exec(*COMMANDS[name])
    if await process.wait() != 0:
        raise RuntimeError(f"{name} failed")

async def verify() -> None:
    for task in TopologicalSorter(TASKS).static_order():
        await run_task(task)
import { execFile } from "node:child_process";
import { promisify } from "node:util";

const dependencies: Record<string, string[]> = {
  "domain:build": [],
  "service:build": ["domain:build"],
  "quality:test": ["domain:build", "service:build"],
};
const commands: Record<string, string[]> = {
  "domain:build": ["pnpm", "--filter", "@eunomia/domain", "build"],
  "service:build": ["pnpm", "--filter", "@eunomia/service", "build"],
  "quality:test": ["pnpm", "--filter", "@eunomia/quality", "test"],
};
const completed = new Set<string>();
const runFile = promisify(execFile);

async function runTask(name: string): Promise<void> {
  for (const dependency of dependencies[name] ?? []) await runTask(dependency);
  if (completed.has(name)) return;
  const [command, ...args] = commands[name];
  await runFile(command, args);
  completed.add(name);
}

await runTask("quality:test");

A cache (stored output that allows unchanged tasks to be reused instead of run again) is safe for deterministic builds and tests. Live eval results should not be cached when model behavior or external inputs can change, unless every input and version is captured. Shared schemas (strict descriptions of data shapes) and generated types (code-created type definitions) keep tool contracts aligned across API, eval, and frontend packages, while explicit dependency declarations (each package's list of required libraries) prevent a friendly local installation from hiding a broken isolated build (a build run with only that package's declared dependencies).

A real finding worth knowing: a TypeScript workspace import may work locally because a dependency was hoisted (installed in a shared parent location) into reach, then fail in an isolated build because the owning package never declared it. Python can hide the same defect when an undeclared module happens to exist in one developer's environment. Isolation tests expose both cases.
In the capstone: Eunomia will keep its service, quality suite, probes and web client in one repository so the event contract, the scenarios that depend on it and the client that reads it change together and are verified as one connected system. Skill Reporter will use the same monorepo contract discipline so shared schemas evolve safely across packages.
Lesson 56

Last-Approved Baseline Promotion for Eval Gates

The problem: comparing Eunomia to only the latest eval output is unsafe because that baseline may already include accepted or misclassified losses. Repeated small degradations can normalize bad quality. Skill Reporter has the same baseline-drift risk unless promotion always compares against a trusted reference artifact.

A regression (a measurable loss in behavior or answer quality) must be measured against a trustworthy baseline, not simply the nearest file in storage. Every report therefore records its code revision (the exact version of the code that produced it), dataset version, rubric version, threshold-policy version, completeness state, final gate decision, and any manual override with its approval evidence.

CURRENT CHANGE WALKS BACK PAST FAILED AND INCOMPLETE REPORTS → SELECTS THE NEAREST COMPATIBLE PASS → COMPARES CURRENT QUALITY → PROMOTES ONLY AFTER A SUCCESSFUL GATE

An ancestry walk (moving backward through earlier code revisions until a valid historical report is found) begins at the current change's parent and supplies reports newest-first along that ancestry. It rejects reports that are incomplete, did not pass their own gate, were manually overridden without approval evidence, or use incompatible dataset, rubric, or threshold-policy versions. The first remaining pass is therefore the nearest trusted comparison point, and the pull-request report displays both its revision and every rejection reason.

from collections.abc import Iterable
from dataclasses import dataclass
from typing import Literal

@dataclass(frozen=True)
class Report:
    revision: str
    complete: bool
    gate: Literal["pass", "fail", "inconclusive"]
    dataset: str
    rubric: str
    threshold_policy: str
    overridden: bool
    override_approval: str | None

def select_baseline(
    history_newest_first: Iterable[Report],
    dataset: str,
    rubric: str,
    threshold_policy: str,
) -> Report:
    for report in history_newest_first:
        compatible = (
            report.dataset == dataset
            and report.rubric == rubric
            and report.threshold_policy == threshold_policy
        )
        override_valid = not report.overridden or report.override_approval is not None
        if report.complete and report.gate == "pass" and compatible and override_valid:
            return report
    raise LookupError("no compatible passing baseline")
interface Report {
  revision: string;
  complete: boolean;
  gate: "pass" | "fail" | "inconclusive";
  dataset: string;
  rubric: string;
  thresholdPolicy: string;
  overridden: boolean;
  overrideApproval: string | null;
}

export function selectBaseline(
  historyNewestFirst: readonly Report[],
  dataset: string,
  rubric: string,
  thresholdPolicy: string,
): Report {
  for (const report of historyNewestFirst) {
    const compatible =
      report.dataset === dataset &&
      report.rubric === rubric &&
      report.thresholdPolicy === thresholdPolicy;
    const overrideValid = !report.overridden || report.overrideApproval !== null;
    if (report.complete && report.gate === "pass" && compatible && overrideValid) {
      return report;
    }
  }
  throw new Error("no compatible passing baseline");
}

The current result must satisfy fixed minimum requirements as well as stay within the permitted change from the baseline. Missing or corrupt history is an explicit policy state, never an excuse to compare against zero or pass automatically. Baseline promotion (marking a newly passing report as the trusted reference for future comparisons) happens only after the current gate succeeds, with coordination that prevents concurrent builds from promoting older results out of order.

The latest report is a fact about time; the trusted baseline is a fact about quality. They are not interchangeable.
A real finding worth knowing: Python and TypeScript implementations can select different historical reports when one treats a missing gate field as failure while the other treats it as merely absent. A shared report schema and explicit eligibility rules are necessary before both implementations can agree on the baseline.
In the capstone: Eunomia will gate every pull request against the last approved run manifest, a run that fully passed, never against whatever ran most recently, preventing an already-regressed run from becoming the new definition of acceptable quality. Skill Reporter will follow the same trusted-baseline rule for report-quality gates.
Lesson 57

Consecutive-Pass Promotion Windows for Eval Gates

The problem: a single green eval run can be luck, not stability. If Eunomia promotes on one pass, noisy runs can slip through as false confidence. Skill Reporter has the same risk when one-off passes are treated as release-ready evidence.

A promotion window (a required run count that must all pass before release) turns promotion into a stability check, not a moment-in-time check. Day 56 chooses the right baseline; Day 57 adds timing discipline: require consecutive passes and keep the same regression tolerance against the approved baseline on every run inside that window.

RECENT RUNS → CONSECUTIVE-PASS WINDOW + BASELINE TOLERANCE CHECK → PROMOTE ONLY WHEN THE WHOLE WINDOW IS STABLE

from dataclasses import dataclass

@dataclass
class EvalRun:
    run_id: str
    score: float
    gate_passed: bool

def should_promote_after_window(
    history: list[EvalRun],
    approved_baseline_score: float,
    window_size: int = 3,
    max_regression: float = 0.02,
) -> tuple[bool, str]:
    if len(history) < window_size:
        return False, f"need {window_size} runs, got {len(history)}"
    window = history[-window_size:]
    failed = [run.run_id for run in window if not run.gate_passed]
    if failed:
        return False, f"window contains gate failures: {failed}"
    for run in window:
        drop = approved_baseline_score - run.score
        if (drop - max_regression) > 1e-9:
            return False, f"run {run.run_id} regressed {drop:.3f} > allowed {max_regression:.3f}"
    return True, f"{window_size} consecutive passes within regression tolerance"
interface EvalRun {
  runId: string;
  score: number;
  gatePassed: boolean;
}

function shouldPromoteAfterWindow(
  history: EvalRun[],
  approvedBaselineScore: number,
  windowSize = 3,
  maxRegression = 0.02,
): { promote: boolean; reason: string } {
  if (history.length < windowSize) {
    return { promote: false, reason: `need ${windowSize} runs, got ${history.length}` };
  }
  const window = history.slice(-windowSize);
  const failed = window.filter((run) => !run.gatePassed).map((run) => run.runId);
  if (failed.length > 0) {
    return { promote: false, reason: `window contains gate failures: ${JSON.stringify(failed)}` };
  }
  for (const run of window) {
    const drop = approvedBaselineScore - run.score;
    if (drop - maxRegression > 1e-9) {
      return {
        promote: false,
        reason: `run ${run.runId} regressed ${drop.toFixed(3)} > allowed ${maxRegression.toFixed(3)}`,
      };
    }
  }
  return { promote: true, reason: `${windowSize} consecutive passes within regression tolerance` };
}
One passing run proves possibility. A consecutive-pass window proves stability.
A real finding worth knowing: strict floating-point comparisons can falsely block an exact-threshold case (for example 0.020000000000000018 > 0.02). Both implementations now use a tiny epsilon guard so equality at the threshold behaves consistently.
In the capstone: Eunomia's deploy approval only records a run's manifest as a candidate; the approved baseline moves to it only after a window of consecutive passing runs on main with tolerance-safe scores across the whole window. Skill Reporter uses the same rule so promotions are based on sustained quality, not a single lucky run.
Lesson 58

Model Retry Guard with Failure Classification

The problem: naive retry loops cause two failures in production: retrying fatal errors forever, and giving up too early on transient failures that would recover. Eunomia and Skill Reporter both need explicit retry rules with a hard budget.

A retry guard (a policy that decides whether a failed attempt is retried or stopped) classifies failures as transient or fatal, then applies a strict retry budget. Success stops immediately, fatal errors stop immediately, transient errors retry only while budget remains.

ATTEMPT RESULT → FAILURE CLASSIFICATION + RETRY BUDGET → SELECTIVE RETRY OR IMMEDIATE STOP

from dataclasses import dataclass
from enum import Enum

class FailureKind(str, Enum):
    TRANSIENT = "transient"
    FATAL = "fatal"

@dataclass(frozen=True)
class AttemptResult:
    ok: bool
    failure_kind: FailureKind | None = None

def decide_retry(attempt_number: int, max_retries: int, result: AttemptResult) -> tuple[bool, str]:
    if result.ok:
        return False, "success"
    if result.failure_kind == FailureKind.FATAL:
        return False, "fatal error - stop immediately"
    if attempt_number > max_retries:
        return False, f"retry budget exhausted ({max_retries})"
    return True, f"transient error - retry {attempt_number}/{max_retries}"
type FailureKind = "transient" | "fatal";

interface AttemptResult {
  ok: boolean;
  failureKind?: FailureKind;
}

function decideRetry(
  attemptNumber: number,
  maxRetries: number,
  result: AttemptResult,
): { shouldRetry: boolean; reason: string } {
  if (result.ok) return { shouldRetry: false, reason: "success" };
  if (result.failureKind === "fatal") {
    return { shouldRetry: false, reason: "fatal error - stop immediately" };
  }
  if (attemptNumber > maxRetries) {
    return { shouldRetry: false, reason: `retry budget exhausted (${maxRetries})` };
  }
  return { shouldRetry: true, reason: `transient error - retry ${attemptNumber}/${maxRetries}` };
}
Retries are useful only when they are selective and bounded.
A real finding worth knowing: without explicit failure classification, different services interpret the same error differently and create inconsistent retry behavior. A shared failure taxonomy and budget rule keeps retry outcomes predictable across stacks.
In the capstone: Eunomia can recover from transient provider/tool issues without masking hard failures or creating runaway loops. Skill Reporter follows the same retry discipline for deterministic reliability.
Lesson 59

Stateful Evaluator Graph

The problem: when evaluation retry logic is hidden inside nested conditionals, operations teams cannot reliably explain why a run was approved, revised, or rejected. The real problem is deciding the next operational step from state, not just generating text. The graph exists to make control flow explicit: it owns step order, branch rules, and state updates.

LLMs still do useful work inside steps (for example, extracting entities and intent from the customer question), but they do not directly decide control flow. State-machine logic decides what happens next; model inference stays bounded inside each step.

Relationship to Lesson 5: same graph pattern, different scope. Lesson 5 applied stateful graph routing to general workflow paths. Lesson 59 applies stateful graph routing to evaluator operations and terminal decision states (`APPROVED` or `REJECTED`).

DRAFT → EVALUATING → APPROVED OR NEEDS_REVISION LOOP → REJECTED AT ATTEMPT CAP

from dataclasses import dataclass
from enum import Enum

class EvalState(str, Enum):
    DRAFT = "draft"
    EVALUATING = "evaluating"
    NEEDS_REVISION = "needs_revision"
    APPROVED = "approved"
    REJECTED = "rejected"

@dataclass
class EvalContext:
    attempt: int
    max_attempts: int
    score: float
    threshold: float
    state: EvalState = EvalState.DRAFT

def step(context: EvalContext) -> EvalContext:
    if context.state == EvalState.DRAFT:
        context.state = EvalState.EVALUATING
        return context
    if context.state == EvalState.EVALUATING:
        if context.score >= context.threshold:
            context.state = EvalState.APPROVED
            return context
        if context.attempt >= context.max_attempts:
            context.state = EvalState.REJECTED
        else:
            context.attempt += 1
            context.state = EvalState.NEEDS_REVISION
        return context
    if context.state == EvalState.NEEDS_REVISION:
        context.state = EvalState.DRAFT
    return context
The graph decides the operation. The model contributes inside the operation.
In the capstone: Eunomia and Skill Reporter use explicit evaluator states in the quality harness (snapshot, replay, assert, archive) so release decisions are traceable and replayable under retry pressure.
Lesson 60

Human-in-the-Loop Gate for High-Risk Actions

The problem: retry logic and evaluator routing still do not answer who is allowed to execute high-risk actions. Without an explicit gate, an agent can run side effects directly from model output. Eunomia and Skill Reporter need a deterministic approval boundary before execution.

The gate policy is explicit and auditable: low risk with high confidence can auto-approve, low confidence can auto-reject, and high-risk actions must remain pending until a human reviewer approves or rejects them.

In the capstone: Eunomia's read-only first release has no high-impact side effects to gate at runtime; its human decision boundaries are the required reviewer on production deploys and the person at the bottom of the answer sequence. Lesson 64

Jev-Style Decision Layer for Agent Routing

The problem: forcing one intent choice on mixed high-risk prompts can produce confident-looking misroutes. In Eunomia, a wrong route can be worse than pausing for clarification.

The fix is a decision-first route layer: score all allowed intents, pick a typed route, attach a confidence score, and escalate to unknown when confidence is below threshold. In this lesson, the Jev pattern is demonstrated with a deterministic in-repo approximation so it is fully runnable offline: no external Jev API call is required for the benchmark.

def route_with_jev_confidence(message: str, min_confidence: float = 0.45) -> RoutedDecision:
    raw = jev_style_raw_decision(message)
    if raw.confidence < min_confidence and raw.intent != Intent.UNKNOWN:
        return RoutedDecision(intent=Intent.UNKNOWN, confidence=raw.confidence, escalated=True)
    return RoutedDecision(intent=raw.intent, confidence=raw.confidence, escalated=False)

function routeWithJevConfidence(message: string, minConfidence = 0.45): RoutedDecision {
  const raw = jevStyleRawDecision(message);
  if (raw.confidence < minConfidence && raw.intent !== "unknown") {
    return { intent: "unknown", confidence: raw.confidence, escalated: true };
  }
  return { intent: raw.intent, confidence: raw.confidence, escalated: false };
}

function jevStyleRawDecision(message: string): Decision {
  const text = message.toLowerCase();
  const scores: Record<Intent, number> = {
    balance: 0.01,
    coverage: 0.01,
    products: 0.01,
    faq: 0.01,
    simulation: 0.01,
    portfolio: 0.01,
    unknown: 0.01,
  };

  if (text.includes("simulate") || text.includes("simulation") || text.includes("projection") || text.includes("what-if")) {
    scores.simulation += 0.95;
  }
  if (text.includes("portfolio") || text.includes("optimise") || text.includes("optimize")) {
    scores.portfolio += 0.95;
  }
  if (text.includes("cover") || text.includes("safe") || text.includes("fscs") || text.includes("coverage")) {
    scores.coverage += 0.85;
  }

  const total = Object.values(scores).reduce((sum, value) => sum + value, 0);
  const probabilities = Object.entries(scores).map(([intent, score]) => ({
    intent: intent as Intent,
    probability: score / total,
  }));
  probabilities.sort((a, b) => b.probability - a.probability);

  return {
    intent: probabilities[0]?.intent ?? "unknown",
    confidence: probabilities[0]?.probability ?? 0,
  };
}

FIXED INTENT OPTIONS → SCORED DECISION + CONFIDENCE → ROUTE ONLY IF ABOVE THRESHOLD; OTHERWISE ESCALATE

Before/after in this run: baseline keyword routing reached accuracy=0.73 with high_risk_misroutes=2. The Jev-style decision layer reached accuracy=1.00 with high_risk_misroutes=0, and it used one explicit escalation on a low-confidence mixed-intent case. On the current Eunomia eval corpus, the result is parity (1.00 → 1.00 accuracy, 0 → 0 high-risk misroutes), which means no demonstrated gain there yet and no regression.

Why substring checks rather than regex?

Python uses in; TypeScript uses includes(). These keep the keyword-to-score rules easy to read. Both substring checks and regex are deterministic. Substrings can create false matches: “balance” matches “balanced”, and “rate” matches “corporate”. Whole-word regex can prevent some of these mistakes, but neither approach understands negation or intent. These heuristic scores are not calibrated probabilities.
