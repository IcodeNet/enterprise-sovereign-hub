Part VI

Security & Guardrails

A useful agent is not automatically a safe one. This part adds hard checks around replies, hostile prompts, generated patches, tool arguments, permissions, customer data, and human-review sampling. The theme throughout is simple: let AI propose, but make ordinary code, narrow authority, isolated storage, repeatable tests, and people decide what is allowed.

Dual-domain map for this part: every guardrail pattern shown for Eunomia is mirrored for Skill Reporter.

  • Eunomia domain: output guards, injection interception, isolated red-team fuzzing, semantic tool-payload validation, scoped permission tokens, tenant isolation, and deterministic human-review sampling.
  • Skill Reporter domain: output guards on generated reports, injection interception, isolated red-team fuzzing, semantic payload validation for report tools, scoped permission tokens, tenant isolation, and deterministic human-review sampling.

Interlink chain: Lesson 13 blocks unsafe output, Lesson 20 blocks hostile inputs, Lesson 40 stress-tests those controls, Lessons 44 and 52 constrain tool authority, and Lessons 54 and 55 enforce tenant-safe retrieval and auditable human oversight.

Lesson 13

Programmatic Output Guardrails

The problem: Eunomia can draft a convincing financial reply that still leaks private account details, makes unsupported product claims, or phrases guidance in a way policy forbids. Asking another model to judge that draft only swaps one uncertain judgment for another. Skill Reporter has the same risk when generated report text can leak sensitive employer or candidate information.

The dependable final checkpoint is a programmatic guardrail (a rule written in ordinary code that checks an AI reply before it is sent). Each rule performs a deterministic check (a check that produces the same result whenever it receives the same input), so a known-bad draft cannot slip through because a model interpreted it differently this time. The small examples below choose to block rather than rewrite a failed draft.

Many first-line rules use pattern matching (searching text for known words, formats, or character sequences). Here the rules cover only one forbidden claim and one account-number shape; they are not general detectors for PII (personally identifiable information), account data, or unsafe fallback behaviour. The decision point must fail closed (block an action when a safety check fails or cannot finish). A checker timeout is therefore a blocked reply, not permission to send an unchecked one.

import re
from unicodedata import normalize

FORBIDDEN = (r"\bguaranteed return\b", r"\baccount \d{8}\b")

def check_output(draft: str) -> str:
    canonical = " ".join(normalize("NFKC", draft).casefold().split())
    violations = [rule for rule in FORBIDDEN if re.search(rule, canonical)]
    if violations:
        raise ValueError("reply blocked by output guardrail")
    return draft
const forbidden = [/\bguaranteed return\b/u, /\baccount \d{8}\b/u];

export function checkOutput(draft: string): string {
  const canonical = draft
    .normalize("NFKC")
    .toLocaleLowerCase("en-GB")
    .replace(/\s+/gu, " ")
    .trim();
  if (forbidden.some((rule) => rule.test(canonical))) {
    throw new Error("reply blocked by output guardrail");
  }
  return draft;
}

CUSTOMER MESSAGE → AI DRAFT → CODE-BASED CHECKS → SEND ONLY ON PASS; OTHERWISE BLOCK SAFELY AND RECORD A REDACTED AUDIT EVENT

The infrastructure-error branch also kept that failure distinct from a security block. The snippets above have a different, explicit limitation: Python case-folding and TypeScript locale-aware lowercasing are not identical, and neither normalizes punctuation.
In the capstone: every Eunomia draft passes code-based checks before it can reach the customer. The two rules shown here are only examples; production policy needs dedicated, tested detectors for PII, cross-customer account details, unsupported financial claims, and unsafe fallback behaviour. Skill Reporter applies the same deterministic output gate before publishing generated report text.
Lesson 20

AI Red Teaming & Attack Interception

The problem: Eunomia may follow a hostile prompt that asks it to ignore policy, expose hidden account data, or invoke a sensitive tool path. Discovering that weakness only when attacked in production is too late. Skill Reporter is equally exposed when injection attempts try to exfiltrate protected report inputs or bypass publication controls.

Red teaming (deliberately attacking your own system to discover security weaknesses) turns that risk into planned testing. Tests should include prompt injection (instructions designed to make an AI ignore or override the rules it was given) and a jailbreak (an attempt to persuade an AI to bypass its safety restrictions), not just malformed requests.

The first defence is attack interception (detecting and stopping a hostile request before it reaches sensitive data or tools). The snippets below demonstrate only a narrow first gate based on two regular expressions; regex matching is one layer, not sufficient attack detection. Replies and tool requests need separate final security checks because a message that passes the first gate can still lead to an unsafe action. Those later checks appear in the architecture diagram but are not implemented by these snippets.

import re
from unicodedata import normalize

ATTACKS = (r"ignore (all|previous) rules", r"show .*user.?s records")

def intercept_prompt(message: str) -> str:
    canonical = normalize("NFKC", message).casefold()
    if any(re.search(pattern, canonical) for pattern in ATTACKS):
        raise PermissionError("hostile prompt blocked")
    return message

async def handle_message(message: str) -> str:
    return await run_agent(intercept_prompt(message))
const attacks = [/ignore (all|previous) rules/u, /show .*user.?s records/u];

export function interceptPrompt(message: string): string {
  const canonical = message.normalize("NFKC").toLocaleLowerCase("en-GB");
  if (attacks.some((pattern) => pattern.test(canonical))) {
    throw new Error("hostile prompt blocked");
  }
  return message;
}

export async function handleMessage(message: string): Promise<string> {
  return runAgent(interceptPrompt(message));
}

HOSTILE TESTS → EARLY ATTACK DETECTOR → BLOCK OR PROCESS → FINAL CHECK ON BOTH REPLIES AND TOOL REQUESTS

A verified finding from the lesson: the tested detector blocked an obvious attack and allowed a legitimate request in both languages. Ambiguous and obfuscated prompts were not tested, so no broader detection claim follows from that result.
In the capstone: Eunomia is tested with prompt-injection and jailbreak attempts that try to expose another customer's account data, reveal PII (personally identifiable information), or trigger an unauthorized financial action. Every confirmed weakness becomes a repeatable security test. Skill Reporter keeps an equivalent injection/jailbreak corpus for skill-report workflows.
Lesson 40

Autonomous Red-Teaming Fuzzing & Automated Patch Proposals

The problem: Eunomia defenders can hand-write only a small set of attack tests, while real attackers keep mutating wording, encoding, and strategy. Security needs broader automated exploration without giving generated tests or fixes direct production authority. Skill Reporter has the same need as report workflows become externally reachable.

Fuzzing (automatically trying many unusual or hostile inputs to find failures) expands a small seed library into a continuing search. An attacker agent (an AI assigned to generate and vary attacks against another system) tests an isolated target. A breach checker (a separate decision component that evaluates target responses against explicit evidence of a crossed boundary) decides whether an attempt succeeded.

After a verified breach, a patcher agent (an AI assigned to propose a defensive change after a verified failure) can draft a narrow guardrail change. That proposal must face both attack tests and a regression test (a test that ensures a fixed problem does not return and existing behaviour still works). Passing tests earns human review, never automatic deployment. The snippets below show only a minimal breach-detection core: three fixed variants and an exact response marker. The marker can misclassify a refusal that quotes it and miss a leak expressed without it; production verdicts need stronger evidence. The Python and TypeScript variant sets also differ, so shared test cases are required before comparing their behaviour. The diagram shows the larger attacker, patcher, test, and review architecture that is not implemented in these snippets.

from base64 import b64encode
from collections.abc import Awaitable, Callable

async def find_breach(
    seed: str,
    run_isolated: Callable[[str], Awaitable[str]],
) -> str | None:
    variants = {seed, seed.swapcase(), b64encode(seed.encode()).decode()}
    for attack in variants:
        response = await run_isolated(attack)
        if "PRIVATE_RECORD" in response:
            return attack
    return None
type IsolatedRunner = (prompt: string) => Promise<string>;

export async function findBreach(
  seed: string,
  runIsolated: IsolatedRunner,
): Promise<string | undefined> {
  const variants = new Set([
    seed,
    seed.toUpperCase(),
    Buffer.from(seed, "utf8").toString("base64"),
  ]);
  for (const attack of variants) {
    if ((await runIsolated(attack)).includes("PRIVATE_RECORD")) return attack;
  }
  return undefined;
}

ATTACKER VARIES TESTS IN ISOLATION → VERIFIED BREACH → PATCHER PROPOSES → SECURITY AND NORMAL-USE TESTS → HUMAN ALONE APPROVES

An automated patch is a candidate, not a decision. Keep production credentials out of the test environment and require a person to review the code, its evidence, and the behavior it might remove.
A verified finding from the lesson: eleven live attacks across the two languages found no breach. The Python patcher was then exercised with a simulated breach; the TypeScript patcher was not verified end to end. A negative attack run is useful evidence, not proof that no other attack can succeed.
In the capstone: Eunomia uses an isolated attacker-and-patcher loop to search for new ways to leak PII (personally identifiable information), cross customer boundaries, or request unauthorized actions, while tests and human approval remain mandatory before any proposed defense reaches production. Skill Reporter runs the same isolated attacker/patcher cycle against report-generation boundaries.
Lesson 44

Semantic Guardrails for FastMCP Tool Payloads

The problem: a Eunomia tool call can satisfy every schema field and type yet still be unsafe: it may target a forbidden resource, exceed policy limits, or point at another customer's account. Skill Reporter has the same semantic risk when payloads reference disallowed report sources, tenants, or publish scopes despite shape-valid JSON.

FastMCP (a framework for exposing application functions as tools that an AI agent can call) can validate the shape of a tool payload (the collection of argument names and values sent to a tool). Shape checking answers “is this a string?”; it does not answer “is this customer's string allowed to select that resource?”

That second question needs semantic validation (checking what supplied values mean and what effect they could have). Sensitive values should usually come from an allow-list (an explicit list of values or actions that are permitted, with everything else rejected), combined here with ownership and value-limit checks before real tool logic is reachable. If a richer payload later includes query text, filters, or nested values, those fields need their own validation; the examples below do not inspect fields they do not define.

from dataclasses import dataclass

ALLOWED_TABLES = {"balances", "transactions"}

@dataclass(frozen=True)
class ToolPayload:
    table: str
    account_id: str
    limit: int

def validate_payload(payload: ToolPayload, owned_accounts: set[str]) -> None:
    if payload.table not in ALLOWED_TABLES:
        raise PermissionError("table is not allowed")
    if payload.account_id not in owned_accounts:
        raise PermissionError("account is not owned by caller")
    if not 1 <= payload.limit <= 100:
        raise ValueError("limit is outside the allowed range")
interface ToolPayload {
  table: string;
  accountId: string;
  limit: number;
}

const allowedTables = new Set(["balances", "transactions"]);

export function validatePayload(
  payload: ToolPayload,
  ownedAccounts: ReadonlySet<string>,
): void {
  if (!allowedTables.has(payload.table)) throw new Error("table is not allowed");
  if (!ownedAccounts.has(payload.accountId)) throw new Error("account is not owned");
  if (!Number.isInteger(payload.limit) || payload.limit < 1 || payload.limit > 100) {
    throw new Error("limit is outside the allowed range");
  }
}

VALIDATE PAYLOAD SHAPE → VALIDATE ITS MEANING → EXECUTE ONLY ALLOWED ARGUMENTS; MALFORMED OR DANGEROUS REQUESTS NEVER REACH THE TOOL

A verified finding from the lesson: the Python guard caught a transformed SQL-injection attempt (specially crafted input intended to change the query a tool executes). In TypeScript, the model refused the sensitive-table request before calling the tool, so the guard was verified separately rather than through that live path.
In the capstone: Eunomia validates each capability argument with domain rules (a minimum term no greater than the maximum, a rate filter within a realistic range), and no capability accepts a customer or account identifier at all, so a caller cannot substitute another customer's account; scope comes only from the verified token. Additional payload fields require additional checks. Skill Reporter applies the same semantic validation to report-query payloads before tools run.
Lesson 52

Cryptographic Tool Permission Scoping

The problem: Eunomia' sensitive tools cannot trust an agent request just because it sounds confident or includes a customer ID. They need cryptographic proof that a trusted authority approved this exact caller, action, resource, amount, and time window. Skill Reporter needs the same proof model for privileged report publication and distribution actions.

A digital signature (cryptographic proof that data was approved by the holder of a secret signing key and was not changed afterward) turns an approval into something the tool can verify. The signed permission token (a signed package describing exactly which action a caller may perform) travels with the tool request, but the signing key never does. These examples use a JWT (JSON Web Token, a standard signed claims format) and RS256 (an algorithm in which a private key signs and a corresponding public key verifies but cannot sign).

The verifier enforces the token's permission scope (the narrow set of tools, actions, resources, values, and time limits covered by an approval), comparing every claim with the requested operation. The exp claim is the expiry time. The jti claim is a unique token identifier used to stop a replay attack (reusing a valid past permission to repeat an action that should happen only once). A production replay store must atomically consume that identifier in shared storage and retain it until expiry, so concurrent workers and restarts cannot reuse it.

from typing import Protocol

import jwt

class ReplayStore(Protocol):
    async def consume_once(self, jti: str, expires_at: int) -> bool: ...

async def verify_permission(
    token: str,
    public_key: str,
    request: dict[str, object],
    replay_store: ReplayStore,
) -> None:
    required = ["tool", "caller", "action", "resource", "amount", "exp", "jti"]
    claims = jwt.decode(
        token, public_key, algorithms=["RS256"],
        audience="eunomia-tools", issuer="eunomia-auth",
        options={"require": required},
    )
    for field in ("tool", "caller", "action", "resource", "amount"):
        if claims[field] != request.get(field):
            raise PermissionError(f"scope mismatch: {field}")
    if not await replay_store.consume_once(str(claims["jti"]), int(claims["exp"])):
        raise PermissionError("permission token already used")
import { jwtVerify, type KeyLike } from "jose";

interface ReplayStore {
  consumeOnce(jti: string, expiresAt: number): Promise<boolean>;
}

export async function verifyPermission(
  token: string,
  publicKey: KeyLike,
  request: Record<string, unknown>,
  replayStore: ReplayStore,
): Promise<void> {
  const requiredClaims = ["tool", "caller", "action", "resource", "amount", "exp", "jti"];
  const { payload } = await jwtVerify(token, publicKey, {
    algorithms: ["RS256"], audience: "eunomia-tools", issuer: "eunomia-auth",
    requiredClaims,
  });
  for (const field of ["tool", "caller", "action", "resource", "amount"] as const) {
    if (payload[field] !== request[field]) throw new Error(`scope mismatch: ${field}`);
  }
  if (!(await replayStore.consumeOnce(payload.jti!, payload.exp!))) {
    throw new Error("token already used");
  }
}

TRUSTED SERVICE SIGNS A NARROW TOKEN → VERIFIER COMPARES EVERY CLAIM WITH THE TOOL REQUEST → EXECUTE ONLY IF ALL CHECKS PASS

A valid signature proves who signed the token and that it was not altered. It does not prove that the signed permission matches the action now being requested; the verifier must establish both facts.
A verified finding from the source lesson: its HMAC-scoped tool errors were absorbed into structured failure output rather than propagated as exceptions. The asymmetric JWT design above is a teaching extension, not the implementation verified by that exercise.
In the capstone: Eunomia's read-only first release applies this lesson only as a principle: least authority, with scope taken from the verified customer token and three capabilities that cannot act. Signed, per-action permission tokens are deferred to the write actions of a later release, where a sensitive action will run only when a token authorizes that exact action for the authenticated customer. Skill Reporter follows the same plan for privileged report operations.
Lesson 54

Distributed Vector Sharding & Tenant Isolation

The problem: Eunomia serves many customers through shared infrastructure. One missing tenant boundary can place one customer's records into another customer's retrieval path, logs, cache, or agent context before cleanup code can react. Skill Reporter has the same exposure across workspaces if tenant boundaries are not enforced at every retrieval and storage layer.

Vector search (finding records by comparing numerical representations of their meaning rather than matching only exact words) is powerful, but its nearest matches must stay inside the right security boundary. Each tenant (one customer or customer organization whose data must remain separate from every other customer's data) should be routed before search begins.

A shard (a physically or logically separate portion of a larger data store) can give each tenant its own index, records, and access policy. This supports tenant isolation (preventing one customer from reading, changing, or searching another customer's data), but the in-process maps below demonstrate only logical routing. They do not create independent storage or access-control boundaries. In production, the authenticated tenant must come from verified server-side identity claims—never the model or request body—and the data plane must enforce separate credentials or equivalent per-tenant authorization.

from typing import Protocol

class VectorShard(Protocol):
    async def search(self, query: str) -> list[str]: ...

async def tenant_search(
    authenticated_tenant: str,
    requested_tenant: str,
    query: str,
    shards: dict[str, VectorShard],
) -> list[str]:
    if requested_tenant != authenticated_tenant:
        raise PermissionError("tenant mismatch")
    shard = shards.get(authenticated_tenant)
    if shard is None:
        raise PermissionError("unknown tenant")
    return await shard.search(query)
interface VectorShard {
  search(query: string): Promise<string[]>;
}

export async function tenantSearch(
  authenticatedTenant: string,
  requestedTenant: string,
  query: string,
  shards: ReadonlyMap<string, VectorShard>,
): Promise<string[]> {
  if (requestedTenant !== authenticatedTenant) throw new Error("tenant mismatch");
  const shard = shards.get(authenticatedTenant);
  if (!shard) throw new Error("unknown tenant");
  return shard.search(query);
}

AUTHENTICATE → SELECT ONE TENANT ROUTE BEFORE SEARCH → QUERY ONLY THAT SHARD → RETURN SAME-TENANT RESULTS; PRODUCTION STORAGE MUST ENFORCE THE BOUNDARY

A verified finding from the lesson: storage isolation held, but the Python agent fabricated its self-reported tenant identifier. The TypeScript path avoided that bug by supplying trusted metadata explicitly. Security routing must therefore use verified server-side identity, not model-reported metadata.
In the capstone: Eunomia applies this lesson's isolation principle without per-tenant vector shards: every port call is scoped to the customer in the verified token, no customer data enters the shared guidance or catalogue indexes, and the evidence route answers another customer's turn with a 404. Per-tenant storage enforcement becomes required if customer documents are ever indexed. Skill Reporter mirrors this with strict workspace-level retrieval isolation.
Lesson 55

Deterministic Hash-Based Sampling for Review Queues

The problem: Eunomia operations can manually inspect only a fraction of interactions, especially around high-risk financial guidance. Naive random sampling chooses different records on every run, making audits irreproducible. Skill Reporter needs the same deterministic review sampling so publication-risk reviews are repeatable and defensible.

A cryptographic hash (a one-way calculation that gives the same fixed-length output for the same input, while a small input change normally gives a very different output that is hard to predict) can map each interaction into a numeric bucket. Deterministic sampling (selecting items by a repeatable rule rather than a new random choice on every run) sends buckets below a policy threshold for inspection. The threshold uses basis points: one basis point is one hundredth of one percent, so 10,000 basis points is 100%.

The input needs a stable identifier (a value that continues to identify the same item across retries and systems), plus an explicit policy version. Selected, safely redacted interactions enter a review queue (a list of selected interactions waiting for a person to inspect). The same identifier and policy reproduce the same result later.

from hashlib import sha256

def should_review(
    interaction_id: str,
    policy_version: str,
    threshold_basis_points: int,
) -> bool:
    if not 0 <= threshold_basis_points <= 10_000:
        raise ValueError("threshold must be from 0 to 10,000 basis points")
    policy = policy_version.encode("utf-8")
    interaction = interaction_id.encode("utf-8")
    stable_key = len(policy).to_bytes(4, "big") + policy + interaction
    digest = sha256(stable_key).digest()
    bucket = int.from_bytes(digest[:8], byteorder="big") % 10_000
    return bucket < threshold_basis_points
import { createHash } from "node:crypto";

export function shouldReview(
  interactionId: string,
  policyVersion: string,
  thresholdBasisPoints: number,
): boolean {
  if (!Number.isInteger(thresholdBasisPoints) ||
      thresholdBasisPoints < 0 || thresholdBasisPoints > 10_000) {
    throw new Error("threshold must be from 0 to 10,000 basis points");
  }
  const policy = Buffer.from(policyVersion, "utf8");
  const length = Buffer.alloc(4);
  length.writeUInt32BE(policy.length);
  const stableKey = Buffer.concat([length, policy, Buffer.from(interactionId, "utf8")]);
  const digest = createHash("sha256").update(stableKey).digest();
  const bucket = Number(digest.readBigUInt64BE(0) % 10_000n);
  return bucket < thresholdBasisPoints;
}

STABLE ID + VERSIONED POLICY → FIXED HASH → NUMERIC BUCKET → REPEATABLE REVIEW DECISION, INCLUDING DURING A LATER AUDIT

A verified finding from the lesson: Python and TypeScript agreed exactly: over 50,000 identifiers the observed review rate was 0.1006, sampled counts were identical, and increasing the threshold produced a verified monotonic superset. Shared test vectors should preserve that agreement.
In the capstone: Eunomia's first release uses stable, hash-based selection on its quality runs: a reproducible share of passing scenario runs goes to human review, and every failure goes regardless of the sample, including any suspected PII (personally identifiable information) leak or cross-customer access. Live turns reach review through the explicit review route and through handoffs; hash-sampling live traffic is deferred to a later release. Skill Reporter uses the same deterministic sampling and mandatory-escalation rules for high-risk report outputs.
