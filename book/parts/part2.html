Part II

Giving Agents Tools at Scale (Protocols & Dynamic Tooling)

A tool written inside one agent works until another agent needs it, a team changes it, or live data moves underneath it. This part replaces that brittle arrangement in five steps: put tools behind a standard server, discover them while the agent is running, subscribe to changing resources, register carefully generated tools without a restart, and build input checks from every tool's own description. Read Lessons 6, 23, 32, 33 and 48 in that order: each adds the piece the next one depends on.

Dual-domain map for this part: every mechanism is shown in the fintech Eunomia implementation and should be mirrored in the Skill Reporter implementation.

  • Fintech domain: balances, savings goals, interest projection, and runtime safety boundaries around customer-impacting tools.
  • Skill Reporter domain: skill lookup, report generation, report-ready updates, and runtime safety boundaries around publishing/reporting tools.

Interlink chain: Lesson 6 creates shared MCP servers, 23 discovers tools at runtime, 32 pushes live updates, 33 adds sandboxed runtime registration, and 48 validates every call against advertised schemas.

Lesson 6

MCP Server Architecture with FastMCP and the TypeScript SDK

The problem: a balance-checking tool starts life inside one assistant. When a second assistant needs the same capability, copying the function feels harmless, but there are now two implementations to secure, test and keep in step. Add more agents and every fix becomes a synchronisation problem. The Skill Reporter agent hits the same failure mode when skill-lookup and report-formatting functions get copied across assistants.

The replacement is MCP — Model Context Protocol (a published set of rules for how an AI agent asks a separate program what tools it has and then calls one). The functions move into an MCP server (the separate program that owns the tools and answers an agent's requests, rather than living inside the agent). Any compliant client can now use one shared implementation, whether that client is written in Python, TypeScript or something else. FastMCP (a Python framework for implementing MCP servers) powers the Python examples; the TypeScript examples use the MCP TypeScript SDK.

Client and server still need a transport (the wire that carries their messages). stdio, standard input/output, pipes text between one client and the server process it launches on the same machine; several clients therefore launch separate processes from the same server implementation. HTTP, Hypertext Transfer Protocol, lets several clients connect over a network to one server process. When a client asks what is available, the server returns a tool schema (a machine-readable description, usually expressed as JavaScript Object Notation or JSON, of a tool's name, purpose and required inputs). FastMCP builds that description from the registered Python function, so a function written once becomes both executable code and a discoverable contract.

from fastmcp import FastMCP

mcp = FastMCP("Eunomia")

@mcp.tool
async def get_balance(account_id: str) -> dict[str, int | str]:
    """Return the current balance in pence."""
    return {"account_id": account_id, "balance_pence": 125_00}

if __name__ == "__main__":
    mcp.run(transport="stdio")
import { McpServer } from "@modelcontextprotocol/sdk/server/mcp.js";
import { StdioServerTransport } from "@modelcontextprotocol/sdk/server/stdio.js";
import { z } from "zod";

const server = new McpServer({ name: "eunomia", version: "1.0.0" });
server.registerTool("get_balance", {
  description: "Return the current balance in pence",
  inputSchema: { accountId: z.string() },
}, async ({ accountId }) => ({
  content: [{ type: "text", text: JSON.stringify({ accountId, balancePence: 12500 }) }],
}));
await server.connect(new StdioServerTransport());

TWO HTTP CLIENTS → ONE NETWORK SERVER; STDIO CLIENTS INSTEAD LAUNCH SEPARATE SERVER PROCESSES FROM ONE SHARED IMPLEMENTATION

A real finding worth knowing: with the stdio transport, an ordinary debug print to standard output corrupts the protocol's message stream. The client then fails with a confusing parse error that points away from the real cause. Logs must go to standard error instead. The same trap exists in both versions: Python's print and TypeScript's console.log are unsafe on that channel.
In the capstone: this is where Eunomia's optional MCP server is born, and the Skill Reporter server follows the same shape. Guidance lookup and catalogue queries stay in the service, and the optional MCP server is a second adapter that exposes those same reviewed implementations to other approved hosts, while the customer's own account snapshot never leaves the service; skill lookup and report-formatting tools do the same in the Skill Reporter stack. An HTTP deployment can serve both halves of either server from one process; a stdio deployment starts one server process per client. Lesson 23 then shows how the hosts that consume such a server discover its tools instead of hardcoding them.
Lesson 23

Dynamic Tool Discovery & MCP Client Connection

The problem: in Eunomia, compliance can require a new tool immediately — for example, splitting "general savings question" from "regulated advice request" before any answer is shown. If the agent carries a hardcoded tool list, that urgent server-side tool cannot be used until the agent is edited, rebuilt and redeployed. Skill Reporter hits the same failure mode when a new report-validation or publishing-safety tool exists on the server but the running agent still cannot see it.

An MCP client (the part of the agent that connects to an MCP server, sends requests and reads replies) removes that last fixed list. It performs runtime discovery (finding which tools exist while the program is running, rather than fixing the list when the code is built). In Eunomia, this means newly deployed account-check, consent-check, or simulation-gate tools become callable without waiting for an app redeploy. In Skill Reporter, newly deployed report-quality and publish-policy tools become callable the same way. The client opens a session (the live connection and context used for discovery and calls) and begins it with a handshake (the opening initialize exchange in which client and server agree on a protocol version), then asks for the current tools.

The reply is a tool manifest (the server's list of each tool's name, description and input schema). A production client follows pagination until it has every page, then converts the complete manifest into definitions the large language model (the AI model that selects and calls tools), or LLM, can see. When the model selects one, a long-lived client sends the call through the still-open session. The short excerpts below demonstrate discovery only: both deliberately close after reading the first page, so they must not be used as the owner of an agent-lifetime session.

from mcp import ClientSession, StdioServerParameters
from mcp.client.stdio import stdio_client

async def discover_tools() -> list[str]:
    params = StdioServerParameters(command="python", args=["eunomia_server.py"])
    async with stdio_client(params) as (read, write):
        async with ClientSession(read, write) as session:
            await session.initialize()
            manifest = await session.list_tools()
            return [tool.name for tool in manifest.tools]
import { Client } from "@modelcontextprotocol/sdk/client/index.js";
import { StdioClientTransport } from "@modelcontextprotocol/sdk/client/stdio.js";

const client = new Client({ name: "eunomia-agent", version: "1.0.0" });
const transport = new StdioClientTransport({
  command: "python",
  args: ["eunomia_server.py"],
});

try {
  await client.connect(transport);
  const manifest = await client.listTools();
  const toolNames: string[] = manifest.tools.map((tool) => tool.name);
} finally {
  await client.close();
}

HANDSHAKE → ASK THE SERVER WHAT EXISTS NOW → CONVERT ITS MANIFEST FOR THE LLM → CALL THE SELECTED TOOL

A real finding worth knowing: the two SDKs (software development kits, meaning the official client libraries) manage connection lifetime differently. Python ties the session to an async with block; TypeScript needs an explicit close call. Discovery helpers such as those above cannot later call a selected tool because they close before returning. An agent therefore needs a long-lived owner that keeps the session open through discovery and calls, follows every manifest page, and closes only during shutdown.
In the capstone: Eunomia's own service deliberately keeps a fixed, reviewed set of three capabilities, because each one is part of a gated release. Runtime discovery applies to the other approved hosts that consume Eunomia's optional MCP server (building on the server from Lesson 6), and Skill Reporter's consumers use the same long-lived pattern against its server. Each MCP client connects at startup, reads every page of the current manifest, builds its toolset and keeps that session available for calls until shutdown, so a consumer picks up a new server tool without its own redeploy. Lesson 32 layers live updates on top of this discovered toolset.
Lesson 32

MCP Real-Time Resource Subscriptions

The problem: discovering tools at startup solves a changing catalogue, but Eunomia still needs fresh customer state during the conversation — balance, goal progress, and eligibility facts that can change after a deposit or profile update. Polling for those changes wastes calls and can leave Eunomia speaking from stale data. Skill Reporter has the same issue for report-ready state and policy updates during an active publishing workflow.

In MCP, a resource (readable data exposed by the server at an address, rather than an action to perform) might live at eunomia://accounts/123/balance. That address is a Uniform Resource Identifier, or URI (the name of a particular MCP resource). The simplest way to watch it is polling (asking the same question again and again on a timer to see if the answer changed), but most requests return “no” and the client can remain stale until the next timer fires.

A subscription (a standing request asking the server to report whenever a named resource changes) reverses that flow. On a deposit, the server sends a notification (a one-way message that expects no reply, here saying that a resource address was updated). The client reads the resource once and receives the fresh balance without a loop of empty checks. A multi-client server must record subscribed URIs separately for each live session, remove them on unsubscribe or disconnect, and notify only the relevant sessions.

The excerpts below isolate the update mechanism for one connected client. They do not implement production subscription routing: the Python call targets the session that invoked the tool, and the TypeScript set assumes exactly one connection.

from fastmcp import Context, FastMCP
from pydantic import AnyUrl

mcp = FastMCP("Eunomia")
balances: dict[str, int] = {"123": 125_00}

@mcp.resource("eunomia://accounts/{account_id}/balance")
async def balance(account_id: str) -> str:
    return str(balances[account_id])

@mcp.tool
async def record_deposit(account_id: str, pence: int, ctx: Context) -> str:
    balances[account_id] += pence
    uri = AnyUrl(f"eunomia://accounts/{account_id}/balance")
    await ctx.session.send_resource_updated(uri)
    return "deposit recorded"
import { McpServer } from "@modelcontextprotocol/sdk/server/mcp.js";
import { SubscribeRequestSchema } from "@modelcontextprotocol/sdk/types.js";

const server = new McpServer(
  { name: "eunomia", version: "1.0.0" },
  { capabilities: { resources: { subscribe: true } } },
);
const subscribedUrisForThisConnection = new Set<string>();
server.server.setRequestHandler(SubscribeRequestSchema, async (request) => {
  subscribedUrisForThisConnection.add(request.params.uri);
  return {};
});

async function balanceChanged(uri: string): Promise<void> {
  if (subscribedUrisForThisConnection.has(uri)) {
    await server.server.sendResourceUpdated({ uri });
  }
}

POLLING REPEATS EMPTY CALLS AND CAN BE STALE; A SUBSCRIPTION PUSHES ONE ADDRESS UPDATE, THEN THE CLIENT READS ONCE

A resource update is a signal, not a durable event log. Subscriptions improve live responsiveness; they do not guarantee that a disconnected client can recover every change it missed.
A real finding worth knowing: the TypeScript excerpt is a handler fragment layered onto Lesson 6's connected server; by itself it omits the transport connection bootstrap and is not standalone. The notification contains only the resource's address, not its new value, so the client must perform a second read. Nothing replays an update that happened before subscription setup or while the connection was down; it is simply lost. The one-client excerpts above are not sufficient for a shared network server: that version also needs per-session subscribe and unsubscribe handling, disconnect cleanup, a resource-read handler and dispatch only to sessions subscribed to the changed URI. Subscription APIs vary between SDK versions, so the installed version and transport must be checked before the design relies on them.
In the capstone: Eunomia's read-only first release does not subscribe to a customer's balance or savings-goal progress: each turn reads a fresh snapshot through readSnapshot and freezes it as evidence. Subscriptions appear only at the optional MCP server, where a host can be told that the catalogue version changed and then re-read it, while a turn already in progress keeps its pinned catalogue version. Skill Reporter applies the same subscription pattern to report-ready and policy-update resources so publication decisions use fresh state instead of stale polling snapshots.
Lesson 33

Dynamic Tool Synthesis & Runtime Registration

The problem: Eunomia can receive customer questions that need a narrow helper tool that does not exist yet (for example, a specific savings projection transform). If every tool must be prewritten, discovery can only confirm the gap and the customer flow stalls until a developer ships a new release. Skill Reporter encounters the same stall when a report-formatting helper is missing in the middle of a reporting run.

Tool synthesis (having an AI or code generator write the source of a new tool function instead of a human writing it) can fill narrow, low-risk gaps. In Eunomia, that means bounded read-only helpers such as calculations or formatting, never money movement or customer-record mutation. In Skill Reporter, that means bounded report-transformation helpers, never privileged publication actions. Before registration, generated source must pass syntax checks, an import allow-list, known test inputs and a sandbox run. A sandbox (a locked-down environment where untrusted code has limited access) is essential because generated source must be treated as hostile until proven otherwise.

If that separate gate succeeds, runtime registration (adding a tool to a running server's catalogue without restarting it) makes the function available. Connected clients must then be told to request the tool list again. In FastMCP, automatic tools/list_changed notifications (messages telling clients that the catalogue changed) depend on registration occurring in an active MCP request context; otherwise the application must arrange notification explicitly. The excerpts below show only the final registration step after the omitted gate has completed, not code generation or sandboxing.

from math import ceil
from fastmcp import FastMCP

mcp = FastMCP("Eunomia")

def months_to_goal(target_pence: int, monthly_pence: int) -> int:
    """Calculate whole months needed to reach a savings target."""
    if target_pence <= 0 or monthly_pence <= 0:
        raise ValueError("amounts must be positive")
    return ceil(target_pence / monthly_pence)

def register_validated_tool() -> None:
    mcp.add_tool(months_to_goal)
import { McpServer } from "@modelcontextprotocol/sdk/server/mcp.js";
import { z } from "zod";

function registerMonthsToGoal(server: McpServer): void {
  server.registerTool("months_to_goal", {
    description: "Calculate whole months needed to reach a savings target",
    inputSchema: {
      targetPence: z.number().int().positive(),
      monthlyPence: z.number().int().positive(),
    },
  }, async ({ targetPence, monthlyPence }) => ({
    content: [{
      type: "text",
      text: String(Math.ceil(targetPence / monthlyPence)),
    }],
  }));
}

MISSING CAPABILITY → GENERATE IN A SANDBOX → VALIDATE OR REJECT → REGISTER → NOTIFY WHERE CONFIGURED → RE-LIST → USE

Eunomia may synthesise a small calculator for a savings projection or “what-if” deposit scenario. It must never synthesise code that moves money or reads customer records; those tools remain human-written, reviewed and deliberately deployed.
A real finding worth knowing: Python can derive a tool's input schema from type hints (annotations that state the expected Python types), but the manifest produced for an unannotated parameter is FastMCP-version-dependent and must be inspected against the pinned package version. TypeScript types are erased at runtime, so a runtime schema must be supplied explicitly. In either language, exec and eval execute source text at runtime; passing generated text to them outside the omitted sandbox and validation gate would bypass the protection this design requires.
In the capstone: Eunomia's first release deliberately does not synthesise or register tools at runtime: its three capabilities and the two tools on its optional MCP server are written by people, reviewed, and shipped through the quality gate, so the advertised contract changes only through a release. If synthesis is added later, this lesson's rules hold: only low-risk calculator or formatting helpers, only a complete implementation may register one, and Lesson 48 checks every call against advertised schemas before execution. The boundary must be capability-based (generated code is technically denied powers it was not granted), not merely a warning in a prompt: the sandbox gives generated code no access to money movement or customer data in Eunomia, and no access to protected report destinations in Skill Reporter, which defers synthesis the same way.
Lesson 48

Dynamic Tool Schema Introspection for Runtime-Registered Tools

The problem: an agent can now discover old and newly synthesised tools, but discovery alone does not prove that the arguments it sends are valid. In Eunomia, malformed arguments can hit account-scoped or simulation-gated financial logic with unclear failures; in Skill Reporter, malformed arguments can reach report-generation or publish-policy tools and fail too late. Without a local checker, both systems push bad input into critical paths instead of stopping early with a repairable error.

Every manifest carries JSON Schema (a standard, written in JSON, that describes what data must look like, including field types and which fields are required). The client uses introspection (examining a description at runtime to learn its structure) to turn that advertised schema into executable validation before making a call.

Python and TypeScript use Pydantic / Zod (validation libraries for Python and TypeScript respectively, which reject data that does not match a declared shape and return clear errors). Here the declaration is not handwritten: the converter creates a dynamic model (a validation class or schema object built by code while the program runs). Valid arguments proceed to the server; invalid ones become a structured error the language model can use to repair its next attempt.

The converters below are deliberately incomplete sketches for a small flat subset. They do not preserve all JSON Schema semantics and must not be treated as production validation.

from typing import Any
from pydantic import BaseModel, create_model

JSON_TYPES: dict[str, type] = {"string": str, "number": float, "integer": int}

def validator_for(name: str, schema: dict[str, Any]) -> type[BaseModel]:
    required = set(schema.get("required", []))
    fields = {
        key: (JSON_TYPES[value["type"]], ... if key in required else None)
        for key, value in schema["properties"].items()
    }
    return create_model(f"{name}Arguments", **fields)

tool_schema: dict[str, Any] = {
    "type": "object",
    "properties": {
        "target": {"type": "number"},
        "monthly": {"type": "number"},
    },
    "required": ["target", "monthly"],
}
Arguments = validator_for("months_to_goal", tool_schema)
validated = Arguments.model_validate({"target": 2000, "monthly": 150})
import { z, type ZodTypeAny } from "zod";

type JsonSchema = {
  properties: Record<string, { type: "string" | "number" }>;
  required?: string[];
};
const jsonTypes: Record<string, ZodTypeAny> = {
  string: z.string(),
  number: z.number(),
};

function validatorFor(schema: JsonSchema): z.ZodObject<Record<string, ZodTypeAny>> {
  const required = new Set(schema.required ?? []);
  const shape = Object.fromEntries(Object.entries(schema.properties).map(([key, value]) =>
    [key, required.has(key) ? jsonTypes[value.type] : jsonTypes[value.type].optional()],
  ));
  return z.object(shape);
}

const argumentsValidator = validatorFor({
  properties: {
    target: { type: "number" },
    monthly: { type: "number" },
  },
  required: ["target", "monthly"],
});
const validated = argumentsValidator.parse({ target: 2000, monthly: 150 });

A SUPPORTED JSON SCHEMA SUBSET → A RUNTIME PYDANTIC OR ZOD CHECKER → VALID CALL, OR A STRUCTURED ERROR BEFORE FINANCIAL LOGIC RUNS

A converter sits on a trust boundary (the point where data moves from a less trusted component into a more trusted one). “It produced a validator” is not proof that the validator means the same thing as the server's schema; acceptance and rejection must be tested against the real manifest.
A real finding worth knowing: the sketches support only flat strings and numbers, plus Python integers. They omit booleans, arrays, objects, null, enumerations, bounds, patterns, multiple allowed types, nested objects, shared-definition references ($ref) and “one of these shapes” unions (anyOf). They also differ from JSON Schema over numeric-string coercion, unknown fields and optional versus required-but-nullable fields (fields that are required to exist but allowed to contain null). A client checker can therefore accept input the server rejects, or reject input the server accepts. Production code should use a version-pinned converter with parity tests, or validate directly against JSON Schema.
In the capstone: Eunomia registers no tools at runtime in its first release, so this lesson applies to the hosts that consume its optional MCP server: they turn the advertised lookupGuidance and queryCatalogue schemas into local tool definitions, while the server still validates every call against the same Zod schemas. A host may rely on its own conversion only with a complete, version-pinned validator and acceptance/rejection parity tests for every manifest entry, and tools registered at runtime as in Lesson 33 would need the same. Skill Reporter follows the same rule. The small converters above demonstrate the idea, not that guarantee.
Part II Through-Line

From One Shared Implementation to Safe Dynamic Tooling

These five lessons form one chain rather than five isolated techniques, and the chain applies to both Eunomia (fintech) and Skill Reporter. Lesson 6 creates shared MCP server foundations. Lesson 23 removes hardcoded tool lists. Lesson 32 adds session-aware live resource updates. Lesson 33 adds sandboxed runtime registration. Lesson 48 turns advertised schemas into client-side validation gates before calls. The result is one repeatable tool-platform pattern that can evolve without giving up explicit boundaries.
