Part IV

Many Agents, One Goal (Multi-Agent Systems)

Parts I–III built one agent that can think, use tools and remember. This part begins where one agent stops being enough: when a decision needs a second opinion, a majority vote, faster independent work, a shared view of events, or protection against two agents overwriting the same data. Each lesson starts with the failure caused by working alone and adds the smallest multi-agent pattern that fixes it. Eunomia, a fintech savings-assistant AI agent, adopts those patterns one at a time, beginning with a worker and a separate quality auditor.

Dual-domain map for this part: every multi-agent coordination pattern shown for Eunomia (fintech) is meant to transfer to Skill Reporter.

  • Eunomia domain: worker/auditor hand-off, consensus voting on regulated-advice classification, concurrent balance/rate/goal lookups, pub/sub coordination, and arbitrated writes to a shared savings goal.
  • Skill Reporter domain: worker/auditor hand-off on generated skill reports, consensus voting on skill-demand classification, concurrent skill-catalogue/report-memory lookups, pub/sub coordination between report and notification agents, and arbitrated writes to a shared skill-definition index.

Interlink chain: Lesson 9 establishes worker→auditor review, Lesson 15 strengthens decisions with thresholded consensus, Lesson 18 reduces latency with concurrent specialists, Lesson 36 decouples coordination with events, and Lesson 45 protects shared writes from races.

Lesson 9

Multi-Agent Hand-Off & Verification

The problem: if Eunomia evaluates its own draft, the same assumptions that produced the answer can approve it, allowing risky or unsupported guidance through with high confidence. Skill Reporter has the same self-review bias when one model both writes and judges report quality.

The smallest useful separation is a worker agent (the agent whose job is to produce the first draft) followed by an auditor agent (a separate agent with different instructions whose only job is to approve or reject that draft). The worker is encouraged to solve the customer's problem; the auditor is encouraged to look for reasons the proposed answer should not be sent. Those are deliberately different jobs.

The connection between them is a hand-off (the moment one agent passes its output to another as structured data rather than loose chat text). In this pattern, the auditor receives the worker's generated title, stack and code, then returns a verdict schema (a fixed decision form such as approved: true/false and reasons: [...]). A fixed form matters because trusted application code can check a known structure directly.

QUESTION → WORKER DRAFT → INDEPENDENT AUDITOR VERDICT → APPROVE, RETRY WITH REASONS, OR USE A SAFE FALLBACK

The workflow uses one worker call followed by one auditor decision, with bounded retry and a safe holding reply if approval never arrives. Malformed, missing or ambiguous approval must never count as permission.

async def deliver(question: str, worker: Worker, auditor: Auditor) -> str:
    reasons: list[str] = []
    for attempt in range(3):
        draft: str = await worker.draft(question, reasons)
        try:
            verdict: Verdict = await auditor.check_and_validate(draft=draft)
        except VerdictValidationError:
            reasons = ["Invalid verdict"]
            continue
        if verdict.approved:
            return draft
        reasons = verdict.reasons
    return SAFE_HOLDING_REPLY
type Verdict = {
  approved: boolean
  reasons: string[]
}

async function deliver(question: string, worker: Worker, auditor: Auditor): Promise<string> {
  let reasons: string[] = []
  for (let attempt = 0; attempt < 3; attempt += 1) {
    const draft = await worker.draft(question, reasons)
    try {
      const verdict: Verdict = await auditor.checkAndValidate({ draft })
      if (verdict.approved) return draft
      reasons = verdict.reasons
    } catch (error) {
      if (!(error instanceof VerdictValidationError)) throw error
      reasons = ["Invalid verdict"]
    }
  }
  return SAFE_HOLDING_REPLY
}

Separation only helps when it is real. Giving the auditor the worker's memory, prompt and incentives creates two names for nearly the same opinion, not an independent check.

Use the same review contract in both Python and TypeScript: worker draft, independent auditor decision, bounded retry, then safe holding reply if approval never arrives.

A real finding worth knowing: the separate auditor rejected five of ten generated examples in the Python run and six of ten in the TypeScript run. Those results show that a second pass can catch problems, but they do not establish how a retry loop or malformed verdict would behave. Application-side schema validation should therefore reject unreadable verdicts rather than letting a model certify its own output as valid.
In the capstone: Eunomia applies the worker–auditor split without a second agent: on the composed step the model drafts a plain explanation of holdings, products or guidance (never advice), and the code verifier acts as the auditor, checking every figure and claim against frozen evidence before a customer can see it; calibrated rubric judges in the quality suite audit tone offline. This hand-off is the base pattern on which every later lesson in this part builds. Skill Reporter applies the same hand-off before any generated skill report reaches a reporter.
Lesson 15

Multi-Agent Majority Voting

The problem: Eunomia can produce different outputs for the same prompt across runs, so one-shot decisions can accept unlucky variance. Skill Reporter faces the same instability in report scoring and recommendations unless agreement is measured across independent runs.

A swarm (a group of agents, often copies of the same agent, that receive the same task separately) turns one uncertain response into several responses. These responses can still share the same blind spots because they come from the same model and prompt. A consensus vote (choosing the answer that most agents gave instead of trusting any one agent) then selects the strongest shared result. This is useful for bounded decisions such as intent labels, risk categories or yes/no classifications; it is not a guarantee that the majority is correct.

Acceptance needs an agreement threshold (the minimum number of matching votes required before the system trusts a result, such as at least three of five votes). If agents can time out, a separate minimum-response rule should say how many must participate. Workers should return fixed labels whenever possible; treating free-form answers as equivalent can accidentally merge materially different amounts, currencies or risk categories. In Eunomia, labels might be regulated_advice, factual_account_query, and general_info. In Skill Reporter, labels might be high_demand_skill, emerging_skill, and low_signal. A tie must always produce “no winner” rather than depend on which item the program encounters first.

ONE TASK FANS OUT TO FIVE SEPARATE AGENTS → FIXED LABELS ARE VALIDATED → VOTES ARE TALLIED → THE AGREEMENT THRESHOLD ACCEPTS OR ESCALATES

The five agents must not copy one another's intermediate work, because then five votes merely repeat one initial mistake. Each submits a fixed final label without seeing the others' outputs. The tally accepts a unique winner only when that winner meets the configured agreement threshold; a tie or a winner with too few matching votes becomes an escalation or safe reply instead of a guessed result.

from collections import Counter
from typing import TypeVar


Label = TypeVar("Label", bound=str)


def consensus(answers: list[Label], minimum_matching_votes: int = 3) -> Label | None:
    counts = Counter(answers)
    highest = max(counts.values(), default=0)
    winners = [
        answer for answer, votes in counts.items() if votes == highest
    ]
    if highest < minimum_matching_votes or len(winners) != 1:
        return None
    return winners[0]

function consensus<T extends string>(
  answers: T[],
  minimumMatchingVotes = 3,
): T | null {
  const counts = new Map<T, number>()
  for (const answer of answers) {
    counts.set(answer, (counts.get(answer) ?? 0) + 1)
  }

  const highest = Math.max(0, ...counts.values())
  const winners = [...counts.entries()]
    .filter(([, votes]) => votes === highest)
    .map(([answer]) => answer)
  if (highest < minimumMatchingVotes || winners.length !== 1) return null
  return winners[0]
}

A majority is evidence of agreement, not proof of truth. If every agent shares the same bad source or misleading prompt, the whole swarm can agree on the same wrong answer.

This lesson uses deterministic fixed-label tallying in both Python and TypeScript: multiple agents vote independently, then application code applies one explicit threshold rule.

A real finding worth knowing: the same model and question produced confident but wrong FastMCP votes in the Python run, while the TypeScript run voted for the correct LangGraph answer. Multiple agents can repeat one systematic error, so agreement is not proof of truth. A deterministic tally can make the counting rule predictable, but it cannot repair bad evidence or correlated model mistakes.
In the capstone: Eunomia's first release does not run several voting agents on each message. The agreement-threshold idea appears as the routing policy's confidence threshold: a question-type classification below the threshold, including a possible request for regulated advice, goes to a person rather than being guessed, and the advice-line scenarios check that rule on every relevant change. Independent voting stays an option if a single classifier proves unstable. Skill Reporter follows the same threshold-then-person rule for skill-demand labels before drafting outbound reporting guidance.
Lesson 18

Concurrent Sub-Agent Workflows

The problem: Eunomia can serialize work that could run in parallel, increasing response time even when subtasks are independent. Skill Reporter has the same latency penalty when independent report stages are forced through one worker path.

A sub-agent (a smaller agent assigned one well-defined piece of a larger task) lets the system divide the job by responsibility. The planner uses fan-out / fan-in (sending independent pieces to several sub-agents at once, then gathering their results back in one place). Because the checks do not depend on each other, they can use concurrency (allowing several pieces of work to be in progress at the same time rather than waiting for each to finish).

When all available results return, an aggregator (the step that combines separate sub-agent results into one final answer) builds a coherent draft. In the sequential version, total waiting time is roughly the sum of every check. In the concurrent version, network waits overlap, so total time can be closer to the slowest single check plus the cost of starting and combining the work. This does not by itself prove that CPU work ran simultaneously.

SEQUENTIAL WORK ADDS EVERY WAIT; CONCURRENT WORK FANS OUT AND OVERLAPS NETWORK WAITS, THEN FANS IN AT AN AGGREGATOR THAT PRESERVES PARTIAL RESULTS

Concurrent execution changes failure handling. A single timeout must not erase two useful successes. Each sub-agent therefore returns either a value or a clearly marked error, and the aggregator is told exactly which evidence is missing. It may produce a cautious partial draft, request the missing lookup again or stop, but it may not describe incomplete evidence as complete.

import asyncio
from collections.abc import Awaitable


async def run_branch(name: str, work: Awaitable[str]) -> dict[str, str]:
    try:
        return {"name": name, "value": await work}
    except Exception as error:
        return {"name": name, "error": str(error)}


async def build_draft() -> str:
    results = await asyncio.gather(
        run_branch("balance", check_balance()),
        run_branch("rates", find_savings_rates()),
        run_branch("goals", check_goals()),
    )
    return aggregate(results, label_missing_as_partial=True)
type Result = { name: string; value?: string; error?: string }
async function runBranch(
  name: string,
  work: () => Promise<string>,
): Promise<Result> {
  try {
    return { name, value: await work() }
  } catch (error) {
    return { name, error: String(error) }
  }
}

async function buildDraft(): Promise<string> {
  const results = await Promise.all([
    runBranch("balance", checkBalance),
    runBranch("rates", findSavingsRates),
    runBranch("goals", checkGoals),
  ])
  return aggregate(results, { labelMissingAsPartial: true })
}

Concurrency does not mean “ignore failures.” It means failures are isolated to the branch where they occurred, made visible, and handled when the results come back together.

Use the same concurrent fan-out/fan-in shape in both Python and TypeScript. Expect moderate latency improvement from overlapping waits, not linear speedup.

A real finding worth knowing: the Python run was about 20% faster with concurrent requests, while the repeated TypeScript comparison improved by about 11%. Both default asyncio.gather(...) and Promise.all(...) surface a branch failure instead of returning a complete array of successes. If an aggregator must retain partial results, each branch must catch and represent its own failure before those operations combine the results, as the wrappers above do.
In the capstone: when a question type needs more than one source, Eunomia's evidence planner can call readSnapshot, queryCatalogue and lookupGuidance at the same time, then freeze the results into one evidence bundle. Any answer built from that bundle still passes the verifier before the customer sees it. Skill Reporter uses the same fan-out/fan-in pattern to gather skill catalogue data, report memory, and policy notes in parallel before synthesis.
Lesson 36

Pub/Sub Agent Coordination

The problem: as Eunomia and Skill Reporter add specialized agents, direct peer-to-peer messaging creates brittle coupling and missed updates. Adding one agent can require rewiring many others, raising change risk and making responsibilities hard to reason about.

A message bus (a shared noticeboard to which agents post messages and from which agents read them instead of contacting one another directly) removes that web of direct one-to-one connections. The bus supports publish / subscribe, or pub/sub (a pattern in which agents publish messages to named topics and any agent subscribed to a topic receives them without the sender knowing who is listening). Lesson 9's worker and auditor are two of the agents whose messages now flow over this bus rather than being passed directly between them.

Each message is an event (a short, structured record that something happened, such as goal_updated). A real bus may deliver the same event more than once, so subscribers must make repeated delivery harmless. The in-memory set below suppresses a duplicate only when deliveries are sequential in one running process. It is not a general idempotency guarantee (a promise that repeating an operation has no additional effect): concurrent copies can both pass the check, a crash can occur after the audit but before the identifier is saved, and a restart clears the set. Stronger guarantees need durable atomic claim-and-complete state and a downstream operation designed for safe retries.

AGENTS PUBLISH STRUCTURED EVENTS TO TOPICS → THE MESSAGE BUS DECOUPLES SENDERS FROM RECEIVERS → SUBSCRIBERS PROCESS EVENTS AND HANDLE REPEATED DELIVERY EXPLICITLY

Decoupling lets a notification agent or audit log join later without changing the worker. It does not, however, create a saved history or a guaranteed delivery order. If an agent must recover older events, the system has to store them durably and send them again during recovery. The sample bus demonstrates routing only; it does not establish behavior for late subscribers, duplicates, delivery order or slow subscribers.

from typing import TypedDict


class DraftReady(TypedDict):
    event_id: str
    draft_id: str


processed_event_ids: set[str] = set()


async def on_draft_ready(event: DraftReady) -> None:
    if event["event_id"] in processed_event_ids:
        return
    await audit(event["draft_id"])
    processed_event_ids.add(event["event_id"])

    await bus.publish("draft_ready", event)

A bus shares news, not necessarily history. If an agent needs past events to rebuild its state, durable storage and explicit redelivery must be designed.

Use the same pub/sub contract in both Python and TypeScript, and ensure nested publications are explicitly awaited so downstream subscribers see complete event chains.

A real finding worth knowing: the Python demonstration created tasks without awaiting them and therefore needed an explicit wait for a nested publication to finish. The TypeScript promise chain naturally awaited its nested publication. That difference is about completion tracking in these implementations; it is not evidence for duplicate handling, late-subscriber behavior, delivery order or slow-subscriber behavior.
In the capstone: Eunomia's first release is one service with no separate agents, so it needs no message bus between them. The same decoupling appears at its edges: a turn records typed events through the TraceSink port and sends review items to the ReviewInbox port without knowing who consumes them. A bus carrying events such as draft_ready is deferred until separate agents or services need to coordinate. Skill Reporter uses the same event contracts so report-generation, review, and notification agents evolve independently.
Lesson 45

Central Write Arbitration for Concurrent Write Hazards

The problem: when Eunomia or Skill Reporter agents update shared records concurrently, one write can overwrite another without warning. This silent conflict can corrupt customer or reporting state unless update ordering and conflict checks are explicit.

This is a concurrent write hazard (the risk that overlapping writes to the same resource leave it wrong or internally inconsistent). It often appears as a race condition (a bug whose result depends on which operation happens to finish first, making it intermittent and difficult to reproduce). Both agents can read version 3, calculate different updates, and then save in succession; the second save overwrites the first even though both calls reported success.

An arbiter (one coordination component that receives write requests for a shared resource) gives participating writers one controlled entrance. It can keep a separate queue for each record so requests for one record are handled in order. The correctness boundary, however, is the shared store's atomic version check, also called optimistic locking (one indivisible store operation that writes only if the record still has the expected version). A local queue is only an efficiency measure: another arbiter replica or a writer that bypasses it can still race. A request rejected by the store must re-read the latest record, reconsider its change and retry with the new version. The arbiter does not replace the worker/auditor hand-off from Lesson 9 or the bus-based coordination from Lesson 36; it adds a third guarantee — that concurrent writes to one shared record cannot silently overwrite each other.

OVERLAPPING WRITES CAN LOSE DATA; THE SHARED STORE MUST CHECK THE EXPECTED VERSION AND WRITE ATOMICALLY, WHILE STALE REQUESTS RE-READ BEFORE RETRYING

The arbiter need not make the business decision itself. Its narrower job is to submit the expected version and complete replacement value to an atomic store operation. A local queue can reduce conflicts for requests that reach one process, and requests for different records can still proceed concurrently, but the store must reject stale versions even when writes arrive through another process.

from dataclasses import dataclass
from typing import Any


@dataclass(frozen=True)
class WriteRequest:
    record_id: str
    expected_version: int
    change: dict[str, Any]


async def apply(request: WriteRequest) -> Record | Stale:
    current = await store.read(request.record_id)
    updated = {
        **current.data,
        **request.change,
        "version": current.version + 1,
    }
    saved = await store.write_if_version(
        request.record_id,
        expected_version=request.expected_version,
        value=updated,
    )
    return saved if saved is not None else STALE
interface WriteRequest {
  recordId: string
  expectedVersion: number
  change: Record<string, unknown>
}

async function apply(request: WriteRequest): Promise<StoredRecord | Stale> {
  const current = await store.read(request.recordId)
  const updated = {
    ...current.data,
    ...request.change,
    version: current.version + 1,
  }
  return (
    (await store.writeIfVersion(
      request.recordId,
      request.expectedVersion,
      updated,
    )) ?? STALE
  )
}

One normal execution thread is not the same as freedom from races. Whenever an operation pauses to await input or output, another operation can read or write the same state.

The versioned-write design above is the operational model for this lesson: the store enforces an atomic expected-version check, stale writes are rejected, and callers must re-read before retrying.

A real finding worth knowing: a model can propose an execution plan, but the application still needs deterministic enforcement. The rule check must verify write ordering explicitly (for example, WRITE before INVALIDATE) and must reject stale versions at the store boundary.
In the capstone: Eunomia's first release is read-only, so no agent writes to a customer's savings goal and there is no shared write to arbitrate. When write actions arrive in a later release, this is the pattern they need: an arbiter coordinates concurrent requests, the shared store rejects stale versions atomically, and a check confirms the saved state matches what the customer was told. Skill Reporter applies the same arbiter-plus-atomic-check pattern to updates on shared skill-definition state.
