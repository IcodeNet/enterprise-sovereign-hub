Part IX

Shipping It (Human Oversight & Deployment)

A useful agent is not shipped merely because it can answer a question. It must stop before sensitive actions, survive a restart while it waits, run the same way outside a developer's laptop, repair safe-to-fix mistakes without weakening permission checks, and keep a live reply coherent when tools or people take time. These five lessons turn Eunomia from working code into a service that can be operated, interrupted, supervised, and verified.

Dual-domain map for this part: the same deployment-and-approval controls apply to Eunomia and Skill Reporter.

  • Eunomia domain: human approval before sensitive actions, containerized runtime parity, durable approval state across restarts, safe tool-call correction, and typed streaming with approval pauses.
  • Skill Reporter domain: the same human approval, container parity, durable pending-state recovery, safe correction, and typed streaming controls for report workflows.

Interlink chain: Lesson 12 defines approval checkpoints, Lessons 23 and 24 make those checkpoints survive container lifecycle and process restart, and Lessons 47 and 53 preserve safe correction and typed streaming around those gates.

Lesson 12

Human-in-the-Loop & Durable State

The problem: Eunomia can reach a high-impact customer action when no authorized reviewer is available. Pausing is required, but an in-memory pause disappears on crash or restart, risking lost work, wrong resume points, or duplicate execution. Skill Reporter has the same approval-state risk for privileged report publication actions.

Human-in-the-loop (HITL) (requiring a person to review or decide part of an automated task) is safe only when it is paired with durable state (saved progress that survives crashes and restarts). A local variable saying “waiting” is not durable. The service needs a checkpoint (a saved record of exactly where a task paused) written to storage before anybody is asked to approve the action.

PREPARE THE ACTION → SAVE BEFORE NOTIFYING → PAUSE → RELOAD AFTER ANY RESTART → CLAIM EXECUTION OR RECORD REJECTION

The saved record must contain enough truth to resume without replaying old work: the task identifier, current step, proposed action, already-checked arguments, reason for review, and an approval status—pending, approved, rejected, or expired. It also needs an idempotency key (a unique value used to recognize repeated attempts at the same sensitive action). The key alone does not guarantee one execution: the action runner must claim the record with an indivisible approved → executing change, save the result durably, and pass the key to the downstream service when that service supports duplicate protection.

async def pause(task_id: str, action_id: str, checked_action: dict):
    checkpoint = {
        "task_id": task_id,
        "step": "awaiting_approval",
        "action": checked_action,
        "status": "pending",
        "idempotency_key": action_id,
    }
    await store.save(checkpoint)
    await reviewer.notify(checkpoint)
    return {"status": "waiting_for_approval"}
async function pause(
  taskId: string,
  actionId: string,
  checkedAction: Action,
): Promise<WaitResult> {

    taskId, actionId, action: checkedAction,
    step: "awaiting_approval", status: "pending",

  await store.save(checkpoint);
  await reviewer.notify(checkpoint);
  return { status: "waiting_for_approval" };

On startup, both the Python and TypeScript services reload pending checkpoints. An approval endpoint (a web route that receives a reviewer's decision) accepts a decision only for a known pending task, resumes at the saved step rather than beginning again, and durably records both the human decision and the final action result. A single guarded path must lead to the sensitive operation; a second “convenient” route around the checkpoint would undo the protection.

The reader should prove the design with a restart test rather than code review alone: start two tasks, stop each process while it waits, restart, approve one, reject the other, and send the approval twice. The approved action must complete once, rejection must execute nothing, and duplicate approval must return the saved outcome rather than repeat the action.
A real finding worth knowing: in the recorded lesson's simulated in-memory store, a second tool call replaced an existing APPROVED record with a new PENDING record. The TypeScript port found the same reset bug and also exhausted a one-step tool budget, producing an empty text response. Because the lesson did not use a durable store, it did not prove survival across a process restart.
In the capstone: Eunomia's read-only first release has no sensitive actions to approve, but it applies durable state to pending human work: review items and handoff tickets live in the review inbox's durable store, so a restart never loses a turn that is waiting for a person. Durable approval of sensitive savings actions, with atomic claiming, durable result storage and duplicate protection so a repeated decision cannot repeat the action, is deferred to the write actions of a later release. Skill Reporter enforces the same approval-and-idempotency discipline for privileged report actions.
Lesson 24

Docker & Compose Orchestration

The problem: Eunomia code that works on one laptop can fail in shared environments because runtime versions, network wiring, and service dependencies differ. The stack needs one repeatable deployment path for build, startup, health, and shutdown. Skill Reporter needs the same parity to avoid environment-specific behavior drift.

Orchestration (coordinating several services as one system) makes that repeatable operation possible. Docker (a system for packaging an application with the software it needs to run) turns each application into an image (a packaged, unchanging template) that can be started as a container (an isolated running instance of a packaged application). Docker Compose (a configuration tool that starts and connects several containers together) describes the whole system: the Python agent, TypeScript web service, durable state store, a private network (a connection available only to services in the stack), a persistent volume (stored data that remains when a container is replaced), and readiness rules.

ONE COMPOSE STACK CONNECTS BOTH APPLICATIONS, CHECKS REAL READINESS, AND KEEPS ONLY DURABLE DATA ON A PERSISTENT VOLUME

Each language implementation gets its own deliberate build instructions. The final packaged images install only required dependencies, copy only required files, use a non-administrator account where practical, and never bake secrets into the reusable filesystem sections that make up an image. Compose declares settings explicitly rather than inheriting accidental values from a developer's shell, and gives connected services stable names on the stack's private network. Each image below provides the application-owned /app/healthcheck command used by Compose.

A health check (an automated test that reports whether a running service is ready to accept work) matters because “the container process exists” is not the same as “the application can serve requests.” Here the agent reports ready only after it can connect to required state storage, and Compose waits for each required dependency; an alternative design may report degraded readiness if it documents which work remains safe. Dependants must wait for readiness or retry connections safely. Clean shutdown must stop new work, finish or checkpoint in-flight work (tasks that have started but not finished), and only then exit.

Verification starts clean: build without cached assumptions, start everything through one Compose command, call both implementations over real network connections, restart an application container, and recreate the stack. Conversation and approval data must remain; machine-specific dependencies must not.
A real finding worth knowing: the recorded lesson first misdiagnosed a connection failure as a TLS certificate problem; the traffic was actually being intercepted by a different endpoint-security proxy. A later run also exposed a stale exact certificate pin. The lesson did not record a Compose localhost bug.
In the capstone: Eunomia packages its TypeScript service, web client and stores in containers, and the same orchestration starts the service, the stub upstream and the Python probes in the right order in CI, waiting for /readyz before the first probe runs. Python appears only in the probes, never on the serving path, and review data lives in durable storage, so replacing or restarting an application container loses no pending review. Skill Reporter uses the same packaging parity across environments.
Lesson 39

Human-in-the-Loop Approval Checkpoints

The problem: after Eunomia asks for approval, that request must wait without blocking other customer sessions. Approve, reject, and timeout paths all need explicit handling; silence or delayed responses must never be treated as consent. Skill Reporter requires the same explicit checkpoint outcomes for report workflows.

A Future/Promise (a live-process placeholder for a result that will be supplied later; Python commonly calls it a Future, while TypeScript uses a Promise) lets one task wait while the service continues handling other requests. It is not durable and disappears if the process restarts. At an approval checkpoint (a point where execution cannot continue until a person decides), the durable record from Lesson 12 remains authoritative; a running service may associate a Future or Promise with that record only as a temporary waiter. After a restart, the service must create a new waiter or resume directly from the durable record rather than pretending the old placeholder survived.

ONE PENDING DECISION RESOLVES EXACTLY ONCE: APPROVE AND REVALIDATE, REJECT AND CANCEL, OR EXPIRE WITHOUT EXECUTING

The approval path first verifies that the identifier exists and is still pending. It resolves the placeholder with an explicit approved value, rechecks the action arguments, executes once, and records the outcome. The rejection path resolves that same placeholder with an explicit rejected value, returns a cancellation result, records a normal human decision rather than a system error, and calls no sensitive tool.

These are registry fragments, not the complete endpoint. They validate the incoming decision and show one guarded settlement path; production code must also route timeout through that path, revalidate arguments after approval, claim execution durably, run the action, and record its outcome.

async def decide(approval_id: str, value: object) -> str:
    if value not in ("approved", "rejected"):
        raise ValueError("decision must be approved or rejected")
    decision = str(value)
    async with pending_lock:
        request = pending.get(approval_id)
        if request is None or request.status != "pending":
            return "late, unknown, or already decided"
        request.status = decision
        pending.pop(approval_id)
    request.future.set_result(decision)
    return decision
type Decision = "approved" | "rejected";

function parseDecision(value: unknown): Decision {
  if (value !== "approved" && value !== "rejected") {
    throw new Error("decision must be approved or rejected");
  }
  return value;
}

async function decide(
  approvalId: string,
  value: unknown,
): Promise<Decision> {
  const decision = parseDecision(value);
  const request = pending.get(approvalId);
  if (!request || request.status !== "pending") {
    throw new Error("late, unknown, or already decided");
  }
  request.status = decision;
  pending.delete(approvalId);
  request.resolve(decision);
  return decision;
}

A timeout (a limit on how long the system will wait) expires without approval. Duplicate and late decisions are rejected clearly, completed entries are removed, and cleanup happens after every outcome. The difficult edge is a race condition (a bug where the result depends on which of two events happens first): approval and timeout may arrive at nearly the same instant. Both languages therefore need one atomic transition (an indivisible state change that competing events cannot both win) from pending to one—and only one—final state.

Python resolves a Future with an explicit decision value; TypeScript retains the function that settles a Promise and calls it from the approval endpoint. Their cancellation details differ, but readers should test the same outcomes for approval, rejection, timeout, and repeated response.

A real finding worth knowing: the recorded Python and TypeScript runs demonstrated the approve and reject paths. They did not observe a timeout race. Treating reviewer responses and timeout as competing attempts at one guarded settlement is defensive guidance that still needs a dedicated concurrency test.
In the capstone: Eunomia's read-only first release has no per-action approval checkpoints; it keeps only the broad oversight principle (a required reviewer on production deploys and a person at the bottom of the answer sequence). When write actions arrive, Eunomia will use a durable approval record for every sensitive savings action and may attach a Future or Promise while a process is live; each affected task will follow an explicit approve, reject, or timeout path, and after restart, work resumes from the durable record rather than the vanished placeholder. Skill Reporter applies the same durable-record recovery for pending human decisions.
Lesson 47

Self-Healing Dynamic Tool Correction

The problem: Eunomia may choose the correct tool but send one malformed argument, like a bad date or account reference. Hard failure wastes recoverable work, while silent rewriting can trigger the wrong action. Skill Reporter has the same correction-vs-safety trade-off for malformed report tool inputs.

A tool call (a structured request from the model to run a named function) must pass schema validation (checking that supplied values match required names, types, and formats) before execution. Format mistakes must be separated from permission denials, network failures, and internal failures because only the first category is a sensible target for automatic correction.

VALIDATE FIRST → EXECUTE ONLY A VALID AND PERMITTED CALL; OTHERWISE RETURN A PRECISE ERROR, CORRECT WITHIN A LIMIT, AND VALIDATE AGAIN

When validation fails, the tool returns a structured error (a failure response with specific fields that software can interpret). It names the invalid field and states the expected format. A safe value such as the displayed date may be returned so the model can see what needs changing; sensitive account, personal, or secret fields must instead be redacted or described only by their non-secret shape. “Tool failed” is not enough information to repair anything.

from datetime import date


def validate_maturity_date(value: str) -> dict[str, object] | None:
    try:
        date.fromisoformat(value)
        return None
    except ValueError:
        return {
            "kind": "validation_error",
            "field": "maturity_date",
            "expected": "a real calendar date in YYYY-MM-DD form",
            "received": value,
            "retryable": True,
        }
type ValidationError = {
  kind: "validation_error";
  field: string;
  expected: string;
  received: string;
  retryable: true;
};

function validateMaturityDate(value: string): ValidationError | null {
  const match = /^(\d{4})-(\d{2})-(\d{2})$/.exec(value);
  if (match) {
    const year = Number(match[1]);
    const month = Number(match[2]);
    const day = Number(match[3]);
    const leap = year % 4 === 0 && (year % 100 !== 0 || year % 400 === 0);
    const days = [31, leap ? 29 : 28, 31, 30, 31, 30, 31, 31, 30, 31, 30, 31];
    if (year > 0 && month > 0 && month <= 12 && day > 0 && day <= days[month - 1]) {
      return null;
    }
  }
  return { kind: "validation_error", field: "maturity_date",
    expected: "a real calendar date in YYYY-MM-DD form",
    received: value, retryable: true };
}

The error is added to the conversation with an instruction to issue a corrected tool call, not a prose apology. The replacement arguments begin validation again from the start. A bounded retry (trying again only up to a fixed limit) permits a small number of attempts for correctable format errors, then stops. Denied actions, missing authorization, and permanent service failures are not retried, and valid formatting never counts as permission: corrected sensitive calls still pass the same human checkpoint.

Test all branches: one malformed but repairable call should become valid on the next attempt; an already valid call should never enter the loop; a permanent failure should stop immediately. Python and TypeScript wording may differ, but their final classification and action must agree.
A real finding worth knowing: after the malformed account identifier was corrected, the Python run repeatedly reported a false zero balance while the TypeScript port reported the correct balance. That divergence shows why a repaired argument and the tool's resulting data must be verified separately; successful correction does not prove a correct answer.
In the capstone: Eunomia can repair the one capability request the model may make on the composed step without collapsing the conversation: the validation error goes back once, the corrected request must pass the same Zod schema and token-derived scope before it runs, and a second failure steps the answer down a step. Write actions, deferred to a later release, would also need the human-approval checkpoint before anything executes. Skill Reporter mirrors this safe-correction path for malformed report-tool calls.
Lesson 53

Resilient Streaming Agent Responses

The problem: Eunomia should stream responses as they are produced, but mid-stream tool calls may block for approvals, retries, or failures. The connection must stay valid, typed, and truthful about state changes instead of fabricating completion. Skill Reporter has the same requirement when long report steps stream progress and checkpoint events.

A streaming response (sending a reply in small pieces as it is produced) uses a ReadableStream (a web interface that lets a server provide those pieces over time). Its stream controller (the object used to add events and close the stream) manages delivery. Ordinary text can appear immediately, but internal tool work is a different event type (a label that tells the receiver what kind of stream item arrived): raw, unchecked arguments must never be presented as completed work.

STREAM TEXT EARLY → ROUTE TOOL EVENTS THROUGH VALIDATION AND APPROVAL → RETURN ONLY VERIFIED RESULTS → EMIT SAFE FAILURES → CLOSE ONCE

The event sequence is explicit: open the connection, send ordered text chunks, emit a safe status event while a tool or approval is pending, emit the verified result or a clear failure, and close exactly once. Every tool passes a typed tool boundary (a checked interface that permits only the tool fields and value types declared by the application). Correctable format errors enter the bounded correction loop; sensitive valid calls enter approval. Streaming never weakens either check.

The following examples are event-shaping sketches. The Python generator is conceptual pseudocode; the recorded Lesson 53 implementation is TypeScript-only because this curriculum has no Python equivalent for the Vercel AI SDK primitive. Both sketches show ordered events, checked tools, a safe error, and one normal close, but they do not implement disconnect handling or backpressure.

async def stream_events(agent):
    try:
        async for event in agent.run():
            if event.kind == "tool_call":
                yield encode({"type": "tool-pending"})
                result = await run_checked_tool(event)
                yield encode({"type": "tool-result", "data": result})
            else:
                yield encode({"type": "text-delta", "data": event.text})
    except Exception:
        yield encode({"type": "safe-error"})
    finally:
        yield encode({"type": "stream-finish"})
const stream = new ReadableStream<Uint8Array>({
  async start(controller) {
    try {
      for await (const event of agent.run()) {
        if (event.kind === "tool_call") {
          controller.enqueue(encode({ type: "tool-pending" }));
          const result = await runCheckedTool(event);
          controller.enqueue(encode({ type: "tool-result", data: result }));
        } else {
          controller.enqueue(encode({ type: "text-delta", data: event.text }));
        }
      }
    } catch {
      controller.enqueue(encode({ type: "safe-error" }));
    } finally {
      controller.close();
    }
  },
});

A production implementation still needs backpressure (slowing production when the receiver cannot consume data quickly enough), disconnect detection, and cancellation of unnecessary model generation (the model's ongoing production of response text). It must release stream resources and separately decide whether already-started durable work should continue, because closing a browser tab should not erase a recorded approval decision. Those behaviours require cancellation signals and pressure-aware stream hooks that are not present in the sketches above.

Readers should verify the TypeScript implementation over a real web connection: the first text should arrive before completion; tool arguments should be checked before execution; an approval delay should not corrupt event order; and failures, slow receivers, and disconnects should clean up. The conceptual Python sketch is not evidence of cross-language streaming equivalence.
A real finding worth knowing: a terse numeric query legitimately produced a tool call with zero narrated text chunks. The revised TypeScript test separated narration from tool-output correctness; a later run measured 57 text chunks while checking the tool result independently. The recorded lesson did not find that the stream closed at the first tool pause.
In the capstone: Eunomia uses this event shape for its typed turn events: only verified text is streamed, and every turn ends with exactly one answer.final, turn.declined, handoff.offered or turn.failed. Pausing a stream for human approval of a sensitive action is deferred with write actions. Production readiness additionally requires tested backpressure, cancellation, disconnect cleanup, and a policy for durable work. Skill Reporter follows the same typed-streaming contract for live report responses.

What 64 Real, Verified Lessons Taught Us

Real execution beats polished theory

The strongest lesson across all 64 lessons is simple: run the code and report what actually happened. A polished explanation cannot replace a real Python execution, a real TypeScript execution, and an honest account of the output. Expected output must never be quietly promoted into claimed output.

The useful findings were not limited to successful demonstrations. Outdated interfaces, environmental failures, timing problems, unsupported features, and different behaviour between the two languages were evidence too. Preserve the real error message and explain its cause. Report the bug that was found and fixed instead of rewriting the history as a flawless first attempt. Say plainly when the libraries, controls, or failure behaviour differ. A verified limitation is more valuable than an invented success.

Verify the explanation separately from the data

A model can return the correct records while attaching an incorrect self-reported field. A tenant identifier (a value that says which customer or account owns data) or a confidence score (the model's own estimate of how likely it is to be correct) may conflict with the retrieved result. One response can therefore contain two claims that need separate checks: whether the records, calculation, or tool output are correct, and whether the model's labels, explanation, ownership field, confidence, or summary are accurate.

A successful lookup does not prove that every generated field around it is trustworthy. Security, ownership, and policy decisions must come from independently checked application data, never from a model describing itself as authorized or confident.

Match verification strictness to the lesson

A deterministic algorithm (a fixed calculation that gives the same output for the same input) should match exactly across language ports. If Python produces 0.375, TypeScript should produce 0.375, digit for digit, unless a documented numerical rule explains the difference.

An LLM-based lesson (a lesson whose wording or choice depends on a language model) normally matches in direction rather than exact phrasing. Both implementations should reach the same practical conclusion, call the appropriate kind of tool, respect the same safety boundary, and produce compatible structured data, while their sentences and token order may differ.

The verification rule: with no model involved, demand exact values, ordering, counts, and state transitions. With a model involved, demand the same intent, safety behavior, evidence, and structured outcome. In a mixed system, check deterministic components exactly and model-generated components semantically. Never excuse an exact algorithmic mismatch as “model variability” when no model produced that value.

Knowing which category a lesson belongs to prevents weak testing on one side and unfair testing on the other.

The “should not trigger” case is part of the feature

Every safety or detection mechanism needs a positive test and a negative test. Proving that a dangerous request triggers a guard is only half the job; the system must also prove that a healthy request does not trigger it. An approval checkpoint should pause a sensitive action but not an ordinary read-only request. A correction loop should retry malformed arguments but not a valid call. A detector should flag its intended risky condition and leave a healthy case alone.

The same symmetry applies to recovery. A retry policy should recover from a temporary failure but stop on a permanent one. A streaming error handler should emit a failure event when needed but not corrupt a successful stream. A durable resume path should restore unfinished work but never replay completed work. False positives can make a safety feature unusable; false negatives make it ineffective. Both sides must be executed and verified.

Final reflection

Shipping a dependable agent is not mainly about producing an impressive answer. It is about making every boundary visible and testable: where data came from, where a model made a claim, where deterministic logic must match exactly, where a person must decide, where state must survive, and where failure must stop rather than disappear.

Across 64 lessons, the reliable pattern stayed consistent: build the smallest real version, run it in both languages, test success and non-triggering cases, preserve the actual evidence, and describe differences without smoothing them away. That discipline is what turns Eunomia from a conversational demonstration into a savings assistant that can be deployed, supervised, interrupted, resumed, corrected, and trusted within clearly defined limits.
