Part X · Capstone

Part X — Building Eunomia

The previous nine parts built the pieces one at a time. This capstone puts the lessons together into one design for Eunomia's safe, read-only first release: a savings assistant that can answer questions about a customer's holdings, maturity dates and deposit protection, describe products from an approved catalogue, quote approved guidance, and hand the conversation to a person when it should not answer alone. The design is one TypeScript service plus a web client. Inside the service, plain business rules sit in the middle, the outside world is reached only through named interfaces, and every answer is built from evidence that can be fetched again later. The same release discipline is applied to Skill Reporter as a parallel domain track. Write actions (moving money, opening or closing accounts) are deliberately deferred. The target is an MVP (minimum viable product — the smallest version that is safe and useful in production), not a toy and not a distant wish list.

Dual-domain map for this capstone: Eunomia and Skill Reporter ship through the same control stack.

  • Eunomia track: read-only savings answers with identity taken from the token, three coarse typed capabilities, an answer-mode sequence, a figure-checking verifier, traces, a quality gate, and independent contract probes.
  • Skill Reporter track: read-only reporting answers with the same identity rule, typed capabilities, sequence, verifier, traces, quality gate, and independent probes.

Integration chain: this capstone composes Parts I–IX into one release boundary: typed contracts, a routing policy, deterministic domain rules, evidence-checked answers, observability, and CI gates all enforced before promotion.

Shared learner terms (book ↔ Eunomia UI): the capstone and the Eunomia chat page use the same four terms so readers do not have to translate vocabulary across materials.

  • Turn: one customer message plus one Eunomia reply, created by POST /v1/turns.
  • Evidence: the frozen bundle an answer was built from (snapshot, catalogue rows, guidance passages, each with a stable id), fetched with GET /v1/turns/{id}/evidence.
  • Review: a request for a person to check one turn, sent with POST /v1/turns/{id}/review, raised by a handoff, or raised by the quality sampler.
  • Turn events: the typed server-sent events the page listens to, from turn.accepted to one ending event such as answer.final.

Complete Eunomia architecture graph (one turn, end to end)

The problem: readers can see strong individual controls in isolation, but still miss the full runtime chain from one customer message to one checked answer. Without the whole path in one place, it is hard to see that the order of the steps is what makes the answer trustworthy.

This section is the complete runtime path as one graph. It starts at the browser, takes identity only from the verified token, picks an answer mode from a fixed policy table, gathers evidence through three read-only capabilities, writes or renders an answer, checks every figure against that evidence, and only then streams it. Separate quality and probe paths sit outside the serving path. Every step matters, but the order is what enforces trust: nothing reaches the customer before it has been checked against evidence that was frozen first.

COMPLETE TURN GRAPH: SERVING PATH + QUALITY PLANE + INDEPENDENT PROBES

Runtime breakdown from message to answer:

  1. The web client sends one message to POST /v1/turns, and the HTTP adapter first verifies the bearer token and builds the customer scope from the token alone; a body that tries to carry a customer id is rejected.
  2. Only then is the turn opened, and the client immediately receives a turn.accepted event carrying the turn id and trace id.
  3. An input screen catches known injection patterns and requests that cross the advice line (asking Eunomia to choose a product for the customer).
  4. The routing policy table maps the question type to its starting answer step (template, composed, or handoff) before any evidence is gathered, because the step decides what evidence to gather.
  5. The service's evidence planner, not the model, calls only the capabilities that question type and step need, through the ports.
  6. Each capability validates its input and output with Zod and returns an evidence id.
  7. The evidence bundle is frozen and stored, and evidence.ready tells the client which evidence ids exist.
  8. The chosen step produces a draft: a template fills fixed wording from evidence with no model call; the composed step asks the ModelGateway to write from evidence only. On that step the model may instead request one more capability call through the same typed interface; the service validates and executes it, adds the result to the bundle under a new evidence id, and re-freezes the bundle before the model writes.
  9. The verifier checks every figure, date and claim in the draft against the frozen evidence.
  10. If verification fails, the turn drops one step and tries again; the last step is a person.
  11. Only verified text is streamed as answer.delta events, closed by one answer.final. A screened-out request ends instead with turn.declined or handoff.offered, and a hard error with turn.failed.
  12. The TraceSink records masked spans: step chosen, verifier verdict, evidence ids, timings, never raw balances or message text.
Eunomia does not trust a single model output. It trusts a path: evidence first, wording second, a check between the two, and a person waiting at the bottom of the sequence.

Ports and adapters: plain rules in the middle, the world at the edge

The problem: Eunomia can use strong models and still fail as a production system if identity, data access, money rules, model calls and delivery are tangled together in one handler. A change to one provider or store then risks every control at once. Skill Reporter has the same architectural risk when reporting logic and its data sources are wired directly together.

Eunomia is one TypeScript service plus a web client, and the service is arranged as ports and adapters (a layout where the core business code talks only to interfaces it owns, and separate adapter code plugs real systems into those interfaces). Think of a travel adaptor: the device (the domain) has one plug shape; the adaptor changes for each country (each provider or store). domain/ holds pure rules: deposit protection per banking group, product facts, money as whole numbers of pence, the routing policy table and the verifier's rules. answering/ holds the sequence runner, which uses those rules and the ports to run one turn. ports/ holds seven interfaces the core depends on. adapters/ holds the HTTP server, model providers, stores and telemetry. Outside the service, quality/ owns scenarios and the release gate, probes/ is an independent Python suite, and web/ is the Next.js client.

This is the architectural form of Lesson 1's type-safe boundaries and Lesson 2's dependency injection (the core is handed its collaborators by trusted startup code instead of creating them itself), and Lesson 30's monorepo orchestration keeps service, quality suite, probes and client changing together in one repository. Scoping every port call to the token's customer applies Lesson 54's tenant-isolation principle (keeping one customer's data separate from another's) without implementing its per-tenant vector shards. The routing policy table is Lesson 5's conditional routing made explicit and testable.

Where decision-first routing fits: Lesson 64 adds a decision-first routing layer before any model work. Here that layer is the routing policy table: a typed question type plus a confidence threshold picks the starting step before evidence is gathered. When the classifier is unsure about a mixed, high-risk message, the table sends it to the handoff step instead of forcing a risky answer.

THE DOMAIN SITS IN THE MIDDLE; EVERY REAL SYSTEM PLUGS IN THROUGH A PORT

The ports are small on purpose. Each one is an interface (a TypeScript description of methods, with no code behind it), so a unit test can hand the core a tiny in-memory version, and a provider change touches one adapter file instead of the whole service.

Production rule: keep the first release small in capability but complete in control. Three coarse read-only capabilities with token-derived scope, frozen evidence, a verifier, traces and a release gate are safer than a long list of fine-grained tools that nobody can audit.

The HTTP surface: five routes and one typed event stream

The problem: a chat endpoint looks simple, but regulated savings answers cross several control points: who is asking, which data they may see, whether the request is admissible, what the answer was built from, and how the client learns that a turn ended badly. Skill Reporter crosses the same points for report requests and their sources.

The whole public surface is five routes. POST /v1/turns is authenticated and answers with a stream of typed server-sent events (SSE — one-way messages from server to browser over an ordinary HTTP response): turn.accepted, evidence.ready, answer.delta, answer.final, turn.declined, handoff.offered and turn.failed. GET /v1/turns/{id}/evidence returns exactly what an answer was built from. POST /v1/turns/{id}/review asks a person to check a turn. GET /livez says the process is alive; GET /readyz says its stores and at least one model provider are reachable, so a load balancer stops sending traffic to an instance that cannot answer.

Identity and customer scope come only from the verified token. The request body is parsed with a strict schema, so a body that adds customerId is rejected rather than ignored. The input screen applies Lesson 20's input-attack and refusal controls before any model call; Lesson 13's programmatic output scan reappears inside the verifier after drafting. Token-derived scope applies the least-authority idea from Lesson 52 and the isolation idea from Lesson 54, but this read-only MVP does not implement Lesson 52's signed capability tokens or Lesson 54's per-tenant vector shards.

VERIFY TOKEN → SCREEN + ROUTE → FREEZE EVIDENCE → DRAFT → VERIFY → STREAM

The route itself stays thin. It parses the body, builds the scope, opens the turn through the TurnStore port, and forwards whatever events the core yields. The HTTP adapter wraps whichever Node web framework the team picks; the core never sees it.

import { z } from "zod"

const TurnBody = z.object({
  message: z.string().trim().min(1).max(2_000),
  conversationId: z.string().uuid().optional(),
}).strict()   // unknown fields such as customerId are a 400, not silently dropped

type RouteDeps = AnswerDependencies   // already holds turns: TurnStore, trace: TraceSink and reviewInbox: ReviewInbox

export function registerTurnRoutes(http: HttpAdapter, deps: RouteDeps) {
  http.post("/v1/turns", { auth: "required" }, async (request, events) => {
    const body = TurnBody.parse(request.body)
    const scope = scopeFromToken(request.verifiedToken)   // the only source of identity
    const turn = await deps.turns.open({ scope, conversationId: body.conversationId })

    events.send({ type: "turn.accepted", turnId: turn.id, traceId: turn.traceId })
    try {
      const run = runTurn({ turn, scope, message: body.message, signal: request.signal }, deps)
      for await (const event of run) events.send(event)
    } catch (error) {
      deps.trace.record({ kind: "turn.error", turnId: turn.id, error: maskError(error) })
      events.send({ type: "turn.failed", turnId: turn.id, code: "TURN_FAILED", retryable: isRetryable(error) })
    } finally {
      events.end()
    }
  })

  http.get("/v1/turns/:id/evidence", { auth: "required" }, async (request) => {
    const bundle = await deps.turns.evidenceFor(request.params.id, scopeFromToken(request.verifiedToken))
    return bundle ?? http.notFound()   // someone else's turn is a 404, never a 403 that confirms it exists
  })

  http.post("/v1/turns/:id/review", { auth: "required" }, async (request) => {
    const bundle = await deps.turns.evidenceFor(request.params.id, scopeFromToken(request.verifiedToken))
    if (!bundle) return http.notFound()
    return deps.reviewInbox.submit({ kind: "customer-request", turnId: request.params.id, evidenceId: bundle.id })
  })
}

The event contract is a Zod discriminated union (a set of object shapes told apart by one shared field, here type). Every event the server sends is parsed against it first, and the web client parses with the same contract, published from contracts/turn/ as @eunomia/turn-contract. There is no "text with a magic prefix" anywhere on the wire.

const EvidenceId = z.string().regex(/^(snap|cat|psg)_[a-z0-9]{10}$/)

export const TurnEvent = z.discriminatedUnion("type", [
  z.object({ type: z.literal("turn.accepted"), turnId: z.string(), traceId: z.string() }),
  z.object({ type: z.literal("evidence.ready"), turnId: z.string(), evidenceIds: z.array(EvidenceId) }),
  z.object({ type: z.literal("answer.delta"), turnId: z.string(), seq: z.number().int().nonnegative(), text: z.string() }),
  z.object({
    type: z.literal("answer.final"),
    turnId: z.string(),
    mode: z.enum(["template", "composed"]),
    text: z.string(),
    citedEvidenceIds: z.array(EvidenceId).min(1),
  }),
  z.object({ type: z.literal("turn.declined"), turnId: z.string(), reason: z.string() }),   // a plain decline: no answer, no evidence to cite
  z.object({ type: z.literal("handoff.offered"), turnId: z.string(), reason: z.string(), reviewTicket: z.string() }),
  z.object({ type: z.literal("turn.failed"), turnId: z.string(), code: z.string(), retryable: z.boolean() }),
])

Notice what answer.delta does not mean. In the composed step the whole draft is verified before the first delta is sent, so deltas are pacing for the reader, not live model tokens as in Lesson 3's streaming typewriter. That costs a second or so of waiting, and it buys a hard guarantee: text already shown in a browser cannot be recalled, so only checked text is ever shown. Lesson 53's resilient-streaming contract still applies: every turn ends with exactly one of answer.final, turn.declined, handoff.offered or turn.failed. A plain decline gets its own ending event rather than an answer.final, because it has no evidence to cite.

Important boundary: the verifier is not the only lock. The strict body schema, token-only scope, input screen, frozen evidence and the ending-event rule each fail closed on their own, so a verifier bug does not silently open the other doors.

The answer-mode sequence and the model gateway

The problem: if every question goes to the same model with the same freedom, Eunomia pays model cost and model risk even for questions ordinary code can answer exactly, and a provider outage takes the whole assistant down. Skill Reporter has the same problem when every report request is treated as a free-writing task for one provider.

Instead of several agent configurations, Eunomia has one answer-mode sequence (an ordered list of ways to answer, from the most predictable to the most human) with three steps. Template: a deterministic answer filled straight from evidence, used when the question type allows it, such as "when does my fixed-term deposit mature?". Composed: the model writes from the frozen evidence only, then the verifier checks every figure and claim; if the planned bundle falls short, the model may request one more capability call, which the service executes and re-freezes into the bundle before the model writes (a second evidence.ready then lists the full set of ids). Handoff: a person. A routing policy table in domain/ picks the starting step for each question type before any evidence is gathered, because the step decides what evidence to gather; the sequence runner in answering/ receives that starting step. A failed verification drops the turn one step; it never climbs back up. Think of a staircase where you may only step down: each step trades a little automation for a little more safety.

This turns Lesson 37's model cascade into a cascade of answer modes rather than model sizes, makes Lesson 11's routing a reviewed table instead of an improvised choice, and puts Lesson 64's decision-first routing at the very top of the turn. Lesson 50's fallback routing lives one level down, inside the gateway.

// service/src/domain/routing-policy.ts — pure, reviewed like code
export type Step = "template" | "composed" | "handoff"
/** TurnStore.open returns an OpenTurn; classification adds what the sequence needs to choose and render a step. */
export type RoutedTurn = OpenTurn & { questionType: QuestionType; confidence: number }

/** A change to this table selects the advice-line and money-facts scenarios in CI. */
const ROUTING_POLICY: Readonly<Record<QuestionType, Step>> = {
  "maturity-date": "template",
  "protection-coverage": "template",
  "holdings-summary": "template",
  "product-search": "composed",
  "guidance": "composed",
  "personal-recommendation": "handoff",   // the advice line: Eunomia explains, it does not choose
  "unclear": "handoff",
}
export const startingStep = (type: QuestionType, confidence: number): Step =>
  confidence >= 0.8 ? ROUTING_POLICY[type] : "handoff"
const SEQUENCE: readonly Step[] = ["template", "composed", "handoff"]
export const oneStepDown = (step: Step): Step => SEQUENCE[Math.min(SEQUENCE.indexOf(step) + 1, SEQUENCE.length - 1)]

// service/src/answering/turn-runner.ts — the step is chosen first, because it decides what evidence to gather
export async function* runTurn(input: TurnInput, deps: AnswerDependencies) {
  const screened = screenInput(input.message)                             // injection and advice-line checks, no model involved
  if (!screened.ok) {
    yield* declineOrHandoff(input.turn, screened.reason, deps)            // turn.declined, or an "advice-line" review item (no evidenceId yet) + handoff.offered
    return
  }
  const route = classify(input.message)                                   // { questionType, confidence }
  const start = startingStep(route.questionType, route.confidence)
  const gathered = await planEvidence(route.questionType, start, input.scope, deps.capabilities, input.signal)  // the service calls the capabilities
  const evidence = await deps.turns.freeze(input.turn.id, gathered)       // frozen and stored before any wording
  yield { type: "evidence.ready", turnId: input.turn.id, evidenceIds: [...evidence.ids] }
  const routed: RoutedTurn = { ...input.turn, ...route }
  yield* answer(routed, start, evidence, deps, input.signal)
}

// service/src/answering/sequence.ts — receives the starting step; it can only step down
async function composeOrNull(deps: AnswerDependencies, turn: RoutedTurn, evidence: EvidenceBundle, signal: AbortSignal) {
  try {
    let reply = await deps.gateway.compose(composeRequest(turn, evidence, { mayRequest: true }), turn.budget, signal)
    if (reply.kind === "capability-request") {                            // at most one extra call per turn
      const added = await deps.capabilities.runRequested(reply.request, turn, deps.gateway, signal)  // Zod-checked; one Lesson 47 correction
      evidence = await deps.turns.refreeze(turn.id, evidence, added)      // new evidence id, stored before the model writes
      reply = await deps.gateway.compose(composeRequest(turn, evidence, { mayRequest: false }), turn.budget, signal)
    }
    return reply.kind === "draft" ? { draft: reply, evidence } : null
  } catch (error) {
    if (error instanceof GatewayUnavailable) return null    // a provider outage drops one step; it is not a failed turn
    if (error instanceof CapabilityRequestRejected) return null   // still malformed after one correction
    throw error
  }
}

export async function* answer(turn: RoutedTurn, start: Step, frozen: EvidenceBundle, deps: AnswerDependencies, signal: AbortSignal) {
  let step = start
  let evidence = frozen

  while (step !== "handoff") {
    const attempt = step === "template"
      ? { draft: renderTemplate(turn.questionType, evidence), evidence }   // draft is null when the evidence does not fit
      : await composeOrNull(deps, turn, evidence, signal)                  // null when the provider chain is down or the request was rejected
    if (attempt && attempt.evidence !== evidence) {
      evidence = attempt.evidence                                          // re-frozen with one requested result
      yield { type: "evidence.ready", turnId: turn.id, evidenceIds: [...evidence.ids] }
    }
    const draft = attempt?.draft ?? null
    const check = draft ? verifyDraft(draft, evidence) : { ok: false as const, problems: [step === "template" ? "no template fit" : "no usable draft"] }

    deps.trace.record({ kind: "step.tried", turnId: turn.id, step, ok: check.ok, problems: check.ok ? [] : check.problems })
    if (check.ok && draft) {
      yield* paceVerifiedText(turn.id, draft.text)
      yield { type: "answer.final", turnId: turn.id, mode: step, text: draft.text, citedEvidenceIds: draft.citedEvidenceIds }
      return
    }
    step = oneStepDown(step)
  }

  const kind = start === "handoff" ? "routed-to-person" : "last-step"     // the table chose a person, or every step was tried
  const ticket = await deps.reviewInbox.submit({ kind, turnId: turn.id, evidenceId: evidence.id })
  yield { type: "handoff.offered", turnId: turn.id, reason: "A colleague will check this for you.", reviewTicket: ticket.id }
}

The ModelGateway port hides providers behind one method. Its adapter holds a fallback chain (an ordered list of providers to try), a circuit breaker per provider (a switch that stops calling a provider for a cool-down period after repeated failures, like a fuse that trips instead of letting every request wait for a timeout), and a per-turn budget so a slow chain cannot run up unbounded cost or time. When the whole chain is unavailable, the gateway throws a typed error and the sequence drops to handoff. The request's abort signal is combined with each provider's timeout, so a customer who closes the page cancels the outstanding call instead of leaving it running.

/** Lesson 29's token bucket: take() waits until the provider's pace allows one more call, or rejects if the signal aborts. */
export interface TokenBucket { take(signal: AbortSignal): Promise<void> }

export function createModelGateway(chain: readonly ProviderAdapter[], clock: Clock, pace: TokenBucket): ModelGateway {
  const breakers = new Map(chain.map((p) => [p.id, new CircuitBreaker({ trips: 3, coolDownMs: 30_000, clock })]))

  return {
    async compose(request, budget, signal) {
      for (const provider of chain) {
        signal.throwIfAborted()                                              // the client left: stop trying providers
        const breaker = breakers.get(provider.id)!
        if (!breaker.isClosed()) continue
        if (!budget.canSpend(provider.estimateCostPence(request), provider.timeoutMs)) continue

        try {
          await pace.take(signal)                                            // Lesson 29: a token bucket keeps calls within the provider's pace
          const callSignal = AbortSignal.any([signal, AbortSignal.timeout(provider.timeoutMs)])   // disconnect or timeout aborts the call
          const reply = await provider.compose(request, callSignal)
          budget.spend(reply.usage.costPence)
          breaker.recordSuccess()
          return ComposeReply.parse(reply)   // structured output: a draft (text + claims + cited evidence ids) or one capability request
        } catch (error) {
          if (signal.aborted) throw error                                    // a disconnect is not the provider's fault
          breaker.recordFailure()
          budget.noteFailure(provider.id, error)
        }
      }
      throw new GatewayUnavailable(budget.failures())
    },
  }
}

Every turn opens an OpenTelemetry span (one timed unit of work inside a trace, which links work across services). Child spans cover the screen, each capability call, each step tried, each provider attempt and the verifier. They reach the outside world only through the TraceSink port, whose adapter masks attributes in the export path (the last step before telemetry leaves the service), so a caller that forgets to clean a field still cannot leak a balance. This is Lesson 7's trace tree joined with Lesson 17's distributed tracing. Record bounded metadata (ids, timings, step, verdict, evidence ids, provider, cost); the evidence store already holds the facts, so the tracing system must not become a second customer database.

Capstone decision: the routing table, templates, prompt and provider chain are versioned configuration, and each has a hash in the run manifest. Changing any of them is a release, gated like code. Eunomia and Skill Reporter share this promotion boundary.

Three coarse capabilities, and the domain rules behind them

The problem: model output can look valid while carrying unsafe arguments: another customer's identifier, an impossible term, a rate filter of 400 percent. Many fine-grained tools also give the model many chances to pick the wrong one or to do arithmetic it should not. Skill Reporter has the same risk when model-generated report arguments are not validated strictly.

There are exactly three read-only capabilities, each declared with Zod on both sides. The service's evidence planner calls the ones a question type needs before the evidence is frozen; the model never calls a store directly. On the composed step the model may request one further call through the same typed interface, and the service validates it, executes it, adds the result under a new evidence id and re-freezes the bundle before the model writes. readSnapshot() takes no arguments and returns one typed, already-scoped snapshot of the customer's holdings, maturities and protection. queryCatalogue({ access, minTermMonths, maxTermMonths, minRatePercent }) filters the approved product catalogue. lookupGuidance({ topic, question }) returns approved passages, each with a stable passage id. Every output carries an evidence id, which is what lets the verifier and the evidence route say exactly where a figure came from.

The capabilities are coarse on purpose. One snapshot call replaces a handful of small lookups, so the model cannot assemble a partial picture and fill the gap by guessing. This is Lesson 1's schema pattern and Lesson 2's injected dependencies turned into a security boundary: scope arrives from the verified token through the injected AccountReader, never from an argument. Domain refinements such as "the minimum term may not exceed the maximum" are Lesson 44's semantic guardrails (business rules beyond data shape). The design applies Lesson 52's least-authority principle without claiming its signed, per-action permission tokens.

import { z } from "zod"

const Pence = z.number().int().nonnegative().safe()
const EvidenceId = z.string().regex(/^(snap|cat|psg)_[a-z0-9]{10}$/)

export const CatalogueFilter = z.object({
  access: z.enum(["easy-access", "notice", "fixed-term"]),
  minTermMonths: z.number().int().min(0).max(120).optional(),
  maxTermMonths: z.number().int().min(0).max(120).optional(),
  minRatePercent: z.number().min(0).max(15).optional(),
}).strict()
export const GuidanceQuery = z.object({
  topic: z.enum(["protection", "maturity", "withdrawals", "isa-basics", "interest-and-tax"]),
  question: z.string().trim().min(3).max(400),
}).strict()

export const capabilities = {

    }),
  }),
} as const

Protection is computed by domain code, never by the model. The scheme limit applies per person per banking group (one licensed bank, which may sell under several brand names), so two brands in the same group share one limit. The function below works in whole pence so there is no rounding, checks that totals stay inside the safe integer range, and reads the limit from a versioned rule rather than a number written into the code. The model may explain the result; it cannot supply or change any input to it.

// service/src/domain/protection.ts — pure: no I/O, no clock, no model
export function protectionByGroup(
  holdings: readonly EligibleHolding[],
  rule: ProtectionRule,                 // { version, limitPencePerGroup } from versioned config
): readonly GroupProtection[] {
  const totals = new Map<string, number>()

  for (const holding of holdings) {
    const next = (totals.get(holding.bankingGroup) ?? 0) + holding.balancePence
    if (!Number.isSafeInteger(next)) throw new DomainError("BALANCE_OUT_OF_RANGE")
    totals.set(holding.bankingGroup, next)
  }

  return [...totals].map(([bankingGroup, eligiblePence]) => {
    const coveredPence = Math.min(eligiblePence, rule.limitPencePerGroup)
    return { bankingGroup, eligiblePence, coveredPence, uncoveredPence: eligiblePence - coveredPence, ruleVersion: rule.version }
  })
}

The verifier is the other half of the same idea. A composed draft comes back as structured output: the text plus a list of claims, each pointing at evidence ids. The verifier pulls every money amount, percentage and date out of the text and requires each to appear in the frozen evidence, requires every claim to cite evidence that exists, and runs Lesson 13's deterministic output scan for other customers' details and advice-line wording. It also requires the draft to cite at least one evidence id, and every cited id to exist in the bundle. If the model's one capability request carries malformed arguments, Lesson 47's bounded correction loop applies: the validation error goes back once, the corrected request is validated again, and a second failure drops the turn a step instead of retrying forever.

export function verifyDraft(draft: Draft, evidence: EvidenceBundle): Verification {
  const problems: string[] = []

  if (draft.citedEvidenceIds.length === 0) problems.push("no cited evidence")
  for (const id of draft.citedEvidenceIds) if (!evidence.ids.has(id)) problems.push(`cited id not in bundle: ${id}`)
  for (const figure of extractFigures(draft.text)) {            // "£1,250.00", "4.10%", "14 March 2027"
    if (!evidence.figures.has(figure.normalised)) problems.push(`figure not in evidence: ${figure.raw}`)
  }
  for (const claim of draft.claims) {
    if (claim.evidenceIds.length === 0) problems.push(`uncited claim: ${claim.id}`)
    for (const id of claim.evidenceIds) if (!evidence.ids.has(id)) problems.push(`unknown evidence id: ${id}`)
  }
  if (namesSomeoneOutsideScope(draft.text, evidence.scope)) problems.push("mentions another customer")
  if (crossesAdviceLine(draft.text)) problems.push("personal recommendation")

  return problems.length === 0 ? { ok: true } : { ok: false, problems }
}
Never ask the model to calculate a financial figure that ordinary code can calculate exactly. Let code gather the evidence, let the model ask for at most one more piece through the same typed interface and explain it, and use code to check that the explanation only repeats what the evidence says.
Capability contract: validate on both sides. Input validation protects the service from the model; output validation catches a broken store before its malformed result becomes persuasive prose; evidence ids let the verifier, the client and a reviewer all point at the same facts.

An optional MCP server shares guidance and the catalogue, never the customer

The problem: other internal assistants want the same approved guidance and product facts. Copying the capability code into each one causes contract drift, while giving each one direct store access widens the attack surface. Skill Reporter has the same integration drift unless shared contracts and narrow gateways are enforced.

A Model Context Protocol (MCP) server lets other approved hosts discover and call capabilities through a standard contract. Eunomia's MCP server is optional, read-only, and exposes only lookupGuidance and queryCatalogue. Both return facts that are the same for every customer. readSnapshot is never exposed: customer holdings stay behind the authenticated /v1/turns route, where scope comes from a customer token. Hosts that call the MCP server authenticate as approved service identities. This selective design matters more than adopting the protocol everywhere.

Lesson 6 becomes the server boundary, Lesson 23 becomes discovery at startup by the hosts that consume this server, and Lesson 48 describes how such a calling host turns the advertised schemas into local tool definitions at runtime. Lesson 33's server-side dynamic tool synthesis and runtime registration is deliberately not used in the first release: the server registers its two tools once, at startup, from reviewed code, so the advertised contract changes only through a gated release. Lesson 32's resource subscriptions (change notifications from the server) can tell a host that the catalogue version changed, but a turn pins the catalogue version in its evidence bundle, so facts do not shift halfway through one answer.

SHARE THE SAME-FOR-EVERYONE FACTS OVER MCP; KEEP THE CUSTOMER SNAPSHOT BEHIND THE TOKEN

The server reuses the exact Zod shapes from the capability declarations, so the MCP contract and the in-service contract cannot drift apart. It is a second adapter onto the same ports, not a second implementation.

import { McpServer } from "@modelcontextprotocol/sdk/server/mcp.js"
import { capabilities, CatalogueFilter, GuidanceQuery, runLookupGuidance, runQueryCatalogue } from "../../capabilities"   // the same reviewed implementations the evidence planner calls
import type { Catalogue, GuidanceStore } from "../../ports"

export function buildGuidanceMcpServer(ports: { guidance: GuidanceStore; catalogue: Catalogue }) {
  const server = new McpServer({ name: "eunomia-guidance", version: "1.0.0" })

  server.registerTool(
    "lookupGuidance",
    { description: "Approved savings guidance passages with stable passage ids.", inputSchema: GuidanceQuery.shape },
    async (args, extra) => {
      const input = capabilities.lookupGuidance.input.parse(args)
      const output = capabilities.lookupGuidance.output.parse(await runLookupGuidance(input, ports, extra.signal))   // a cancelled MCP request cancels the lookup
      return { content: [{ type: "text", text: JSON.stringify(output) }] }
    },
  )

  server.registerTool(
    "queryCatalogue",
    { description: "Products in the approved catalogue matching a filter.", inputSchema: CatalogueFilter.shape },
    async (args, extra) => {
      const input = capabilities.queryCatalogue.input.parse(args)     // includes the min/max term refinement
      const output = capabilities.queryCatalogue.output.parse(await runQueryCatalogue(input, ports, extra.signal))

    },

}
Capstone decision: MCP is an interoperability boundary, not a shortcut around authorization. Every exposed capability calls the same reviewed implementation with the same input and output schema checks as inside the service, as the sample shows, and nothing customer-specific is on it. Timeouts and traces are added by the adapter around each handler, as the HTTP adapter does for its routes; that wrapper is not shown here. The same rule applies to Eunomia and Skill Reporter integrations.

The Next.js client renders typed turn events and shows its evidence

The problem: a chat page must reconcile acceptance, evidence, paced text, a final answer, a handoff, errors and dropped connections without ever making a half-finished turn look like a complete financial answer. Hand-built string handling drifts from what the server really sends. Skill Reporter needs the same typed event discipline for long-running report generation.

The client in web/ is a Next.js (React web framework) application. A server-side route in the client forwards the signed-in session's token to POST /v1/turns and passes the event stream back unchanged; it never adds a customer id of its own. In the browser, a small reader splits the stream into frames, parses each one with the published TurnEvent contract, and feeds it to a reducer (a function that takes the current screen state plus one event and returns the next state). Unknown or malformed events are dropped and counted, not displayed.

This is Lesson 53's error-aware event contract on the receiving side. Lesson 38's typed multimodal-event principle matters before Eunomia ever accepts images or files: every kind of content gets its own event type rather than a string with a magic prefix. And because answer.delta is paced verified text rather than live generation, the client never has to retract words, which Lesson 3's raw token stream would have made possible.

"use client"
import { TurnEvent } from "@eunomia/turn-contract"   // the contracts/turn/ workspace package; the service sends with the same schema

export const droppedEvents = { count: 0 }   // malformed frames are dropped and counted, never shown

export async function* readTurnEvents(response: Response): AsyncGenerator<TurnEvent> {
  const reader = response.body!.pipeThrough(new TextDecoderStream()).getReader()
  let buffer = ""
  for (;;) {
    const { value, done } = await reader.read()
    if (done) return
    buffer += value
    let end: number
    while ((end = buffer.indexOf("\n\n")) !== -1) {
      const frame = buffer.slice(0, end)
      buffer = buffer.slice(end + 2)
      const data = frame.split("\n").filter((l) => l.startsWith("data: ")).map((l) => l.slice(6)).join("\n")
      if (!data) continue
      let parsed: ReturnType<typeof TurnEvent.safeParse> | null = null
      try { parsed = TurnEvent.safeParse(JSON.parse(data)) } catch { parsed = null }
      if (parsed?.success) yield parsed.data
      else droppedEvents.count += 1
    }
  }
}

export function turnReducer(state: TurnView, event: TurnEvent): TurnView {
  switch (event.type) {
    case "turn.accepted":   return { ...state, turnId: event.turnId, status: "working" }
    case "evidence.ready":  return { ...state, evidenceIds: event.evidenceIds }
    case "answer.delta":    return event.seq === state.nextSeq
                              ? { ...state, draft: state.draft + event.text, nextSeq: state.nextSeq + 1 }
                              : state
    case "answer.final":    return { ...state, status: "answered", text: event.text, cited: event.citedEvidenceIds }
    case "turn.declined":   return { ...state, status: "declined", text: event.reason }
    case "handoff.offered": return { ...state, status: "handed-off", ticket: event.reviewTicket }
    case "turn.failed":     return { ...state, status: "failed", retryable: event.retryable }
  }
}

If the stream closes while the state is still working, the page shows "this answer did not finish" and offers a retry with the same conversation id; it never promotes the partial draft to an answer. Under each finished answer, a "Where this came from" panel calls GET /v1/turns/{id}/evidence and lists the snapshot date, catalogue version and guidance passages behind it, and an "Ask a person to check" button calls POST /v1/turns/{id}/review. The browser is never trusted to calculate balances or protection; it only displays figures that came back in verified events.

Event rule: turn events are part of the product contract. Version them, test them from outside, and make the ending explicit; a dropped connection must never look like a complete financial answer.

An independent Python probe suite proves the contract from outside

The problem: tests that run inside the service can inherit the same wrong assumptions as the service, and mocks keep passing after the real HTTP contract breaks. Skill Reporter has the same blind spot without an independent client that only sees what a real caller sees.

Eunomia's probes/ folder is a separate Python suite. A contract probe (a test that checks a promise the public API makes, such as "every turn ends with exactly one ending event", by calling it the way a real client would) talks to any running environment over HTTP only, chosen by a base URL and a test credential. It shares no code with the service: not the Zod schemas, not the fixtures, not a helper. The client holds only public HTTP calls and its own reading of the wire contract; fixtures name which test customer signs in; the tests state user-visible promises. A stub upstream (a controllable stand-in for the account, catalogue and guidance stores and for the model providers, which counts every call it receives) can inject latency, errors and malformed payloads on request.

A different language makes accidental imports impossible, but language alone does not prove independence. The suite is independent because it uses only public contracts, its own fixtures, and observable behaviour. This applies Lesson 26's principle of verifying the real running system from outside (there through a browser, here through HTTP calls), and Lesson 24's process orchestration is how CI starts the service, the stub and the probes in the right order and waits for /readyz before the first probe runs.

quality/ turns answer quality into versioned, pinned evidence

The problem: unit tests prove that a schema rejects bad input; probes prove that the HTTP contract holds. Neither proves that an answer after a prompt or model change still shows the right figure, cites the right passage, stays on the right side of the advice line, and reads clearly. Skill Reporter needs the same layer to catch quality regressions that types and contracts miss.

quality/ holds scenario files grouped by risk: money facts, the advice line, privacy, injection and tone. Each scenario is a list of checkable properties (shows this figure, cites a passage, never names another customer, declines advice) plus any rubrics (written scoring rules) that a judge model applies. Properties are checked by code first because they are cheap and exact; rubric judges run after, and a judge is allowed to gate a release only once its scores agree well enough with human labels on a calibration set. Every run writes a run manifest (a small file that pins exactly what was tested): model, provider chain, and the hashes of the prompt, templates, routing policy, capability schemas and scenario set.

The harness loop has four steps. Snapshot: restore the scenario's fixture state in the stores, so every run starts from the same known world. Replay: run the turn through the real HTTP surface, exactly as a client would. Assert: check properties against the turn and its evidence bundle, then run the calibrated rubric judges. Archive: store the evidence bundle, events, verdicts and manifest id together, so any failure can be reopened later. Then a deterministic hash decides which passes also go to the review inbox; every failure always goes.

import { createHash } from "node:crypto"

export async function runScenario(scenario: Scenario, run: RunContext): Promise<ScenarioResult> {
  await run.fixtures.restore(scenario.fixture)                                       // 1. snapshot
  const turn = await run.client.streamTurn(scenario.turn, { as: scenario.signedInAs }) // 2. replay (real HTTP)
  const evidence = await run.client.evidenceFor(turn.turnId)

  const properties = scenario.properties.map((p) => checkProperty(p, turn, evidence)) // 3. assert, exact first
  const rubrics = await run.judges.score(scenario.rubrics, turn, evidence)
  const result = { scenarioId: scenario.id, manifestId: run.manifest.id, turn, evidence, properties, rubrics }

  await run.archive.store(result)                                                    // 4. archive
  if (!passed(result) || sampledForReview(run.manifest.id, scenario.id, run.reviewShare)) {
    await run.reviewInbox.submit({ kind: "quality-run", turnId: turn.turnId, evidenceId: evidence.id, manifestId: run.manifest.id })
  }
  return result
}

/** Same manifest + scenario always lands on the same side of the line, so reviewers see a stable sample. */
export function sampledForReview(manifestId: string, scenarioId: string, share: number): boolean {
  const digest = createHash("sha256").update(`${manifestId}:${scenarioId}`).digest()
  return digest.readUInt32BE(0) / 0x1_0000_0000 < share
}

Lessons 10 and 19 supply evaluation-driven development and judge calibration against human-labelled examples; reviewers' labels from the inbox feed that calibration set. Lesson 55's deterministic sampling is the hash above: re-running the same manifest picks the same passes, so two people reviewing "the sample" are looking at the same turns. A strong production turn can become a new scenario only after redaction, deduplication and a person's approval; a run's manifest can become the new approved baseline only after the gate passes (Lesson 56's last-approved baseline rule) and then only after a window of consecutive passing runs on main (Lesson 57).

Evaluation rule: never let the same uncalibrated model write the answer, judge the answer, and approve its own release without independent human labels. That is one opinion wearing three badges.

Continuous integration blocks quality regressions, not just build failures

The problem: a change can compile, pass unit tests and pass every probe while still dropping a figure, weakening the advice line, or making answers harder to read. Ordinary CI stays green through that. Skill Reporter has the same release risk without a quality gate tied to promotion.

The pipeline on GitHub Actions has four stages. Checks: lint (static code-quality checks), types, unit tests and build. Probes: start the built service and the stub upstream, wait for /readyz, run the Python suite. Quality gate: on a pull request, pick scenario groups from the paths changed against origin/<base branch>, using full git history (a style-only change in web/ runs none; a change to the prompt, routing table, templates, capabilities or provider chain runs the groups that depend on it; any change to domain/ runs money facts); on a push to main, run the full scenario set with no path filtering. Then compare against the last approved manifest. Production: a protected environment with a required reviewer.

This is Lesson 25's eval gate made selective, Lesson 30's shared pipeline across one repository, and Lesson 56's approved-baseline comparison. The required reviewer applies the broad human-oversight principle from Lessons 12 and 39, but it is not their durable per-action checkpoint; write actions, which would need that, are deferred.

CHECKS → PROBES → QUALITY GATE (PATH-SELECTED ON PRS, FULL ON MAIN) → PROTECTED PRODUCTION WITH A REQUIRED REVIEWER

Branch protection makes the workflow a required status check, so a pull request cannot merge unless it succeeds; that rule lives in the repository settings, outside the YAML. The production environment has a required reviewer, so a named person must approve before the deploy job starts, and the same approval records the run's manifest as a candidate. The approved baseline in quality/manifests/approved.yaml moves to that candidate only after a window of consecutive passing runs on main (Lesson 57); one approval never moves it on its own. When the window is met, quality:promote opens a pull request under a bot identity that updates approved.yaml, so the baseline moves only through that reviewed change, merged like any other.

The gate checks two things per risk group. A floor is an absolute minimum pass rate; an allowed regression is the most the pass rate may fall below the last approved manifest. A tone pass rate of 0.93 may clear its floor of 0.90 and still block if the approved run reached 0.97 and the allowed regression is 0.02. Money facts, privacy and the advice line are zero-tolerance groups: one wrong figure, one other customer named, or one personal recommendation blocks the change whatever the average says. Promotion follows Lesson 57: the approved manifest only moves after a window of consecutive passing runs on main, never after one lucky pass, and then only when the promotion pull request that updates approved.yaml is reviewed and merged.

Delivery rule: the baseline is an approved manifest, never "whatever main produced most recently". A failed run cannot lower the bar for the next one.

The operating loop is concrete. Every answer carries a turn id and a trace id, and its evidence can be fetched again. A customer (through the review route), the sequence runner (at the last step, or when the routing table hands off), the input screen (for advice requests) and the quality harness's sampler can each send a turn to the review inbox. A reviewer's label can become calibration data, and an approved, redacted turn can become a new scenario. A required status check runs the affected scenario groups, compares them with the approved manifest, and blocks a material regression. Production promotion passes a required reviewer and records the manifest as a candidate; the approved baseline moves to it only after a window of consecutive passing runs on main, so an operator always knows exactly which model, prompt and schemas to return to. That closes the path from Lesson 1's first schema to Lesson 57's rule of promoting only after a window of consecutive passing runs.

The finished system: Eunomia is useful because the model can read a customer's question, ask for one more piece of evidence when the planned bundle falls short, and explain holdings, products and guidance in plain words. It is trustworthy because identity, schemas, pence arithmetic, the routing table, frozen evidence, the verifier, traces, independent probes, human review and the release gate surround that reasoning at every boundary. Skill Reporter ships under the same boundary model: the capabilities are domain-specific, but the safety and verification controls are shared.
The capstone lesson: production AI architecture is not a larger prompt. It is a chain of small, inspectable contracts that lets a probabilistic model contribute where judgement helps, while ordinary software stays in charge of identity, money, evidence and release.
