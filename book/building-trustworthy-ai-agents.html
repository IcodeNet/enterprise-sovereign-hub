Part I

Foundations of an Agent with Checked Data

Before an AI agent (software that lets a model use instructions, data, and tools to complete a task) can be trusted with real work, it needs replies a program can read, access to current facts, incremental delivery, evidence from private documents, and routing for multi-step decisions. This part builds those five foundations in Python and TypeScript and exercises each one with running examples.

Two problem domains run through this part:

  • Domain A — Skill Reporter (simple baseline): input is a job-market query. Goal is to extract a skill, assess demand, and produce structured output your code can trust.
  • Domain B — Fintech Service Agent (higher-risk): input is a customer question about accounts, product rules, or simulation. Goal is to route safely, ground policy answers in evidence, and enforce consent/risk checks before simulations.

How these lessons interlink: Lesson 1 defines checked output contracts, Lesson 2 adds fresh tool data, Lesson 3 adds live delivery, Lesson 4 adds evidence grounding (RAG), and Lesson 5 adds graph routing that composes those earlier pieces.

Runnable-example rule for this part: each snippet should include all imports it uses, and every variable should be introduced before first use.

Lesson 1

Agent Foundations with Checked Types

The problem: Eunomia and Skill Reporter cannot operate reliably if model output is just free-form prose. Downstream code needs typed fields, not guesses from paragraphs. Without fixed output structure, both domains risk mis-parsing critical values and making wrong decisions.

The fix is type-safe data (checked so values have the kinds the code expects): tell the AI which fields (named values in a data object) to return and what kind each one is, using a schema (a machine-checked description such as "field X is text, field Y is a whole number from 1 to 10"). In Python this is built with Pydantic (a Python data-validation library); in TypeScript, with Zod (a TypeScript data-validation library). A tool validates each answer against that schema before your own code sees it and can retry when an attempt does not fit. This checks structure and ranges, not whether the AI's claims are factually correct.

PLAIN QUESTION → AI DRAFTS A REPLY → SCHEMA VALIDATES REQUIRED FIELDS (retry if it fails) → YOUR CODE READS CHECKED VALUES

Here's what that looks like in Python, using pydantic_ai: a BaseModel (Pydantic's building block for defining a validated data model) called MarketInsight with three required fields, and an Agent told to produce values that pass those checks.

import asyncio

from pydantic import BaseModel, Field
from pydantic_ai import Agent


class MarketInsight(BaseModel):
    skill_name: str = Field(description="The exact name of the technical skill identified.")
    demand_frequency: int = Field(ge=1, le=10, description="Frequency level found in text from 1 (low) to 10 (high).")
    justification: str = Field(description="A single clear sentence explaining why this skill is needed.")


market_agent = Agent(
    "openai:gpt-4o",
    output_type=MarketInsight,
    system_prompt="Extract one skill and rate demand from 1 to 10.",
)

sample_job = "Hiring an AI engineer with strong LangGraph and Python experience."


async def main() -> None:
    result = await market_agent.run(sample_job)
    data: MarketInsight = result.output
    print(data.model_dump())


if __name__ == "__main__":
    asyncio.run(main())
A real finding worth knowing: field descriptions are not just comments for other developers — they are sent to the AI as part of its instructions and guide what it writes. Clear descriptions reduce ambiguity, while the schema performs the actual validation.

The TypeScript equivalent swaps Pydantic for Zod and pydantic_ai for the Vercel AI SDK (a popular TypeScript library for generating text, calling tools, and streaming replies across model providers), but the idea is identical: define the schema once, hand it to the model-calling function, and validate the declared fields and constraints. These default object schemas do not promise to reject every undeclared extra property; configure strict rejection separately if that matters.

Lesson 2

Fresh Request Data & Tool Calling

The problem: Eunomia and Skill Reporter both need current system facts, not only model memory. Training data can be stale, and prompt text alone cannot fetch live account or reporting state. Without explicit tools, both domains answer confidently with outdated or missing data.

Baking a live number straight into the AI's setup doesn't work either — the moment you have more than one user, or the number changes between requests, a hardcoded value (one written directly into the program) is wrong. The fix is two matched pieces: a dependency (fresh data or a service the agent needs) supplied for each request through dependency injection (providing those needs from the outside instead of making the agent fetch global data itself), and a tool call (a function the AI can decide to run mid-answer instead of only replying with text) that reads from that bundle.

LIVE DATA BUNDLE INJECTED → AGENT DECIDES IT NEEDS A FACT → CALLS A TOOL → TOOL READS THE BUNDLE → A BOUNDED FOLLOW-UP STEP CAN WORD THE RESULT

In Python, this is deps_type plus a decorated function (a function registered by placing @agent.tool above it):

import asyncio
from dataclasses import dataclass

from pydantic import BaseModel
from pydantic_ai import Agent, RunContext


@dataclass
class DatabaseDeps:
    user_id: str
    skill_database: dict[str, int]


class TrendAssessment(BaseModel):
    skill_name: str
    live_count: int
    summary: str


trend_agent = Agent(
    "openai:gpt-4o",
    deps_type=DatabaseDeps,
    output_type=TrendAssessment,
    system_prompt="Use the tool to get the live count before answering.",
)


@trend_agent.tool
async def fetch_live_skill_count(ctx: RunContext[DatabaseDeps], skill_name: str) -> int:
    return ctx.deps.skill_database.get(skill_name.lower().strip(), 0)


mock_deps = DatabaseDeps(
    user_id="demo-user",
    skill_database={"langgraph": 142, "pydantic": 118, "llamaindex": 96},

prompt = "What is live demand for LangGraph?"

    print(result.output.model_dump())

import { generateText, stepCountIs, tool } from "ai"
import { openai } from "@ai-sdk/openai"
import { z } from "zod"

interface DatabaseDeps {
  userId: string
  skillDatabase: Record<string, number>
}

const SkillNameSchema = z.object({ skillName: z.string() })

const deps: DatabaseDeps = {
  userId: "demo-user",
  skillDatabase: { langgraph: 142, pydantic: 118, llamaindex: 96 },
}

const prompt = "What is live demand for LangGraph?"

async function fetchLiveSkillCount(deps: DatabaseDeps, skillName: string): Promise<number> {
  return deps.skillDatabase[skillName.toLowerCase().trim()] ?? 0
}

async function main(): Promise<void> {
  const result = await generateText({
    model: openai("gpt-4o"),
    tools: {
      fetchLiveSkillCount: tool({
        description: "Look up the current count for a skill.",
        inputSchema: SkillNameSchema,
        execute: (args) => fetchLiveSkillCount(deps, args.skillName),
      }),
    },
    stopWhen: stepCountIs(3),
    prompt,
  })
  console.log(result.text)
}

main().catch(console.error)

If request data comes from an external boundary, validate it there; otherwise a missing lookup can still collapse to the examples' default value of zero.

Lesson 3

Streaming Replies / A Live-Typing Chat Page

The problem: Eunomia and Skill Reporter can generate valid answers slowly enough to appear broken. If users see no progress while work is running, trust drops and retries increase. Both domains need streaming and explicit progress state, not silent waits.

The fix is streaming (sending a reply piece by piece as it is generated instead of waiting for the whole response). In a browser, the HTTP response body is exposed to JavaScript as a ReadableStream (a Web API for consuming streamed data), so the user sees chunks (pieces delivered by the stream) arrive like live typing in a modern chat interface. Tool arguments can still be type-checked and schema-validated before execution; this example does not add runtime validation for the tool's returned value.

BROWSER REQUESTS → HTTP RESPONSE BODY STREAMS → TEXT ARRIVES IN CHUNKS WHILE TOOL ARGUMENTS REMAIN TYPED AND VALIDATED

The way to actually prove a reply is streaming — rather than one big blocking response dressed up to look streamed — is to measure it directly: count the chunks and time the gap between the first one arriving and the whole thing finishing. The Python example observes model-output deltas in a terminal; the TypeScript example observes stream parts that an HTTP handler can pass to a browser. They test the same incremental-generation idea at different layers.

import asyncio
import time

from pydantic_ai import Agent


trend_agent = Agent("openai:gpt-4o", system_prompt="Answer in plain English.")
prompt = "Explain in two short sentences why liquidity buffers matter."


async def main() -> None:
    chunk_count = 0
    started = time.perf_counter()
    first_chunk_ms = None

    async with trend_agent.run_stream(prompt) as result:
        async for chunk in result.stream_text(delta=True):
            if chunk:
                chunk_count += 1
                if first_chunk_ms is None:
                    first_chunk_ms = (time.perf_counter() - started) * 1000

    total_ms = (time.perf_counter() - started) * 1000
    print(f"chunks={chunk_count}, first_chunk_ms={first_chunk_ms:.1f}, total_ms={total_ms:.1f}")


if __name__ == "__main__":
    asyncio.run(main())
import { streamText } from "ai"
import { openai } from "@ai-sdk/openai"

async function main(): Promise<void> {
  const started = Date.now()
  let chunkCount = 0
  let firstChunkMs: number | null = null

  const result = streamText({
    model: openai("gpt-4o"),
    prompt: "Explain in two short sentences why liquidity buffers matter.",
  })

  for await (const part of result.fullStream) {
    if (part.type === "text-delta" && part.textDelta.length > 0) {
      chunkCount += 1
      if (firstChunkMs === null) firstChunkMs = Date.now() - started
    }
  }

  const totalMs = Date.now() - started
  console.log({ chunkCount, firstChunkMs, totalMs })
}

main().catch(console.error)
A real finding worth knowing: a terse, purely numeric question can produce a reply with zero narrated text chunks — the model goes straight to a tool call and stops, because there's nothing to narrate. That's not a bug; it's a reminder that "no text streamed" and "streaming is broken" are two different claims that need separate checks.
In the capstone: Eunomia's chat page keeps this lesson's goal (visible progress instead of a silent wait) with one deliberate change: the service verifies the whole answer before streaming, so the web client receives paced, already-verified answer.delta events closed by one answer.final, not live model tokens. Text already shown in a browser cannot be recalled, so the first release never streams unchecked chunks.
Lesson 4

Evidence-Based Answers with a Search-Then-Answer Workflow

The problem: Eunomia and Skill Reporter can sound confident while being wrong when answers are not grounded in approved sources. Model pretraining does not include your current product and policy truth. Both domains need retrieval-backed evidence to prevent confident hallucinations.

The fix is RAG (Retrieval-Augmented Generation — searching real documents before asking the AI to answer) to make responses grounded (conditioned on supplied evidence). This example uses vector search (matching numeric representations of meaning rather than exact words), applies a minimum relevance threshold, and returns a fixed no-evidence message when nothing qualifies. It is the first genuine multi-step workflow (a pipeline where each step does one job and passes its result to the next): search, check relevance, then generate.

QUESTION → SEARCH BY MEANING → RELEVANCE CHECK → GENERATE FROM RETRIEVED EVIDENCE, OR RETURN A FIXED NO-EVIDENCE MESSAGE

Splitting search and generation into two separate steps — instead of one function that does both — means either step can be tested, replaced, or reordered on its own: a real document database can later replace the sample sentences without touching how the final answer gets generated.

Instruction that matters, but is not an enforcement boundary: tell the AI to use the retrieved evidence. The relevance threshold prevents unsupported generation when search returns nothing useful; the prompt reduces the risk of blending in general knowledge, but cannot prove that every generated sentence came from the evidence.
import asyncio
from dataclasses import dataclass

from pydantic_ai import Agent


@dataclass
class Match:
    text: str
    score: float


class InMemoryVectorStore:
    def __init__(self, docs: list[str]) -> None:
        self.docs = docs

    async def search(self, query: str, top_k: int) -> list[Match]:
        query_terms = set(query.lower().split())
        scored: list[Match] = []
        for doc in self.docs:
            overlap = len(query_terms.intersection(doc.lower().split()))
            score = overlap / max(len(query_terms), 1)
            scored.append(Match(text=doc, score=score))
        return sorted(scored, key=lambda m: m.score, reverse=True)[:top_k]


vector_store = InMemoryVectorStore(
    [
        "ISA withdrawals may be restricted during a fixed term.",
        "Instant access accounts allow withdrawals without notice.",
        "Portfolio simulations require consent and a complete risk profile.",
    ]
)
rag_agent = Agent("openai:gpt-4o", system_prompt="Answer using only the retrieved evidence.")
MIN_RELEVANCE = 0.35
question = "Can I withdraw early from a fixed-term ISA?"


async def main() -> None:
    matches = await vector_store.search(query=question, top_k=3)
    relevant = [match for match in matches if match.score >= MIN_RELEVANCE]
    if not relevant:
        print("I don't have enough product evidence to answer that.")
        return

    context = "\n".join(match.text for match in relevant)
    answer = await rag_agent.run(
        f"Use only this retrieved evidence:\n{context}\n\nQuestion: {question}"
    )
    print(answer.output)


if __name__ == "__main__":
    asyncio.run(main())
import { generateText } from "ai"
import { openai } from "@ai-sdk/openai"

type Match = { text: string; score: number }

class InMemoryVectorStore {
  constructor(private readonly docs: string[]) {}

  async search({ query, topK }: { query: string; topK: number }): Promise<Match[]> {
    const queryTerms = new Set(query.toLowerCase().split(/\s+/))
    const scored = this.docs.map((text) => {
      const docTerms = new Set(text.toLowerCase().split(/\s+/))
      const overlap = [...queryTerms].filter((term) => docTerms.has(term)).length
      return { text, score: overlap / Math.max(queryTerms.size, 1) }
    })
    return scored.sort((a, b) => b.score - a.score).slice(0, topK)
  }
}

const vectorStore = new InMemoryVectorStore([
  "ISA withdrawals may be restricted during a fixed term.",
  "Instant access accounts allow withdrawals without notice.",
  "Portfolio simulations require consent and a complete risk profile.",
])

const MIN_RELEVANCE = 0.35

async function answerQuestion(question: string): Promise<string> {
  const matches = await vectorStore.search({ query: question, topK: 3 })
  const relevant = matches.filter((match) => match.score >= MIN_RELEVANCE)
  if (relevant.length === 0) return "I don't have enough product evidence to answer that."

  const context = relevant.map((match) => match.text).join("\n")
  const { text } = await generateText({
    model: openai("gpt-4o"),
    prompt: `Use only this retrieved evidence:\n${context}\n\nQuestion: ${question}`,
  })
  return text
}

answerQuestion("Can I withdraw early from a fixed-term ISA?")
  .then(console.log)
  .catch(console.error)
A real finding worth knowing: a vector search genuinely matches on meaning, not spelling — a question that never literally uses the word "frameworks" can still correctly retrieve a sentence about frameworks, something a classic exact-keyword search would miss entirely.

Lesson 5

Branching Agent Workflows with Shared State

The problem: Eunomia and Skill Reporter should not run every request through one identical path. Request intent and risk differ sharply: routine explanations, account-scoped retrieval, ISA-rule questions, and simulation requests need different controls. A single linear flow increases cost, latency, and policy risk in both domains. The real problem is deciding the next operational step from state, not just generating text.
The real problem is deciding the next operational step from state, not just generating text. The role of the graph is to make that control flow explicit: it owns step order, branch rules, and state updates. LLMs still do useful work inside steps (for example, extracting entities and intent from the customer question), but they do not directly decide control flow.

If control flow stays implicit inside one model prompt, planning, tool use, retrieval, guardrails, and human approval can blur into one opaque step. Then teams cannot clearly answer why a request took a specific path, why a safety gate was skipped, or why a risky action was attempted. The graph fixes that by turning routing into an explicit, auditable system decision.

The fix is a stateful workflow (one that remembers shared values as it runs) with conditional routing (choosing the next path from those values). A graph connects each node (one processing step) through an edge (a path to another step). The graph checks its state (the shared notebook of current values) and chooses which node runs next — built here with LangGraph (a library family for branching, stateful AI workflows; this lesson uses Python and TypeScript variants).

Libraries used in this lesson: Python uses langgraph for graph routing and Python's built-in typing module for a clear state shape. TypeScript uses @langchain/langgraph for the same graph routing pattern. The small examples below now include imports so you can see exactly where StateGraph comes from.

When the next step depends on what we already know, use a graph: think of the graph as a traffic controller. It reads the current state and sends each request to the right lane. For example, an interest question goes to the interest lane, a product-rule question goes to the policy lane, and a simulation request goes to the simulation lane. The model can still help inside each lane (for extraction or wording), but the graph owns the route, so behavior stays predictable, testable, and easy to audit.

How the agent uses the graph at run time: (1) the agent receives a query and stores it in state, (2) it runs extract_skill_node to pull out one skill name, (3) it runs evaluate_demand_node to set demand_level (demandLevel in TypeScript), and (4) the graph routes to exactly one final node based on that value. The graph is the step-order engine for the agent.

AI EXTRACTS SKILL → PLAIN CODE CHECKS A FIXED LIST → GRAPH BRANCHES LIVE: priority path OR standard path, never both

Not every decision needs an AI call. evaluate_demand_node never touches the model — a simple list-membership check is faster, free, and literally cannot hallucinate. Reaching for an AI call here would be slower for zero benefit.

Here is the full branching wiring in one place. StateGraph is LangGraph's workflow builder object: it holds your state shape, your nodes, and your routing rules. First, evaluate_demand_node writes demand_level (demandLevel in TypeScript) into shared state. Next, the routing function reads that value. Finally, the map tells the graph which node to run for each possible value.

import asyncio
from typing import Literal, TypedDict

from langchain_core.messages import HumanMessage, SystemMessage
from langchain_openai import ChatOpenAI
from langgraph.graph import END, StateGraph


class GraphState(TypedDict):
    job_query: str
    identified_skill: str
    demand_level: str
    final_report: str


async def extract_skill_node(state: GraphState) -> dict[str, str]:
    llm = ChatOpenAI(model="gpt-4o", temperature=0)
    response = await llm.ainvoke(
        [
            SystemMessage(
                content="Extract the primary technical skill name from the user's job query. Reply with only the skill name."
            ),
            HumanMessage(content=state["job_query"]),
        ]
    )
    return {"identified_skill": str(response.content).strip()}


async def evaluate_demand_node(state: GraphState) -> dict[str, str]:
    skill = state["identified_skill"].lower()
    target_stack = ["langgraph", "pydantic", "vercel ai", "llamaindex"]
    demand = "HIGH_DEMAND" if any(target in skill for target in target_stack) else "STANDARD_DEMAND"
    return {"demand_level": demand}


async def high_priority_evaluator(state: GraphState) -> dict[str, str]:
    return {
        "final_report": f"PRIORITY TRACK: '{state['identified_skill']}' is a high-demand core skill."
    }


async def standard_evaluator(state: GraphState) -> dict[str, str]:
    return {"final_report": f"STANDARD TRACK: Identified skill '{state['identified_skill']}'."}


def route_by_demand(state: GraphState) -> Literal["high_priority_evaluator", "standard_evaluator"]:
    return "high_priority_evaluator" if state["demand_level"] == "HIGH_DEMAND" else "standard_evaluator"


# Runtime flow:
# 1) Agent receives a query in state["job_query"].
# 2) extract_skill_node writes state["identified_skill"].
# 3) evaluate_demand_node writes state["demand_level"].
# 4) route_by_demand picks exactly one final evaluator node.
builder = StateGraph(GraphState)
builder.add_node("extract_skill_node", extract_skill_node)
builder.add_node("evaluate_demand_node", evaluate_demand_node)
builder.add_node("high_priority_evaluator", high_priority_evaluator)
builder.add_node("standard_evaluator", standard_evaluator)
builder.set_entry_point("extract_skill_node")
builder.add_edge("extract_skill_node", "evaluate_demand_node")
builder.add_conditional_edges(
    "evaluate_demand_node",
    route_by_demand,
    {
        "high_priority_evaluator": "high_priority_evaluator",
        "standard_evaluator": "standard_evaluator",
    },
)
builder.add_edge("high_priority_evaluator", END)
builder.add_edge("standard_evaluator", END)
graph = builder.compile()


async def main() -> None:
    final_output = await graph.ainvoke(
        {
            "job_query": "Senior AI role requiring expertise in LangGraph.",
            "identified_skill": "",
            "demand_level": "",
            "final_report": "",
        }
    )
    print(final_output["final_report"])


if __name__ == "__main__":
    asyncio.run(main())

import { generateText } from "ai"
import { END, START, StateGraph, StateSchema } from "@langchain/langgraph"

  • account_data → auth_check_node → account_data_lookup_node. Example: "How much interest did I earn last month on my Instant Saver?" requires customer authentication and account-level lookup.

  • unclear → clarification_node. Example: "Can I do that transfer now?" is ambiguous, so the assistant asks what transfer, which account, and whether the question is policy-only or account-specific.

FAQ vs account-data routing rule: account signals include personal scope and identifiers (for example "my balance", "my account", reference numbers, "this month for me"). FAQ signals are general policy/how-to/eligibility questions that can be answered from docs without user-record access.

Ambiguity rule: if confidence is below threshold, ask one clarifier: "Are you asking about general policy, or your specific account details?" In high-risk cases, default to the account-data path rather than guessing.

Part II

Giving Agents Tools at Scale (Protocols & Dynamic Tooling)

A tool written inside one agent works until another agent needs it, a team changes it, or live data moves underneath it. This part replaces that brittle arrangement in five steps: put tools behind a standard server, discover them while the agent is running, subscribe to changing resources, register carefully generated tools without a restart, and build input checks from every tool's own description. Read Lessons 6, 23, 32, 33 and 48 in that order: each adds the piece the next one depends on.

Dual-domain map for this part: every mechanism is shown in the fintech Eunomia implementation and should be mirrored in the Skill Reporter implementation.

  • Fintech domain: balances, savings goals, interest projection, and runtime safety boundaries around customer-impacting tools.
  • Skill Reporter domain: skill lookup, report generation, report-ready updates, and runtime safety boundaries around publishing/reporting tools.

Interlink chain: Lesson 6 creates shared MCP servers, 23 discovers tools at runtime, 32 pushes live updates, 33 adds sandboxed runtime registration, and 48 validates every call against advertised schemas.

Lesson 6

MCP Server Architecture with FastMCP and the TypeScript SDK

The problem: a balance-checking tool starts life inside one assistant. When a second assistant needs the same capability, copying the function feels harmless, but there are now two implementations to secure, test and keep in step. Add more agents and every fix becomes a synchronisation problem. The Skill Reporter agent hits the same failure mode when skill-lookup and report-formatting functions get copied across assistants.

The replacement is MCP — Model Context Protocol (a published set of rules for how an AI agent asks a separate program what tools it has and then calls one). The functions move into an MCP server (the separate program that owns the tools and answers an agent's requests, rather than living inside the agent). Any compliant client can now use one shared implementation, whether that client is written in Python, TypeScript or something else. FastMCP (a Python framework for implementing MCP servers) powers the Python examples; the TypeScript examples use the MCP TypeScript SDK.

Client and server still need a transport (the wire that carries their messages). stdio, standard input/output, pipes text between one client and the server process it launches on the same machine; several clients therefore launch separate processes from the same server implementation. HTTP, Hypertext Transfer Protocol, lets several clients connect over a network to one server process. When a client asks what is available, the server returns a tool schema (a machine-readable description, usually expressed as JavaScript Object Notation or JSON, of a tool's name, purpose and required inputs). FastMCP builds that description from the registered Python function, so a function written once becomes both executable code and a discoverable contract.

from fastmcp import FastMCP

    """Return the current balance in pence."""
    return {"account_id": account_id, "balance_pence": 125_00}

if __name__ == "__main__":

In the capstone: this is where Eunomia's optional MCP server is born, and the Skill Reporter server follows the same shape. Lesson 23

Dynamic Tool Discovery & MCP Client Connection

The problem: in Eunomia, compliance can require a new tool immediately — for example, splitting "general savings question" from "regulated advice request" before any answer is shown. If the agent carries a hardcoded tool list, that urgent server-side tool cannot be used until the agent is edited, rebuilt and redeployed. Skill Reporter hits the same failure mode when a new report-validation or publishing-safety tool exists on the server but the running agent still cannot see it.

An MCP client (the part of the agent that connects to an MCP server, sends requests and reads replies) removes that last fixed list. It performs runtime discovery (finding which tools exist while the program is running, rather than fixing the list when the code is built). In Eunomia, this means newly deployed account-check, consent-check, or simulation-gate tools become callable without waiting for an app redeploy. In Skill Reporter, newly deployed report-quality and publish-policy tools become callable the same way. The client opens a session (the live connection and context used for discovery and calls) and begins it with a handshake (the opening initialize exchange in which client and server agree on a protocol version), then asks for the current tools.

The reply is a tool manifest (the server's list of each tool's name, description and input schema). A production client follows pagination until it has every page, then converts the complete manifest into definitions the large language model (the AI model that selects and calls tools), or LLM, can see. When the model selects one, a long-lived client sends the call through the still-open session. The short excerpts below demonstrate discovery only: both deliberately close after reading the first page, so they must not be used as the owner of an agent-lifetime session.

from mcp import ClientSession, StdioServerParameters
from mcp.client.stdio import stdio_client

async def discover_tools() -> list[str]:
    params = StdioServerParameters(command="python", args=["eunomia_server.py"])
    async with stdio_client(params) as (read, write):
        async with ClientSession(read, write) as session:
            await session.initialize()
            manifest = await session.list_tools()
            return [tool.name for tool in manifest.tools]
import { Client } from "@modelcontextprotocol/sdk/client/index.js";
import { StdioClientTransport } from "@modelcontextprotocol/sdk/client/stdio.js";

const client = new Client({ name: "eunomia-agent", version: "1.0.0" });
const transport = new StdioClientTransport({
  command: "python",
  args: ["eunomia_server.py"],
});

try {
  await client.connect(transport);
  const manifest = await client.listTools();
  const toolNames: string[] = manifest.tools.map((tool) => tool.name);
} finally {
  await client.close();
}

HANDSHAKE → ASK THE SERVER WHAT EXISTS NOW → CONVERT ITS MANIFEST FOR THE LLM → CALL THE SELECTED TOOL

A real finding worth knowing: the two SDKs (software development kits, meaning the official client libraries) manage connection lifetime differently. Python ties the session to an async with block; TypeScript needs an explicit close call. Discovery helpers such as those above cannot later call a selected tool because they close before returning. An agent therefore needs a long-lived owner that keeps the session open through discovery and calls, follows every manifest page, and closes only during shutdown.
In the capstone: Eunomia's own service deliberately keeps a fixed, reviewed set of three capabilities, because each one is part of a gated release. Runtime discovery applies to the other approved hosts that consume Eunomia's optional MCP server (building on the server from Lesson 6), and Skill Reporter's consumers use the same long-lived pattern against its server. Each MCP client connects at startup, reads every page of the current manifest, builds its toolset and keeps that session available for calls until shutdown, so a consumer picks up a new server tool without its own redeploy. Lesson 32

MCP Real-Time Resource Subscriptions

The problem: discovering tools at startup solves a changing catalogue, but Eunomia still needs fresh customer state during the conversation — balance, goal progress, and eligibility facts that can change after a deposit or profile update. Polling for those changes wastes calls and can leave Eunomia speaking from stale data. Skill Reporter has the same issue for report-ready state and policy updates during an active publishing workflow.

In MCP, a resource (readable data exposed by the server at an address, rather than an action to perform) might live at eunomia://accounts/123/balance. That address is a Uniform Resource Identifier, or URI (the name of a particular MCP resource). The simplest way to watch it is polling (asking the same question again and again on a timer to see if the answer changed), but most requests return “no” and the client can remain stale until the next timer fires.

A subscription (a standing request asking the server to report whenever a named resource changes) reverses that flow. On a deposit, the server sends a notification (a one-way message that expects no reply, here saying that a resource address was updated). The client reads the resource once and receives the fresh balance without a loop of empty checks. A multi-client server must record subscribed URIs separately for each live session, remove them on unsubscribe or disconnect, and notify only the relevant sessions.

The excerpts below isolate the update mechanism for one connected client. They do not implement production subscription routing: the Python call targets the session that invoked the tool, and the TypeScript set assumes exactly one connection.

from fastmcp import Context, FastMCP
from pydantic import AnyUrl

mcp = FastMCP("Eunomia")
balances: dict[str, int] = {"123": 125_00}

@mcp.resource("eunomia://accounts/{account_id}/balance")
async def balance(account_id: str) -> str:
    return str(balances[account_id])

@mcp.tool
async def record_deposit(account_id: str, pence: int, ctx: Context) -> str:
    balances[account_id] += pence
    uri = AnyUrl(f"eunomia://accounts/{account_id}/balance")
    await ctx.session.send_resource_updated(uri)
    return "deposit recorded"

const server = new McpServer(

  { capabilities: { resources: { subscribe: true } } },

const subscribedUrisForThisConnection = new Set<string>();
server.server.setRequestHandler(SubscribeRequestSchema, async (request) => {
  subscribedUrisForThisConnection.add(request.params.uri);
  return {};

async function balanceChanged(uri: string): Promise<void> {
  if (subscribedUrisForThisConnection.has(uri)) {

POLLING REPEATS EMPTY CALLS AND CAN BE STALE; A SUBSCRIPTION PUSHES ONE ADDRESS UPDATE, THEN THE CLIENT READS ONCE

A resource update is a signal, not a durable event log. Subscriptions improve live responsiveness; they do not guarantee that a disconnected client can recover every change it missed.
A real finding worth knowing: the TypeScript excerpt is a handler fragment layered onto Lesson 6's connected server; by itself it omits the transport connection bootstrap and is not standalone. The notification contains only the resource's address, not its new value, so the client must perform a second read. Nothing replays an update that happened before subscription setup or while the connection was down; it is simply lost. The one-client excerpts above are not sufficient for a shared network server: that version also needs per-session subscribe and unsubscribe handling, disconnect cleanup, a resource-read handler and dispatch only to sessions subscribed to the changed URI. Subscription APIs vary between SDK versions, so the installed version and transport must be checked before the design relies on them.
In the capstone: Eunomia's read-only first release does not subscribe to a customer's balance or savings-goal progress: each turn reads a fresh snapshot through readSnapshot and freezes it as evidence. Subscriptions appear only at the optional MCP server, where a host can be told that the catalogue version changed and then re-read it, while a turn already in progress keeps its pinned catalogue version. Skill Reporter applies the same subscription pattern to report-ready and policy-update resources so publication decisions use fresh state instead of stale polling snapshots.
Lesson 33

Dynamic Tool Synthesis & Runtime Registration

The problem: Eunomia can receive customer questions that need a narrow helper tool that does not exist yet (for example, a specific savings projection transform). If every tool must be prewritten, discovery can only confirm the gap and the customer flow stalls until a developer ships a new release. Skill Reporter encounters the same stall when a report-formatting helper is missing in the middle of a reporting run.

Tool synthesis (having an AI or code generator write the source of a new tool function instead of a human writing it) can fill narrow, low-risk gaps. In Eunomia, that means bounded read-only helpers such as calculations or formatting, never money movement or customer-record mutation. Lesson 48

Dynamic Tool Schema Introspection for Runtime-Registered Tools

The problem: an agent can now discover old and newly synthesised tools, but discovery alone does not prove that the arguments it sends are valid. In Eunomia, malformed arguments can hit account-scoped or simulation-gated financial logic with unclear failures; in Skill Reporter, malformed arguments can reach report-generation or publish-policy tools and fail too late. Without a local checker, both systems push bad input into critical paths instead of stopping early with a repairable error.

Every manifest carries JSON Schema (a standard, written in JSON, that describes what data must look like, including field types and which fields are required). The client uses introspection (examining a description at runtime to learn its structure) to turn that advertised schema into executable validation before making a call.

Python and TypeScript use Pydantic / Zod (validation libraries for Python and TypeScript respectively, which reject data that does not match a declared shape and return clear errors). Here the declaration is not handwritten: the converter creates a dynamic model (a validation class or schema object built by code while the program runs). Valid arguments proceed to the server; invalid ones become a structured error the language model can use to repair its next attempt.

The converters below are deliberately incomplete sketches for a small flat subset. They do not preserve all JSON Schema semantics and must not be treated as production validation.

Lesson 14

Hybrid Search: Dense + Sparse Retrieval

The problem: meaning-only search can answer “what's the rate on the 95-day notice account?” with a different notice product that merely sounds similar. Exact-word search has the opposite weakness: it can miss “how long do I have to wait to get my money out?” because the customer never used the formal words “notice period.” A dependable fintech retrieval layer must understand both meaning and exact product language. Skill Reporter has the same requirement when users ask in plain language but the catalogue stores formal skill names and versioned tags.

Dense retrieval (search by meaning, where each passage becomes a long list of numbers and passages with similar meanings sit close together) handles everyday descriptions. That list is an embedding (a numeric fingerprint of what a piece of text means, produced by a model). Dense retrieval can connect “wait to get my money out” with a passage about a withdrawal notice period even when the words differ.

Sparse retrieval (classic keyword search that scores exact query words, with rare words receiving more weight), commonly implemented with BM25 (the standard formula for that keyword score), protects exact identifiers such as “95-day.” The dense branch searches a vector index (a store organised by meaning fingerprints); the sparse branch uses a tokenizer (a component that splits text into searchable terms). Each returns its top K (the highest-ranked K results). The two searches then need score fusion (combining two result lists into one final ranking).

The introductory baseline below divides each branch by its highest score before applying a weight. This max-score normalisation (scaling one result list by its largest observed score) makes the scales comparable for a small example, but it is sensitive to which candidates happen to be present and gives a one-result branch its full weight. Lesson 49 replaces it with rank-based RRF for the production design, and Lesson 51 consumes that fused retrieval output in its grounding check.

from collections import defaultdict
from typing import TypeAlias

Ranked: TypeAlias = list[tuple[str, float]]

def fuse_scores(dense: Ranked, sparse: Ranked) -> Ranked:
    fused: defaultdict[str, float] = defaultdict(float)
    for results, weight in ((dense, 0.6), (sparse, 0.4)):
        if not results:
            continue
        peak = max(score for _, score in results)
        if peak <= 0:
            raise ValueError("branch scores must include a positive value")
        for document_id, score in results:
            fused[document_id] += weight * score / peak
    return sorted(fused.items(), key=lambda item: item[1], reverse=True)

print(fuse_scores([("notice", 0.82)], [("notice", 12.4), ("fixed", 9.1)]))
type ScoredResult = { documentId: string; score: number };

function fuseScores(
  dense: ScoredResult[],
  sparse: ScoredResult[],
): ScoredResult[] {
  const fused = new Map<string, number>();
  for (const [results, weight] of [[dense, 0.6], [sparse, 0.4]] as const) {
    if (results.length === 0) continue;
    const peak = Math.max(...results.map(({ score }) => score));
    if (peak <= 0) throw new Error("branch scores must include a positive value");
    for (const { documentId, score } of results) {
      fused.set(documentId, (fused.get(documentId) ?? 0) + weight * score / peak);
    }
  }
  return [...fused].map(([documentId, score]) => ({ documentId, score }))
    .sort((a, b) => b.score - a.score);
}

Lesson 21

Knowledge Graph Construction

The problem: similarity search can find a passage that sounds relevant, but it cannot reliably answer “which accounts held at this bank pay monthly interest?” That question asks how products, banks, rates, and payment schedules are connected. Those connections must be extracted and stored in a directly queryable form. Skill Reporter faces the same graph need when linking skills to roles, regions, confidence bands, and report sections.

A knowledge graph (a network of things joined by labelled links) turns prose into explicit facts. Each entity (one distinct thing, such as a product, bank, or interest rate, represented as a node) is connected by a relationship or edge (a labelled, one-directional link between two entities). The smallest useful graph fact is a triple (subject → relationship → object), such as “Easy Saver → HAS_RATE → 4.1%.”

The extraction step asks a model for structured triples rather than a summary. Before storage, names are normalised so “Easy Saver,” “Easy-Saver account,” and “the Easy Saver” can become one node. Relationship direction must also be validated: “Easy Saver → HELD_AT → Partner Bank A” is meaningful, while the reversed edge claims that a bank is held at an account. The small example focuses on normalisation and provenance; it does not implement that domain validation. Each stored edge retains its source document, passage, and extraction time. That provenance makes the edge source-linked; it does not independently prove that the source is true.

Lesson 28

Semantic Conversation Memory

The problem: a customer may say “I'm saving for a house deposit” and return to that goal twenty messages later. A chat system that keeps only the latest few turns has already discarded it. The agent needs to recall an earlier turn because it is relevant, not merely because it is recent. Skill Reporter has the same failure mode when a reporter's earlier constraint (for example "UK-only roles" or "weekly summary format") is dropped mid-session.

A model can read only its context window (the maximum number of tokens it can consider at once; anything outside that limit is invisible). Sliding window memory (keeping only the last N messages and dropping the rest) controls that limit but forgets long-running goals. Semantic memory (storing past turns as embeddings, or meaning fingerprints, so they can be searched by meaning rather than position) lets the current message retrieve a relevant statement from much earlier in the conversation.

Relevance alone is not enough when a customer changes their mind. Recency weighting (giving newer memories a small ranking boost) helps a recent correction outrank an older, equally relevant preference. Similarity search (ranking stored memories by closeness of meaning) selects older turns, while prompt assembly (combining chosen memory with recent turns for the model) controls what is sent. The example stays within one conversation; cross-session retention additionally needs authenticated customer identity, consent, deletion rules, retention limits, and tenant isolation.

from dataclasses import dataclass
from datetime import datetime, timezone
from math import sqrt
from typing import Awaitable, Callable

@dataclass(frozen=True)
class Memory:
    text: str
    created_at: datetime
    embedding: list[float]
    embedding_model: str

def cosine_similarity(left: list[float], right: list[float]) -> float:
    if len(left) != len(right) or not left:
        raise ValueError("embedding dimensions must match and be non-empty")
    left_norm = sqrt(sum(value * value for value in left))
    right_norm = sqrt(sum(value * value for value in right))
    if left_norm == 0 or right_norm == 0:
        raise ValueError("embeddings must have non-zero magnitude")
    return sum(a * b for a, b in zip(left, right)) / (left_norm * right_norm)

async def recall(query: str, memories: list[Memory], embedding_model: str,
                 embed: Callable[[str], Awaitable[list[float]]]) -> list[Memory]:
    query_vector = await embed(query)
    now = datetime.now(timezone.utc)
    def score(memory: Memory) -> float:
        if memory.embedding_model != embedding_model:
            raise ValueError("embedding model mismatch")
        similarity = cosine_similarity(query_vector, memory.embedding)
        recency = 1 / (1 + max(0, (now - memory.created_at).days))
        return similarity + 0.05 * recency
    return sorted(memories, key=score, reverse=True)[:3]
interface Memory {
  text: string;
  createdAt: Date;
  embedding: number[];
  embeddingModel: string;
}

type Embed = (text: string) => Promise<number[]>;

function cosineSimilarity(left: number[], right: number[]): number {
  if (left.length === 0 || left.length !== right.length) {
    throw new Error("embedding dimensions must match and be non-empty");
  }
  const dot = left.reduce((sum, value, index) => sum + value * right[index], 0);
  const leftNorm = Math.sqrt(left.reduce((sum, value) => sum + value * value, 0));
  const rightNorm = Math.sqrt(right.reduce((sum, value) => sum + value * value, 0));
  if (leftNorm === 0 || rightNorm === 0) throw new Error("embeddings must have non-zero magnitude");
  return dot / (leftNorm * rightNorm);
}

async function recall(query: string, memories: Memory[],
  embeddingModel: string, embed: Embed): Promise<Memory[]> {
  const queryVector = await embed(query);
  const score = (memory: Memory): number => {
    if (memory.embeddingModel !== embeddingModel) throw new Error("embedding model mismatch");
    const similarity = cosineSimilarity(queryVector, memory.embedding);
    const ageDays = Math.max(0, (Date.now() - memory.createdAt.getTime()) / 86_400_000);
    return similarity + 0.05 / (1 + ageDays);
  };
  return [...memories].sort((a, b) => score(b) - score(a)).slice(0, 3);
}

Lesson 34

Graph-Based Entity Memory & Relationship Resolution

The problem: a customer says “my partner's ISA,” “the joint account,” and later “that one I opened last year.” The agent must decide whether each phrase points to something already known or introduces something new. A pile of disconnected notes cannot reliably support that decision or preserve how a fact changed. Skill Reporter needs the same entity resolution when users alternate between aliases like “that backend Rust track,” “the infra report,” and a formal skill identifier.

Entity memory (a running record of the specific people, accounts, and goals mentioned so far, together with facts about each) gives the conversation a stable set of things. Entity resolution (deciding whether a new phrase such as “the joint one” refers to an existing entry or a new one) connects each mention to that set. The resolver can use names, ownership, account type, and nearby conversation context, but uncertain matches should remain uncertain rather than being forced.

Changing facts need fact supersession (marking an older fact out of date when a new fact replaces it, instead of deleting or silently overwriting it). Every version also carries provenance (where and when the fact came from, so it can later be traced and checked). The small resolver below matches known aliases, creates a new entity when none match, and refuses an ambiguous match; production matching can add account type and conversation context without removing that ambiguity branch.

from dataclasses import dataclass, replace
from datetime import datetime

@dataclass(frozen=True)
class Entity:
    entity_id: str
    aliases: frozenset[str]

@dataclass(frozen=True)
class Fact:
    entity_id: str
    key: str
    value: str
    observed_at: datetime
    source_turn: int
    current: bool = True

def normalise_mention(text: str) -> str:
    return " ".join(text.casefold().split())

def resolve_or_create(mention: str, entities: list[Entity],
                      new_entity_id: str) -> tuple[str, list[Entity]]:
    target = normalise_mention(mention)
    matches = [entity for entity in entities
               if target in {normalise_mention(alias) for alias in entity.aliases}]
    if len(matches) == 1:
        return matches[0].entity_id, entities
    if len(matches) > 1:
        raise ValueError("ambiguous entity mention")
    created = Entity(new_entity_id, frozenset({mention}))
    return created.entity_id, [*entities, created]

def supersede(facts: list[Fact], new_fact: Fact) -> list[Fact]:
    history = [replace(fact, current=False)
               if fact.entity_id == new_fact.entity_id and fact.key == new_fact.key
               else fact for fact in facts]
    return [*history, replace(new_fact, current=True)]
interface Entity {
  entityId: string;
  aliases: string[];
}
interface Fact {
  entityId: string;
  key: string;
  value: string;
  observedAt: Date;
  sourceTurn: number;
  current: boolean;
}

const normaliseMention = (text: string): string =>
  text.toLowerCase().trim().split(/\s+/).join(" ");

function resolveOrCreate(mention: string, entities: Entity[], newEntityId: string): {
  entityId: string; entities: Entity[];
} {
  const target = normaliseMention(mention);
  const matches = entities.filter((entity) =>
    entity.aliases.some((alias) => normaliseMention(alias) === target));
  if (matches.length === 1) return { entityId: matches[0].entityId, entities };
  if (matches.length > 1) throw new Error("ambiguous entity mention");
  const created = { entityId: newEntityId, aliases: [mention] };
  return { entityId: created.entityId, entities: [...entities, created] };
}

function supersede(facts: Fact[], newFact: Fact): Fact[] {
  const history = facts.map((fact) =>
    fact.entityId === newFact.entityId && fact.key === newFact.key
      ? { ...fact, current: false }
      : fact,
  );
  return [...history, { ...newFact, current: true }];
}

Lesson 49

Updating Search Indexes Safely with RRF

The problem: rebuilding an entire search index because one interest rate changed is slow and wasteful. Merely adding the new version is worse: the old rate remains searchable, so the agent can still quote withdrawn information. An update must remove precisely what became stale, add precisely what changed, and preserve fair hybrid ranking. Skill Reporter has the same correctness risk when one skill definition or demand tier changes but stale versions remain retrievable.

Search works on a chunk (a small passage cut from a larger document) rather than a whole product sheet. Cache invalidation (removing stored results that are no longer true so they cannot be served again) starts with a manifest that records every chunk owned by a document. A content hash (a short fingerprint calculated from a chunk's text) makes a text change overwhelmingly likely to produce a new ID; an occurrence key keeps identical repeated chunks distinct. Comparing the old and new manifests identifies unchanged chunks to keep, stale chunks to delete, and new chunks to index.

The update must apply to both the dense index (the meaning-based store) and sparse index (the exact-word store) as one atomic commit, so readers see either the old version or the new version rather than a partial mixture. Content-derived IDs do not replace ownership metadata: the old document manifest is what makes stale IDs discoverable.

The query side uses Reciprocal Rank Fusion, or RRF (merging ranked lists from each result's position rather than its raw score). Rank starts at 1. Each result earns 1 ÷ (k + rank) from each list, and those contributions are added; k is a smoothing constant (a value that limits how sharply scores fall by rank), commonly 60. Dense and keyword scores can live on completely different scales because RRF never compares them directly.

from collections import defaultdict
from hashlib import sha256
from typing import Protocol

Manifest = dict[str, str]

class IndexTransaction(Protocol):
    def delete_from_both(self, chunk_id: str) -> None: ...
    def upsert_into_both(self, chunk_id: str, text: str) -> None: ...
    def commit(self, manifest: Manifest) -> None: ...

def content_id(document_id: str, occurrence: str, text: str) -> str:
    digest = sha256(text.encode("utf-8")).hexdigest()[:12]
    return f"{document_id}:{occurrence}:{digest}"

def replace_document(document_id: str, old_manifest: Manifest,
                     chunks: dict[str, str], transaction: IndexTransaction) -> Manifest:
    new_manifest = {occurrence: content_id(document_id, occurrence, text)
                    for occurrence, text in chunks.items()}
    old_ids, new_ids = set(old_manifest.values()), set(new_manifest.values())
    for stale_id in old_ids - new_ids:
        transaction.delete_from_both(stale_id)
    for occurrence, new_id in new_manifest.items():
        if new_id not in old_ids:
            transaction.upsert_into_both(new_id, chunks[occurrence])
    transaction.commit(new_manifest)
    return new_manifest

def reciprocal_rank_fusion(rankings: list[list[str]], k: int = 60) -> list[str]:
    scores: defaultdict[str, float] = defaultdict(float)
    for ranking in rankings:
        for rank, chunk_id in enumerate(ranking, start=1):
            scores[chunk_id] += 1 / (k + rank)
    return sorted(scores, key=lambda chunk_id: (-scores[chunk_id], chunk_id))

function replaceDocument(documentId: string, oldManifest: Manifest,
  chunks: Record<string, string>, transaction: IndexTransaction): Manifest {
  const newManifest = Object.fromEntries(Object.entries(chunks).map(([occurrence, text]) =>
    [occurrence, contentId(documentId, occurrence, text)]));
  const oldIds = new Set(Object.values(oldManifest));
  const newIds = new Set(Object.values(newManifest));
  for (const staleId of oldIds) {
    if (!newIds.has(staleId)) transaction.deleteFromBoth(staleId);
  }
  for (const [occurrence, newId] of Object.entries(newManifest)) {
    if (!oldIds.has(newId)) transaction.upsertIntoBoth(newId, chunks[occurrence]);
  }
  transaction.commit(newManifest);
  return newManifest;
}

function reciprocalRankFusion(rankings: string[][], k = 60): string[] {
  const scores = new Map<string, number>();
  for (const ranking of rankings) {
    ranking.forEach((chunkId, index) => {
      scores.set(chunkId, (scores.get(chunkId) ?? 0) + 1 / (k + index + 1));
    });
  }
  return [...scores].sort((a, b) => b[1] - a[1] || a[0].localeCompare(b[0]))
    .map(([chunkId]) => chunkId);
}

Combining Passage and Graph Retrieval

The problem: vector search can find a convincing passage from the wrong product, while a knowledge graph can confirm that it contains a relationship but does not contain the explanatory text a customer needs. “Sounds right” is not enough. A factual answer should require a matching passage and a source-linked graph relationship, and disagreement must stop the answer rather than invite a guess. Skill Reporter needs the same agreement rule so a report claim is published only when text evidence and graph facts both align.

RAG (Retrieval-Augmented Generation: having a model write from documents fetched at question time rather than from facts absorbed during training) supplies the passage. Graph-RAG (RAG that also checks a knowledge graph for explicit relationships) supplies a structured representation. Together they improve grounding (ensuring every factual claim can be traced to a specific retrieved source).

The central rule is cross-representation consistency (checking that a retrieved passage and a graph edge agree before using either). Both branches compare a shared canonical product ID, bank ID, and notice period rather than display names. Agreement shows that two representations of the source are consistent; it is not independent verification when both came from the same product sheet. Independent verification requires a separate authoritative source, such as a live product system or versioned source of record.

An entity link (the mapping from a passage mention to a graph entity) performs the join (matching records across the two representations). A mismatch or missing edge produces a decline or clarifying question and a review signal.

Lesson 9

Multi-Agent Hand-Off & Verification

The problem: if Eunomia evaluates its own draft, the same assumptions that produced the answer can approve it, allowing risky or unsupported guidance through with high confidence. Skill Reporter has the same self-review bias when one model both writes and judges report quality.

The smallest useful separation is a worker agent (the agent whose job is to produce the first draft) followed by an auditor agent (a separate agent with different instructions whose only job is to approve or reject that draft). The worker is encouraged to solve the customer's problem; the auditor is encouraged to look for reasons the proposed answer should not be sent. Those are deliberately different jobs.

The connection between them is a hand-off (the moment one agent passes its output to another as structured data rather than loose chat text). In this pattern, the auditor receives the worker's generated title, stack and code, then returns a verdict schema (a fixed decision form such as approved: true/false and reasons: [...]). A fixed form matters because trusted application code can check a known structure directly.

QUESTION → WORKER DRAFT → INDEPENDENT AUDITOR VERDICT → APPROVE, RETRY WITH REASONS, OR USE A SAFE FALLBACK

The workflow uses one worker call followed by one auditor decision, with bounded retry and a safe holding reply if approval never arrives. Malformed, missing or ambiguous approval must never count as permission.

Lesson 15

Multi-Agent Majority Voting

The problem: Eunomia can produce different outputs for the same prompt across runs, so one-shot decisions can accept unlucky variance. Skill Reporter faces the same instability in report scoring and recommendations unless agreement is measured across independent runs.

A swarm (a group of agents, often copies of the same agent, that receive the same task separately) turns one uncertain response into several responses. These responses can still share the same blind spots because they come from the same model and prompt. A consensus vote (choosing the answer that most agents gave instead of trusting any one agent) then selects the strongest shared result. This is useful for bounded decisions such as intent labels, risk categories or yes/no classifications; it is not a guarantee that the majority is correct.

Acceptance needs an agreement threshold (the minimum number of matching votes required before the system trusts a result, such as at least three of five votes). If agents can time out, a separate minimum-response rule should say how many must participate. Workers should return fixed labels whenever possible; treating free-form answers as equivalent can accidentally merge materially different amounts, currencies or risk categories. In Eunomia, labels might be regulated_advice, factual_account_query, and general_info. In Skill Reporter, labels might be high_demand_skill, emerging_skill, and low_signal. A tie must always produce “no winner” rather than depend on which item the program encounters first.

ONE TASK FANS OUT TO FIVE SEPARATE AGENTS → FIXED LABELS ARE VALIDATED → VOTES ARE TALLIED → THE AGREEMENT THRESHOLD ACCEPTS OR ESCALATES

The five agents must not copy one another's intermediate work, because then five votes merely repeat one initial mistake. Each submits a fixed final label without seeing the others' outputs. The tally accepts a unique winner only when that winner meets the configured agreement threshold; a tie or a winner with too few matching votes becomes an escalation or safe reply instead of a guessed result.

  answers: T[],
  minimumMatchingVotes = 3,
): T | null {
  const counts = new Map<T, number>()
  for (const answer of answers) {
    counts.set(answer, (counts.get(answer) ?? 0) + 1)

    .map(([answer]) => answer)

  return winners[0]
}

Lesson 18

Concurrent Sub-Agent Workflows

The problem: Eunomia can serialize work that could run in parallel, increasing response time even when subtasks are independent. Skill Reporter has the same latency penalty when independent report stages are forced through one worker path.

A sub-agent (a smaller agent assigned one well-defined piece of a larger task) lets the system divide the job by responsibility. The planner uses fan-out / fan-in (sending independent pieces to several sub-agents at once, then gathering their results back in one place). Because the checks do not depend on each other, they can use concurrency (allowing several pieces of work to be in progress at the same time rather than waiting for each to finish).

When all available results return, an aggregator (the step that combines separate sub-agent results into one final answer) builds a coherent draft. In the sequential version, total waiting time is roughly the sum of every check. In the concurrent version, network waits overlap, so total time can be closer to the slowest single check plus the cost of starting and combining the work. This does not by itself prove that CPU work ran simultaneously.

SEQUENTIAL WORK ADDS EVERY WAIT; CONCURRENT WORK FANS OUT AND OVERLAPS NETWORK WAITS, THEN FANS IN AT AN AGGREGATOR THAT PRESERVES PARTIAL RESULTS

Concurrent execution changes failure handling. A single timeout must not erase two useful successes. Each sub-agent therefore returns either a value or a clearly marked error, and the aggregator is told exactly which evidence is missing. It may produce a cautious partial draft, request the missing lookup again or stop, but it may not describe incomplete evidence as complete.

Lesson 36

Pub/Sub Agent Coordination

The problem: as Eunomia and Skill Reporter add specialized agents, direct peer-to-peer messaging creates brittle coupling and missed updates. Adding one agent can require rewiring many others, raising change risk and making responsibilities hard to reason about.

A message bus (a shared noticeboard to which agents post messages and from which agents read them instead of contacting one another directly) removes that web of direct one-to-one connections. The bus supports publish / subscribe, or pub/sub (a pattern in which agents publish messages to named topics and any agent subscribed to a topic receives them without the sender knowing who is listening). Lesson 9's worker and auditor are two of the agents whose messages now flow over this bus rather than being passed directly between them.

Each message is an event (a short, structured record that something happened, such as goal_updated). A real bus may deliver the same event more than once, so subscribers must make repeated delivery harmless. The in-memory set below suppresses a duplicate only when deliveries are sequential in one running process. It is not a general idempotency guarantee (a promise that repeating an operation has no additional effect): concurrent copies can both pass the check, a crash can occur after the audit but before the identifier is saved, and a restart clears the set. Stronger guarantees need durable atomic claim-and-complete state and a downstream operation designed for safe retries.

AGENTS PUBLISH STRUCTURED EVENTS TO TOPICS → THE MESSAGE BUS DECOUPLES SENDERS FROM RECEIVERS → SUBSCRIBERS PROCESS EVENTS AND HANDLE REPEATED DELIVERY EXPLICITLY

Decoupling lets a notification agent or audit log join later without changing the worker. It does not, however, create a saved history or a guaranteed delivery order. If an agent must recover older events, the system has to store them durably and send them again during recovery. The sample bus demonstrates routing only; it does not establish behavior for late subscribers, duplicates, delivery order or slow subscribers.

Lesson 45

Central Write Arbitration for Concurrent Write Hazards

The problem: when Eunomia or Skill Reporter agents update shared records concurrently, one write can overwrite another without warning. This silent conflict can corrupt customer or reporting state unless update ordering and conflict checks are explicit.

This is a concurrent write hazard (the risk that overlapping writes to the same resource leave it wrong or internally inconsistent). It often appears as a race condition (a bug whose result depends on which operation happens to finish first, making it intermittent and difficult to reproduce). Both agents can read version 3, calculate different updates, and then save in succession; the second save overwrites the first even though both calls reported success.

An arbiter (one coordination component that receives write requests for a shared resource) gives participating writers one controlled entrance. It can keep a separate queue for each record so requests for one record are handled in order. The correctness boundary, however, is the shared store's atomic version check, also called optimistic locking (one indivisible store operation that writes only if the record still has the expected version). A local queue is only an efficiency measure: another arbiter replica or a writer that bypasses it can still race. A request rejected by the store must re-read the latest record, reconsider its change and retry with the new version. The arbiter does not replace the worker/auditor hand-off from Lesson 9 or the bus-based coordination from Lesson 36; it adds a third guarantee — that concurrent writes to one shared record cannot silently overwrite each other.

OVERLAPPING WRITES CAN LOSE DATA; THE SHARED STORE MUST CHECK THE EXPECTED VERSION AND WRITE ATOMICALLY, WHILE STALE REQUESTS RE-READ BEFORE RETRYING

The arbiter need not make the business decision itself. Its narrower job is to submit the expected version and complete replacement value to an atomic store operation. A local queue can reduce conflicts for requests that reach one process, and requests for different records can still proceed concurrently, but the store must reject stale versions even when writes arrive through another process.

from typing import Any

    record_id: str

Lesson 8

Async Concurrency & Batch Processing

The problem: Eunomia often needs multiple independent checks before replying (balance, rates, goals, and recent transactions). Running those calls one by one makes the customer wait for avoidable latency. Skill Reporter has the same bottleneck when it gathers catalogue evidence, memory evidence, and policy evidence sequentially instead of in parallel.

Async (asynchronous code that can start a slow operation, do other work while it waits, and resume when the result arrives) lets independent calls overlap. That creates concurrency (several tasks making progress during the same period by taking turns whenever another task is waiting), rather than strict one-by-one execution. Put the independent requests into a batch (a group of requests launched together and collected as one set), then gather every outcome before composing the answer.

import asyncio
from collections.abc import Awaitable, Callable

async def run_batch(
    items: list[str], fetch: Callable[[str], Awaitable[str]], limit: int = 3
) -> list[str | Exception]:
    semaphore = asyncio.Semaphore(limit)

    async def limited(item: str) -> str:
        async with semaphore:
            return await fetch(item)

    return await asyncio.gather(*(limited(item) for item in items), return_exceptions=True)
type Result = { ok: true; value: string } | { ok: false; error: unknown };
async function runBatch(
  items: string[], fetchItem: (item: string) => Promise<string>, limit = 3
): Promise<Result[]> {
  const results: Result[] = new Array(items.length);
  let next = 0;
  async function worker(): Promise<void> {
    while (next < items.length) {
      const index = next++;
      try {
        results[index] = { ok: true, value: await fetchItem(items[index]) };
      } catch (error) {
        results[index] = { ok: false, error };
      }
    }
  }

  await Promise.all(Array.from({ length: limit }, () => worker()));
  return results;
}

ONE REQUEST → CONTROLLED PARALLEL CALLS → SETTLE EVERY RESULT → COMBINE WHAT SUCCEEDED AND EXPLAIN WHAT DID NOT

Unbounded concurrency merely replaces waiting with overload. A semaphore (a counter that permits only a fixed number of tasks to run at once) keeps a large batch from firing thousands of calls together. The useful result is not “everything succeeded”; it is a complete ledger of which calls succeeded and which failed, so the agent can still answer from the available facts.

A real finding worth knowing: the default “wait for all” helper in either language rejects the entire batch when one call fails. The other calls may continue in the background, but their results are never collected. Use the “settle all” variant so every call becomes an explicit success or failure, and put a concurrency cap in place before launching a large batch.
In the capstone: Eunomia's evidence planner runs the capability calls a question type needs with overlap, while a semaphore admits only three calls at once. Latency is therefore set by the longest call under that cap, rather than the sum of every call, and a missing source is recorded in the bundle so the answer sequence steps down instead of the whole turn failing, while a malformed source stops the turn safely before any model call. Skill Reporter uses the same capped fan-out to collect report evidence without saturating its dependencies.
Lesson 27

Self-Healing Code & Auto-Repair Loops

The problem: Eunomia can generate a savings-projection helper that looks correct but crashes on edge cases. Without an automatic repair loop, an operator must manually feed each crash back to the model. Skill Reporter faces the same operational drag when generated report-transformation code fails on real input variations.

A safe repair system runs generated code in a sandbox (an isolated environment with no access to real files, networks or customer data, and with strict time and memory limits). If the run fails, it captures the stack trace (the crash report showing which line failed and why) and starts a repair loop (run, capture the error, ask for a correction, then run again up to a fixed attempt limit).

async def repair_until_valid(code: str, attempts: int = 3) -> str:

GENERATE → RUN IN A LOCKED-DOWN SANDBOX → PROVE CORRECTNESS → REPAIR WITH THE ERROR, OR STOP AFTER A FIXED LIMIT

The decisive check is an acceptance test (a test written before generation that defines the correct result). A process exit code (the numeric status a program returns when it stops) can prove only that the program stopped without reporting an error; it cannot prove the answer is right. The loop must also terminate runaway child processes (subprocesses that outlive or ignore the parent operation's limit) when its time limit expires, although Python and TypeScript require different process-control details to do that reliably.

“Self-healing” does not mean unlimited retries or permission to run generated code on the host. It means a small, observable number of attempts inside a hostile-by-default sandbox, followed by a safe refusal.
A real finding worth knowing: a model may appear to repair a crash by wrapping the failing line in a catch-all that hides the error. The script then exits cleanly while returning the wrong answer. Count a repair as successful only when a real acceptance test passes, never merely because the crash disappeared. Also verify that the language-specific timeout path actually kills a runaway child process.
In the capstone: Eunomia's first release generates no code and calculates no projections at runtime; Part X keeps this code-repair theme outside the serving path. If generated savings-projection code is added later, it is repaired and rerun only inside a sandbox, and if the acceptance test still fails when the attempt limit is reached, Eunomia says it cannot calculate the projection right now rather than presenting a plausible but wrong number. Lesson 29

Token Bucket Rate Limiting

The problem: concurrency makes Eunomia faster, but it can also burst model and upstream calls hard enough to hit provider limits during customer peaks. The result is avoidable 429 failures on valid requests. Skill Reporter sees the same quota spike risk during scheduled reporting windows unless outbound pace is controlled.

A rate limit (the maximum number of requests, or amount of model text, accepted during a time window) is commonly enforced with HTTP 429 (the standard “Too Many Requests” response). Rather than waiting to be rejected, the agent can pace itself with a token bucket (a container of request permits that has a fixed capacity, refills steadily, and makes a request wait when no permit is available). These permits are not the text tokens used to measure model input and output.

import asyncio
from time import monotonic

class TokenBucket:
    def __init__(self, capacity: int, rate: float) -> None:
        if capacity <= 0 or rate <= 0:
            raise ValueError("capacity and rate must be positive")
        self.capacity, self.rate, self.tokens = capacity, rate, float(capacity)
        self.updated = monotonic()
        self.lock = asyncio.Lock()

    async def acquire(self) -> None:
        while True:
            async with self.lock:
                now = monotonic()
                self.tokens = min(self.capacity, self.tokens + (now - self.updated) * self.rate)
                self.updated = now
                if self.tokens >= 1:
                    self.tokens -= 1
                    return
                delay = (1 - self.tokens) / self.rate
            await asyncio.sleep(delay)
class TokenBucket {
  private tokens: number;
  private updated = performance.now();
  constructor(private capacity: number, private ratePerSecond: number) {
    if (capacity <= 0 || ratePerSecond <= 0) {
      throw new RangeError("capacity and rate must be positive");
    }
    this.tokens = capacity;
  }
  async acquire(): Promise<void> {
    for (;;) {
      const now = performance.now();
      const elapsed = (now - this.updated) / 1_000;
      this.tokens = Math.min(this.capacity, this.tokens + elapsed * this.ratePerSecond);
      this.updated = now;
      if (this.tokens >= 1) {
        this.tokens -= 1;
        return;
      }
      await new Promise((resolve) => setTimeout(resolve, ((1 - this.tokens) / this.ratePerSecond) * 1_000));
    }
  }
}

REQUESTS TAKE PERMITS FROM A FINITE BUCKET → THE BUCKET REFILLS STEADILY → EXCESS CALLS WAIT LOCALLY INSTEAD OF REACHING HTTP 429

Refill calculations must use a monotonic clock (a timer that only moves forward and is unaffected by corrections to the computer's calendar time). Capacity allows a small, intentional burst; refill speed controls the sustained rate. When no permit is available, these simple implementations make callers sleep and compete again; a separate first-in, first-out queue is needed when arrival-order fairness matters.

A real finding worth knowing: a bucket refilled from wall-clock time (calendar time that can jump when the system clock is corrected) can grant a flood of permits or stop refilling when that clock is corrected. Use a monotonic clock. Separately, a request-count bucket cannot enforce a provider's text-volume limit: a few very long prompts may still cause 429 responses, so model-text limits need their own weighted accounting (charging each request in proportion to the text volume it consumes).
In the capstone: when many customers ask Eunomia questions at once, a bucket inside the model gateway keeps model calls beneath the provider's accepted pace. Customers may wait briefly inside Eunomia, but these snippets do not guarantee first-in, first-out service; add a real queue when that fairness is required. Skill Reporter uses the same token-bucket pacing to avoid upstream quota spikes during reporting cycles.
Lesson 35

Cross-Agent Deadlock Prevention & Circuit Breakers

The problem: when a dependency starts failing, Eunomia can keep calling it and waiting for timeouts, spreading slowdown across customer sessions. At the same time, cooperating agents can each wait for the other and deadlock. Skill Reporter has the same dual risk when report assembly depends on services that are failing or waiting on each other.

A cascading failure (one broken service making its callers slow or broken until the damage spreads through the system) is contained by a circuit breaker (a guard that counts failures and temporarily rejects new calls after a threshold). Its normal closed state passes calls through. Its open state fails immediately during a cool-down, and its half-open state (a cautious recovery state that admits one test request) decides whether normal traffic is safe again.

from collections.abc import Awaitable, Callable
from time import monotonic
class CircuitBreaker:
    def __init__(self, threshold: int = 5, cooldown: float = 10) -> None:
        self.threshold, self.cooldown = threshold, cooldown
        self.failures, self.opened_at, self.probing = 0, 0.0, False
    async def call(self, operation: Callable[[], Awaitable[str]]) -> str:
        now = monotonic()
        if self.failures >= self.threshold:
            if now - self.opened_at < self.cooldown or self.probing:
                raise RuntimeError("circuit open")
            self.probing = True
        try:
            value = await operation()
        except Exception:
            self.failures += 1
            self.opened_at, self.probing = now, False
            raise
        self.failures, self.probing = 0, False
        return value
class CircuitBreaker {
  private failures = 0;
  private openedAt = 0;
  private probing = false;
  async call(operation: () => Promise<string>): Promise<string> {
    const now = performance.now();
    if (this.failures >= 5) {
      if (now - this.openedAt < 10_000 || this.probing) throw new Error("circuit open");
      this.probing = true;
    }
    try {
      const value = await operation();
      this.failures = 0; this.probing = false;
      return value;
    } catch (error) {
      this.failures += 1; this.openedAt = now; this.probing = false;
      throw error;
    }
  }
}

FAILURES TRIP THE BREAKER CLOSED → OPEN → ONE HALF-OPEN PROBE; TIMEOUTS AND FIXED ORDERING BREAK SIMPLE CROSS-AGENT WAITS

Circuit breakers contain calls to unhealthy dependencies; a deadlock (two or more workers each waiting for something held by another, so none can continue) needs a different guard: bounded waits, release on timeout, and one fixed ordering (a shared rule that every worker follows when acquiring several resources). These measures are deliberately simple. They prevent an indefinite hang even before the system gains the full distributed detector introduced in Lesson 46.

A real finding worth knowing: a naive half-open implementation often allows every request arriving at the recovery moment through, even though it intends to allow “the next request.” That surge can knock the recovering service down again. The half-open probe must be protected so one request is in flight (started but not yet completed) per process. A fleet-wide single probe requires a shared atomic store or distributed lease; production breakers also tag state generations so a late completion from an older generation cannot reset newer state.
In the capstone: Eunomia's model gateway keeps a circuit breaker per provider: after repeated failures it stops calling that provider for a cool-down and moves to the next one in the chain, or the answer steps down a step, so customers do not wait through repeated timeouts. A store that keeps failing makes /readyz report the instance unready. The first release has no cooperating agents that could wait on each other, so this lesson's wait-graph half is not needed yet. Skill Reporter mirrors this breaker discipline for report and policy services.
Lesson 37

Autonomous Model Cascades & Cost-Aware Escalation

The problem: Eunomia cannot run every request on the most expensive model without unsustainable cost, but routing all requests to a cheap model degrades quality on regulated or high-risk questions. Skill Reporter has the same trade-off: routine summaries are cheap, but high-stakes publication checks need stronger reasoning.

A model cascade (an ordered sequence of models from cheapest to most capable, tried until an answer passes) starts small and escalates only when necessary. After each attempt, a quality gate (an automatic, programmatic check that decides whether an answer is acceptable) either returns the answer or triggers escalation (sending the same task to the next, more capable model).

from collections.abc import Awaitable, Callable

Model = Callable[[str], Awaitable[dict[str, object]]]

class RetryableModelError(Exception):
    pass

async def run_cascade(question: str, models: list[Model]) -> dict[str, object]:
    failures: list[str] = []
    for model in models:
        try:
            answer = await model(question)
        except RetryableModelError as error:
            failures.append(type(error).__name__)
            continue
        if quality_gate(answer):
            return answer
    raise RuntimeError(f"no model produced an acceptable answer ({len(failures)} unavailable)")

def quality_gate(answer: dict[str, object]) -> bool:
    citations = answer.get("citations")
    return (
        isinstance(answer.get("text"), str)
        and isinstance(citations, list)
        and all(isinstance(citation, str) for citation in citations)
    )
type Answer = { text: string; citations: string[] };
type Model = (question: string) => Promise<unknown>;
class RetryableModelError extends Error {}

async function runCascade(question: string, models: Model[]): Promise<Answer> {
  let unavailable = 0;
  for (const model of models) {
    try {
      const answer = await model(question);
      if (qualityGate(answer)) return answer;
    } catch (error) {
      if (!(error instanceof RetryableModelError)) throw error;
      unavailable += 1;
    }
  }
  throw new Error(`no model produced an acceptable answer (${unavailable} unavailable)`);
}

function qualityGate(value: unknown): value is Answer {
  if (typeof value !== "object" || value === null) return false;
  const answer = value as Partial<Answer>;
  return (
    typeof answer.text === "string" &&
    Array.isArray(answer.citations) &&
    answer.citations.every((citation) => typeof citation === "string")
  );
}

Only failures that the model adapter classifies as retryable should advance the cascade. Cancellation, authentication errors, and policy failures must propagate instead of being swallowed; retryable failures should be recorded for observability.

TRY THE CHEAP MODEL → CHECK THE OUTPUT → RETURN AN ACCEPTABLE ANSWER OR ESCALATE HARD CASES → FALL BACK SAFELY IF NO ATTEMPT PASSES

The relevant measure is cost per answer (the combined cost of every model attempted for one question, including rejected attempts). A cascade saves money only when the first model handles enough traffic and the gate is accurate enough to avoid needless escalation. Reliable gates inspect facts the program can verify, such as schema validity (whether the output has the required fields and value types), required fields, and whether cited figures match source data. The snippets demonstrate shape checks only; source-backed factual checks are still required before treating an answer as verified.

A model grading its own confidence is not an independent check. Confidence is generated text too, and a wrong answer can be delivered with complete certainty.
A real finding worth knowing: asking the cheap model “are you confident?” makes a poor quality gate because models can report high confidence on wrong answers. Program-verifiable checks are much stronger. A gate that is too strict creates the opposite failure: almost every question reaches the large model, so the cascade costs more than sending each question directly there.
In the capstone: Eunomia turns this into a cascade of answer modes rather than model sizes. “What is my balance?” is answered by a template from the frozen snapshot with no model at all; questions that need wording go to the composed step; and if a composed draft fails the objective gate (the verifier), Eunomia hands the customer to a person. Inside the composed step, the gateway's ordered provider chain handles the choice between providers. Skill Reporter uses the same gated fallback policy for report-quality checks.
Lesson 46

Distributed Deadlock Detection & Recovery

The problem: timeouts can break circular waits in Eunomia, but only after wasting the full timeout budget and without proving whether the system was truly deadlocked or just slow. As Eunomia spans more services, no single worker sees the full wait chain. Skill Reporter inherits the same visibility gap once report generation, validation, and publishing are distributed.

A distributed system (work spread across separate processes or machines that communicate over a network) needs a shared picture. Each worker reports waits to a wait-for graph (a live map whose dots are agents and whose arrow from A to B means “A is waiting for B”). Cycle detection (walking those arrows to find a path that returns to its starting point) can then identify a deadlock as soon as its final arrow appears.

The following snippets are single-process pseudocode for the cycle walk, limited to one active dependency per agent. A production distributed detector must apply edge updates atomically to a shared registry, support every simultaneous wait, attach an expiry to each edge, and remove edges on every exit path.

waits_for: dict[str, str] = {}

async def register_wait(agent: str, dependency: str) -> None:
    waits_for[agent] = dependency
    seen: set[str] = set()
    current = agent

    while current in waits_for:
        if current in seen:
            victim = min(seen, key=retry_cost)
            waits_for.pop(victim, None)
            await cancel_victim(victim)
            return
        seen.add(current)
        current = waits_for[current]

async def stop_waiting(agent: str) -> None:
    waits_for.pop(agent, None)
const waitsFor = new Map<string, string>();
async function registerWait(agent: string, dependency: string): Promise<void> {
  waitsFor.set(agent, dependency);
  const seen = new Set<string>();
  let current: string | undefined = agent;
  while (current !== undefined && waitsFor.has(current)) {
    if (seen.has(current)) {
      const victim = [...seen].sort((a, b) => retryCost(a) - retryCost(b))[0];
      waitsFor.delete(victim);
      await cancelVictim(victim);
      return;
    }
    seen.add(current);
    current = waitsFor.get(current);
  }
}

function stopWaiting(agent: string): void {
  waitsFor.delete(agent);
}

EACH AGENT REPORTS ITS ACTIVE WAIT → THE REGISTRY FINDS A CYCLE → ONE DELIBERATE VICTIM IS CANCELLED → THE REMAINING WORK CAN COMPLETE

Once a loop is found, victim selection (choosing which participant to cancel or restart so the rest can proceed) should consider retry cost and fairness. Always cancelling the same role can cause starvation (a worker being denied enough uninterrupted time to ever finish). Every registered edge also needs an expiry and must be removed on success, failure, cancellation, and timeout.

A real finding worth knowing: stale arrows create false deadlock alarms. An agent can finish or crash without removing its “I am waiting on X” entry, leaving a cycle that exists only in the registry. Give every entry an expiry time and run “stop waiting” on every exit path, including errors. Rotate or score victims as well; always choosing the same kind of agent can starve it indefinitely.
In the capstone: Eunomia's first release has no cooperating checks that can wait on each other, so distributed deadlock detection is not needed on its serving path; a per-turn budget and the one-ending-event rule already stop a turn from hanging. If separate checking services are added later, an event-driven detector can see the loop when the shared registry atomically accepts the closing edge, remove and cancel one selected side, and retry safely. Skill Reporter applies the same detector when report-synthesis and policy-validation branches create circular waits.
Lesson 50

Dynamic Agent Tool Fallback & Secondary Routing

The problem: Eunomia' primary data source can remain technically up while becoming too slow for a customer conversation. Waiting indefinitely for perfect freshness often harms trust more than a timely, clearly-labelled fallback. Skill Reporter faces the same decision when primary reporting data is slow during publication deadlines.

Latency (the time from sending a request to receiving its response) can be controlled with a routing deadline (an internal maximum wait before fallback begins). When the primary reaches that deadline, secondary routing (sending the work to a backup provider) chooses a faster source with known trade-offs, such as cached rather than live data. This 800-millisecond routing threshold is not itself a customer-facing service-level agreement.

import asyncio
from collections.abc import Awaitable, Callable

async def route_with_fallback(
    primary: Callable[[], Awaitable[str]], secondary: Callable[[], Awaitable[str]]
) -> str:
    task = asyncio.create_task(primary())
    done, _ = await asyncio.wait({task}, timeout=0.8)
    if done:
        return task.result()

    task.cancel()

    def observe_completion(finished: asyncio.Task[str]) -> None:
        if not finished.cancelled():
            finished.exception()

    task.add_done_callback(observe_completion)
    return await secondary()
async function routeWithFallback(): Promise<string> {
  const controller = new AbortController();
  const primary = primaryProvider({ signal: controller.signal });
  let timedOut = false;
  let timeout: ReturnType<typeof setTimeout> | undefined;
  const deadline = new Promise<never>((_, reject) => {
    timeout = setTimeout(() => {
      timedOut = true;
      controller.abort();
      reject(new Error("primary deadline exceeded"));
    }, 800);
  });

  try {
    return await Promise.race([primary, deadline]);
  } catch (error) {
    if (!timedOut) throw error;
    void primary.catch(() => undefined);
    return await secondaryProvider();
  } finally {
    clearTimeout(timeout);
  }
}

START THE PRIMARY WITH A DEADLINE → TRIGGER FALLBACK AND REQUEST CANCELLATION AT THE DEADLINE → LABEL THE SECONDARY ANSWER'S FRESHNESS

The abandoned operation also needs cancellation (actively signalling slow work to stop so it releases connections, processing time, and cost). Racing a request against a timer changes which result the router uses; it does not necessarily stop the loser, so the abandoned promise or task must still be observed. Each primary breach should be logged and fed into the circuit breaker from Lesson 35, so repeated slowness eventually prevents wasteful primary attempts altogether. Programmatic Output Guardrails

The problem: Eunomia can draft a convincing financial reply that still leaks private account details, makes unsupported product claims, or phrases guidance in a way policy forbids. Asking another model to judge that draft only swaps one uncertain judgment for another. Skill Reporter has the same risk when generated report text can leak sensitive employer or candidate information.

The dependable final checkpoint is a programmatic guardrail (a rule written in ordinary code that checks an AI reply before it is sent). Each rule performs a deterministic check (a check that produces the same result whenever it receives the same input), so a known-bad draft cannot slip through because a model interpreted it differently this time. The small examples below choose to block rather than rewrite a failed draft.

Many first-line rules use pattern matching (searching text for known words, formats, or character sequences). Here the rules cover only one forbidden claim and one account-number shape; they are not general detectors for PII (personally identifiable information), account data, or unsafe fallback behaviour. The decision point must fail closed (block an action when a safety check fails or cannot finish). A checker timeout is therefore a blocked reply, not permission to send an unchecked one.

Autonomous Red-Teaming Fuzzing & Automated Patch Proposals

The problem: Eunomia defenders can hand-write only a small set of attack tests, while real attackers keep mutating wording, encoding, and strategy. Fuzzing (automatically trying many unusual or hostile inputs to find failures) expands a small seed library into a continuing search. An attacker agent (an AI assigned to generate and vary attacks against another system) tests an isolated target. Lesson 44

Semantic Guardrails for FastMCP Tool Payloads

The problem: a Eunomia tool call can satisfy every schema field and type yet still be unsafe: it may target a forbidden resource, exceed policy limits, or point at another customer's account. Skill Reporter has the same semantic risk when payloads reference disallowed report sources, tenants, or publish scopes despite shape-valid JSON.

FastMCP (a framework for exposing application functions as tools that an AI agent can call) can validate the shape of a tool payload (the collection of argument names and values sent to a tool). Shape checking answers “is this a string?”; it does not answer “is this customer's string allowed to select that resource?”

That second question needs semantic validation (checking what supplied values mean and what effect they could have). Sensitive values should usually come from an allow-list (an explicit list of values or actions that are permitted, with everything else rejected), combined here with ownership and value-limit checks before real tool logic is reachable. If a richer payload later includes query text, filters, or nested values, those fields need their own validation; the examples below do not inspect fields they do not define.

Lesson 52

Cryptographic Tool Permission Scoping

The problem: Eunomia' sensitive tools cannot trust an agent request just because it sounds confident or includes a customer ID. They need cryptographic proof that a trusted authority approved this exact caller, action, resource, amount, and time window. Skill Reporter needs the same proof model for privileged report publication and distribution actions.

A digital signature (cryptographic proof that data was approved by the holder of a secret signing key and was not changed afterward) turns an approval into something the tool can verify. The signed permission token (a signed package describing exactly which action a caller may perform) travels with the tool request, but the signing key never does. These examples use a JWT (JSON Web Token, a standard signed claims format) and RS256 (an algorithm in which a private key signs and a corresponding public key verifies but cannot sign).

The verifier enforces the token's permission scope (the narrow set of tools, actions, resources, values, and time limits covered by an approval), comparing every claim with the requested operation. The exp claim is the expiry time. The jti claim is a unique token identifier used to stop a replay attack (reusing a valid past permission to repeat an action that should happen only once). A production replay store must atomically consume that identifier in shared storage and retain it until expiry, so concurrent workers and restarts cannot reuse it.

from typing import Protocol

import jwt

class ReplayStore(Protocol):
    async def consume_once(self, jti: str, expires_at: int) -> bool: ...

async def verify_permission(
    token: str,
    public_key: str,
    request: dict[str, object],
    replay_store: ReplayStore,
) -> None:
    required = ["tool", "caller", "action", "resource", "amount", "exp", "jti"]
    claims = jwt.decode(
        token, public_key, algorithms=["RS256"],
        audience="eunomia-tools", issuer="eunomia-auth",
        options={"require": required},
    )
    for field in ("tool", "caller", "action", "resource", "amount"):
        if claims[field] != request.get(field):
            raise PermissionError(f"scope mismatch: {field}")
    if not await replay_store.consume_once(str(claims["jti"]), int(claims["exp"])):
        raise PermissionError("permission token already used")
import { jwtVerify, type KeyLike } from "jose";

interface ReplayStore {
  consumeOnce(jti: string, expiresAt: number): Promise<boolean>;
}

export async function verifyPermission(
  token: string,
  publicKey: KeyLike,
  request: Record<string, unknown>,
  replayStore: ReplayStore,
): Promise<void> {
  const requiredClaims = ["tool", "caller", "action", "resource", "amount", "exp", "jti"];
  const { payload } = await jwtVerify(token, publicKey, {
    algorithms: ["RS256"], audience: "eunomia-tools", issuer: "eunomia-auth",
    requiredClaims,
  });
  for (const field of ["tool", "caller", "action", "resource", "amount"] as const) {
    if (payload[field] !== request[field]) throw new Error(`scope mismatch: ${field}`);
  }
  if (!(await replayStore.consumeOnce(payload.jti!, payload.exp!))) {
    throw new Error("token already used");
  }
}

Distributed Vector Sharding & Tenant Isolation

The problem: Eunomia serves many customers through shared infrastructure. One missing tenant boundary can place one customer's records into another customer's retrieval path, logs, cache, or agent context before cleanup code can react. Skill Reporter has the same exposure across workspaces if tenant boundaries are not enforced at every retrieval and storage layer.

Vector search (finding records by comparing numerical representations of their meaning rather than matching only exact words) is powerful, but its nearest matches must stay inside the right security boundary. Each tenant (one customer or customer organization whose data must remain separate from every other customer's data) should be routed before search begins.

A shard (a physically or logically separate portion of a larger data store) can give each tenant its own index, records, and access policy. This supports tenant isolation (preventing one customer from reading, changing, or searching another customer's data), but the in-process maps below demonstrate only logical routing. They do not create independent storage or access-control boundaries. In production, the authenticated tenant must come from verified server-side identity claims—never the model or request body—and the data plane must enforce separate credentials or equivalent per-tenant authorization.

Lesson 55

Deterministic Hash-Based Sampling for Review Queues

The problem: Eunomia operations can manually inspect only a fraction of interactions, especially around high-risk financial guidance. Naive random sampling chooses different records on every run, making audits irreproducible. Skill Reporter needs the same deterministic review sampling so publication-risk reviews are repeatable and defensible.

A cryptographic hash (a one-way calculation that gives the same fixed-length output for the same input, while a small input change normally gives a very different output that is hard to predict) can map each interaction into a numeric bucket. Deterministic sampling (selecting items by a repeatable rule rather than a new random choice on every run) sends buckets below a policy threshold for inspection. The threshold uses basis points: one basis point is one hundredth of one percent, so 10,000 basis points is 100%.

The input needs a stable identifier (a value that continues to identify the same item across retries and systems), plus an explicit policy version. Selected, safely redacted interactions enter a review queue (a list of selected interactions waiting for a person to inspect). The same identifier and policy reproduce the same result later.

from hashlib import sha256

def should_review(
    interaction_id: str,
    policy_version: str,
    threshold_basis_points: int,
) -> bool:
    if not 0 <= threshold_basis_points <= 10_000:
        raise ValueError("threshold must be from 0 to 10,000 basis points")
    policy = policy_version.encode("utf-8")
    interaction = interaction_id.encode("utf-8")
    stable_key = len(policy).to_bytes(4, "big") + policy + interaction
    digest = sha256(stable_key).digest()
    bucket = int.from_bytes(digest[:8], byteorder="big") % 10_000
    return bucket < threshold_basis_points
import { createHash } from "node:crypto";

export function shouldReview(
  interactionId: string,
  policyVersion: string,
  thresholdBasisPoints: number,
): boolean {
  if (!Number.isInteger(thresholdBasisPoints) ||
      thresholdBasisPoints < 0 || thresholdBasisPoints > 10_000) {
    throw new Error("threshold must be from 0 to 10,000 basis points");
  }
  const policy = Buffer.from(policyVersion, "utf8");
  const length = Buffer.alloc(4);
  length.writeUInt32BE(policy.length);
  const stableKey = Buffer.concat([length, policy, Buffer.from(interactionId, "utf8")]);
  const digest = createHash("sha256").update(stableKey).digest();
  const bucket = Number(digest.readBigUInt64BE(0) % 10_000n);
  return bucket < thresholdBasisPoints;
}

OpenTelemetry & Agent Tracing

The problem: when Eunomia returns a slow, incorrect, or surprising savings answer, teams need to know exactly which model and tool steps ran and where delay or error started. Plain logs rarely reconstruct that full execution path. Skill Reporter has the same blind spot when report outputs are late or wrong and the team cannot trace where the pipeline diverged.

OpenTelemetry (a shared standard for creating and exporting operational records from software) gives the request a structured history. A trace (the complete structured record of one request as it moves through a system) begins at the incoming API call. Inside it, each span (one timed operation inside a trace, such as a model call or tool call) records a named piece of work, its duration, and whether it succeeded.

CUSTOMER REQUEST → API SPAN → AGENT SPAN → ORDERED MODEL AND TOOL CHILD SPANS → EXPORTER → INSPECTABLE TRACE STORE

The parent agent span owns child spans for the first model call, the savings-data lookup, and the final model call. Each span can carry safe operational details such as the operation name, model or tool name, elapsed time, and success state. It should not carry the customer's message, account number, balance, or any other private value. The completed trace must be inspected, not merely emitted, to confirm that its parent-child links match the order that really ran.

from collections.abc import Awaitable, Callable

        with tracer.start_as_current_span("tool.savings_lookup") as tool_span:

                tool_span.set_attribute("tool.success", False)
                tool_span.record_exception(exc)
                tool_span.set_status(Status(StatusCode.ERROR))
                raise
            tool_span.set_attribute("tool.success", True)

import { SpanStatusCode, trace } from "@opentelemetry/api";

const tracer = trace.getTracer("eunomia.agent");

export async function runAgent(
  callTool: () => Promise<string>,
): Promise<string> {
  return tracer.startActiveSpan("agent.run", async (agentSpan) => {
    agentSpan.setAttribute("agent.version", "savings-v3");
    try {
      return await tracer.startActiveSpan("tool.savings_lookup", async (toolSpan) => {
        try {
          const result = await callTool();
          toolSpan.setAttribute("tool.success", true);
          return result;
        } catch (error) {
          toolSpan.setAttribute("tool.success", false);
          toolSpan.setStatus({ code: SpanStatusCode.ERROR });
          if (error instanceof Error) toolSpan.recordException(error);
          throw error;
        } finally {
          toolSpan.end();
        }
      });
    } finally {
      agentSpan.end();
    }
  });
}

A test must therefore prove that later tool work remains beneath the correct request rather than assuming it does.

Tracing is diagnostic support, not part of the customer's transaction. Use an asynchronous batch exporter with a bounded queue and timeout; if capacity is exhausted or export fails, drop or report telemetry separately rather than blocking the customer request.

Explicit context-propagation checks are required; a green tool span alone proves only that the tool ran.

Lesson 10

Evaluation-Driven Development

The problem: Eunomia can look convincing in demos while still failing common, ambiguous, or risk-sensitive customer requests. Without versioned expectations, prompt and policy tweaks become guesswork instead of measurable improvement. Skill Reporter has the same risk: report quality can drift silently unless every change is measured against saved evaluation cases.

Evaluation-Driven Development, or EDD (defining automated quality checks before or while building an AI feature) starts with user failures the team wants to prevent. Each desired behavior becomes an eval case (one saved input with explicit criteria for judging the resulting answer): the input, facts that must appear, behavior that is forbidden, and a scoring rule an engineer can explain.

LLM-as-a-Judge Benchmarking

LLM-as-a-judge (using a second language model to score another model's answer) provides a repeatable first pass. The judge receives the user's request, the evidence available to the agent, the candidate answer, and a rubric (a written scoring guide that defines what each score means). The rubric must describe observable qualities rather than vague goals such as “be good,” and the result must contain a structured score plus a short reason tied to evidence.

REQUEST + RELEVANT EVIDENCE + CANDIDATE ANSWER + RUBRIC → JUDGE MODEL → STRUCTURED RESULT → COMPARE WITH TRUSTED HUMAN LABELS → ACCEPT OR REVISE THE JUDGE SETUP

A benchmark (a fixed set of cases used to compare quality across versions) needs clear passes, clear failures, and difficult boundary cases. It must also probe order bias, preference for longer answers, leaked reference answers, and preference for wording similar to the rubric. The judge must not receive hidden hints about the expected score, because that would test hint-following rather than answer quality.

Calibration (checking automated scores against trusted human labels to learn whether the judge is reliable) happens before the judge is trusted in automation. Python and TypeScript judge clients run the same labelled examples and normalize their structured outputs into one report. In these abbreviated clients, prompt is assembled beforehand by a separately validated builder from the user request, relevant evidence, candidate answer, and rubric. Direct checks for safety, privacy, and required facts remain separate: a high clarity score can never cancel a prohibited disclosure.

CI/CD Eval Gates

The problem: Eunomia evals do not protect production if they run only manually or inconsistently. Every proposed change needs the same automatic gate, and meaningful quality loss must be blocked before merge. Skill Reporter requires the same CI discipline so reporting regressions never ship by accident.

CI/CD (the automated process that builds, tests, and delivers software changes) runs the relevant checks for every pull request (a proposed set of code changes submitted for review before merging). An eval gate (an automated pass-or-fail decision based on evaluation results) turns the report into an enforceable decision instead of an optional attachment.

PULL REQUEST → BUILD → START CONTROLLED SYSTEM → RUN EVALS → REPORT → QUALITY DECISION, WITH INFRASTRUCTURE FAILURE KEPT DISTINCT FROM A PRODUCT PASS

The workflow first builds affected packages, starts the controlled test system, and selects cases based on the changed files. High-risk changes still take the full-suite path. It produces machine-readable results (structured data that software can parse reliably) for automation and a readable artifact for reviewers, including every failed case. New results are compared with an accepted baseline (a trusted earlier result used as the point of comparison) and a threshold (the minimum acceptable score or maximum permitted regression).

Average quality is not enough: one critical safety failure blocks the change even if every ordinary case passes. Model outages, network failures, and broken test infrastructure are reported as inconclusive (unable to establish product quality because the evaluation did not complete reliably) rather than mislabeled as product regressions or, worse, quality passes. Any exception requires an explicit recorded approval; the threshold is never quietly weakened to make a build green.

A monorepo (one repository containing several related software packages) keeps the connected system under one versioned change. A workspace (the package-manager configuration that links local packages and manages their shared installation) defines the package boundaries and their declared dependencies. Source, tests, and build output stay inside the package that owns them; only genuinely common configuration belongs at the root.

Last-Approved Baseline Promotion for Eval Gates

The problem: comparing Eunomia to only the latest eval output is unsafe because that baseline may already include accepted or misclassified losses. Repeated small degradations can normalize bad quality. Skill Reporter has the same baseline-drift risk unless promotion always compares against a trusted reference artifact.

A regression (a measurable loss in behavior or answer quality) must be measured against a trustworthy baseline, not simply the nearest file in storage. Every report therefore records its code revision (the exact version of the code that produced it), dataset version, rubric version, threshold-policy version, completeness state, final gate decision, and any manual override with its approval evidence.

CURRENT CHANGE WALKS BACK PAST FAILED AND INCOMPLETE REPORTS → SELECTS THE NEAREST COMPATIBLE PASS → COMPARES CURRENT QUALITY → PROMOTES ONLY AFTER A SUCCESSFUL GATE

An ancestry walk (moving backward through earlier code revisions until a valid historical report is found) begins at the current change's parent and supplies reports newest-first along that ancestry. It rejects reports that are incomplete, did not pass their own gate, were manually overridden without approval evidence, or use incompatible dataset, rubric, or threshold-policy versions. The first remaining pass is therefore the nearest trusted comparison point, and the pull-request report displays both its revision and every rejection reason.

Consecutive-Pass Promotion Windows for Eval Gates

The problem: a single green eval run can be luck, not stability. If Eunomia promotes on one pass, noisy runs can slip through as false confidence. Skill Reporter has the same risk when one-off passes are treated as release-ready evidence.

A promotion window (a required run count that must all pass before release) turns promotion into a stability check, not a moment-in-time check. Day 56 chooses the right baseline; Day 57 adds timing discipline: require consecutive passes and keep the same regression tolerance against the approved baseline on every run inside that window.

RECENT RUNS → CONSECUTIVE-PASS WINDOW + BASELINE TOLERANCE CHECK → PROMOTE ONLY WHEN THE WHOLE WINDOW IS STABLE

Model Retry Guard with Failure Classification

The problem: naive retry loops cause two failures in production: retrying fatal errors forever, and giving up too early on transient failures that would recover. Eunomia and Skill Reporter both need explicit retry rules with a hard budget.

A retry guard (a policy that decides whether a failed attempt is retried or stopped) classifies failures as transient or fatal, then applies a strict retry budget. Success stops immediately, fatal errors stop immediately, transient errors retry only while budget remains.

ATTEMPT RESULT → FAILURE CLASSIFICATION + RETRY BUDGET → SELECTIVE RETRY OR IMMEDIATE STOP

from dataclasses import dataclass
from enum import Enum

class FailureKind(str, Enum):
    TRANSIENT = "transient"
    FATAL = "fatal"

    ok: bool

        return False, "fatal error - stop immediately"

  if (result.ok) return { shouldRetry: false, reason: "success" };
  if (result.failureKind === "fatal") {
    return { shouldRetry: false, reason: "fatal error - stop immediately" };
  }
  if (attemptNumber > maxRetries) {
    return { shouldRetry: false, reason: `retry budget exhausted (${maxRetries})` };
  }
  return { shouldRetry: true, reason: `transient error - retry ${attemptNumber}/${maxRetries}` };
}

The problem: when evaluation retry logic is hidden inside nested conditionals, operations teams cannot reliably explain why a run was approved, revised, or rejected. function jevStyleRawDecision(message: string): Decision {
  const text = message.toLowerCase();
  const scores: Record<Intent, number> = {
    balance: 0.01,
    coverage: 0.01,
    products: 0.01,
    faq: 0.01,
    simulation: 0.01,
    portfolio: 0.01,
    unknown: 0.01,
  };

  if (text.includes("simulate") || text.includes("simulation") || text.includes("projection") || text.includes("what-if")) {
    scores.simulation += 0.95;
  }
  if (text.includes("portfolio") || text.includes("optimise") || text.includes("optimize")) {
    scores.portfolio += 0.95;
  }
  if (text.includes("cover") || text.includes("safe") || text.includes("fscs") || text.includes("coverage")) {
    scores.coverage += 0.85;
  }

  const total = Object.values(scores).reduce((sum, value) => sum + value, 0);
  const probabilities = Object.entries(scores).map(([intent, score]) => ({
    intent: intent as Intent,
    probability: score / total,
  }));
  probabilities.sort((a, b) => b.probability - a.probability);

  return {
    intent: probabilities[0]?.intent ?? "unknown",
    confidence: probabilities[0]?.probability ?? 0,
  };
}

Lesson 11

Multi-Model Router & Semantic Cache

The problem: if Eunomia sends every savings question to the most expensive model, routine requests become too costly and too slow. Exact-text caching misses many equivalent customer questions with different wording. Skill Reporter has the same inefficiency when semantically similar report requests are not reused safely.

A model router (a decision-maker that sends each request to the cheapest and fastest model capable of answering it safely) makes model choice part of the application rather than a permanent setting. Start with a baseline that sends every request to one expensive model and records cost, response time, and answer quality. Then classify each incoming question by complexity, required tools, and risk. Routine low-risk work may fit a small local model, ordinary cloud work may fit a lower-cost model, and complex or sensitive requests can still reach the highest-capability model.

The second saving comes from a semantic cache (a store that can reuse an earlier answer when a new question has the same meaning even if the wording differs). Each question is turned into an embedding (a list of numbers representing the meaning of a piece of text), then compared with stored questions. A similarity threshold (the minimum meaning-match score required before a cached answer may be reused) prevents a merely related question from being treated as identical. An uncertain match means no cached answer is reusable: the router should make a fresh model call rather than force reuse.

Lesson 16

Local Model Integration & Quantization

The problem: routing every Eunomia request to remote models can violate cost targets, latency goals, or data-boundary policy. Local models reduce that dependency, but raw model sizes can exceed available hardware. Skill Reporter faces the same trade-off when report workloads must stay in controlled infrastructure.

A local model (an AI model running on hardware controlled by the application owner rather than through an outside cloud request) should first be measured on its own. Record memory use, startup time, response time, and answer quality before connecting it to the agent. The act of producing answers is called inference (running a trained model to produce an answer), and its practical cost includes loading the model as well as generating each token (a small unit of text processed or produced by a model).

Quantization (reducing the numerical precision of a model so it uses less memory and often runs faster) can make local inference practical on smaller hardware, but the trade-off must be measured rather than assumed. Run the lower-precision model behind a local model server—a program on controlled hardware that accepts model requests—and compare model size, memory use, speed, and answer quality with the unmodified version.

CHECK TASK, IMPACT, AND DATA-EGRESS POLICY → USE THE LOCAL QUANTIZED MODEL WHEN SUITABLE → USE CLOUD ONLY WHEN REMOTE PROCESSING IS APPROVED → FAIL CLOSED FOR LOCALITY-RESTRICTED WORK → VALIDATE, STREAM, AND MEASURE

Put local and cloud providers behind one interface so the rest of the agent workflow does not care which one answered. Protect the local path with a health check (a probe that reports whether a service can accept work), request time limits, bounded retries (repeated attempts capped at a fixed count), and a circuit breaker (a guard that temporarily stops requests to a repeatedly failing service). A fallback (a backup route used when the preferred model is unavailable or unsuitable) may use the approved cloud model only when policy permits the prompt to leave the controlled environment. Locality-restricted requests must fail closed or use another approved in-boundary provider; high-impact or complex requests are a separate category and may use cloud only under the same data-egress policy.

Context Caching & Prompt Compression

The problem: Eunomia repeatedly re-sends fixed instructions and long prior turns, increasing token spend and latency until context limits are hit. Skill Reporter has the same growth problem as report conversations and artifacts accumulate unless reusable context is separated from per-turn state.

A model’s context window (the maximum amount of text and other input a model can consider in one request) has to hold system instructions, policy text, tool descriptions, retrieved documents, conversation turns, and the current question. A token budget (the planned limit on the small text units sent to and generated by a model) assigns space to those parts before one of them silently crowds out another.

Separate stable instructions from changing customer content. The stable prefix (the unchanged opening portion of a prompt) can then use context caching (reusing the model provider’s earlier processing of a repeated prompt prefix). Measure request size, reported cache hits and misses (whether reusable work was found or a fresh request was needed), response time, and cost for both cached and uncached calls; a provider-reported hit does not guarantee a meaningful saving if the prefix is small or the rest of the request dominates.

CACHE THE STABLE PREFIX → COMPRESS OLD HISTORY WITH FACT CHECKS → ASSEMBLE IT WITH RECENT TURNS AND THE CURRENT QUESTION → LOOP UNTIL THE PROMPT FITS → REQUEST, STREAM, AND MEASURE

Prompt compression (shortening input while preserving the facts and instructions needed for the current task) should follow a policy, not an improvised “summarize this” request. Keep recent turns verbatim, summarize older turns, retain unresolved tasks and durable preferences, and protect amounts, dates, account constraints, consent decisions, and safety instructions from lossy summarization (shortening that discards some original information). Rebuild the prompt in a fixed order: stable prefix, compressed history, recent messages, then the current question.

The problem: static examples can improve Eunomia behavior for some requests but degrade others by adding irrelevant tokens and biasing responses. Skill Reporter has the same issue when one fixed few-shot set is applied to every report type regardless of context.

Few-shot examples (a small set of sample questions and good answers placed in the prompt) should come from an approved library, not from raw customer conversations or unreviewed model output. Each entry needs an identifier, question, approved answer, topic, risk level, tool requirements, and version. Establish both a no-example baseline and a fixed-example baseline before building anything more elaborate.

Dynamic selection (choosing examples at request time rather than always using a fixed list) represents the current question and candidate examples by meaning, then filters by safety, topic, and required capabilities. Select a small, diverse set instead of several near-duplicates, enforce a strict token budget for examples, and use no examples when no candidate is relevant enough. That no-example branch is a designed success path, not a retrieval failure.

Autonomous Agent Self-Reflection & Multi-Turn State Rollbacks

The problem: one unsupported Eunomia assumption can cascade through later tool calls and recommendations. Retrying only the latest step preserves the original bad state, while full restart may repeat valid or external actions. Skill Reporter has the same rollback challenge when an early wrong premise contaminates later report stages.

Self-reflection (a structured check in which the agent evaluates whether recent decisions still satisfy the goal and rules) works only when the state is explicit. Represent each turn with the goal, plan, known facts, tool results, completed actions, and unresolved questions. Trigger reflection on meaningful signals—contradictory evidence, repeated tool failure, a violated constraint, or a failed result check—not after every ordinary turn.

A checkpoint (a saved snapshot of the agent’s internal state at a known stage) should be written before important decisions and before any tool that may change the outside world. Reflection identifies the earliest unsupported decision and chooses a specific checkpoint. A rollback (restoring internal state from an earlier checkpoint) then discards dependent reasoning while preserving evidence that was already valid.

An idempotency key (a stable request identifier used to recognize a repeated operation) belongs in a durable action ledger (a store recording each external operation and its outcome). Where reversal is possible, record a compensation step (a separate operation that counteracts an earlier side effect). These controls protect external actions while reflection repairs internal state.

SAVE CHECKPOINTS → REFLECT ONLY ON FAILURE SIGNALS → IDENTIFY THE EARLIEST INVALID DECISION → RESTORE THE LAST VALID INTERNAL STATE → REVISE THE PLAN WHILE THE EXTERNAL ACTION LEDGER PREVENTS DUPLICATES

A side effect (a real-world change outside the agent’s internal memory, such as updating a record or sending a message) is not undone by restoring memory. The durable ledger must atomically reserve a key with a fingerprint of the intended request before execution, reject reuse with a different payload, and mark the original result after completion. The external provider should also honor the key so a crash after execution but before ledger completion can be reconciled without blindly repeating the action. Human approval remains necessary where correction is consequential.

A production state machine must still detect a stated trigger, identify the earliest unsupported decision, cap rollback depth, choose the last valid checkpoint, and create a revised plan. Lesson 39

Human-in-the-Loop Approval Checkpoints

The problem: after Eunomia asks for approval, that request must wait without blocking other customer sessions. Approve, reject, and timeout paths all need explicit handling; silence or delayed responses must never be treated as consent. Skill Reporter requires the same explicit checkpoint outcomes for report workflows.

A Future/Promise (a live-process placeholder for a result that will be supplied later; Python commonly calls it a Future, while TypeScript uses a Promise) lets one task wait while the service continues handling other requests. It is not durable and disappears if the process restarts. At an approval checkpoint (a point where execution cannot continue until a person decides), the durable record from Lesson 12 remains authoritative; a running service may associate a Future or Promise with that record only as a temporary waiter. After a restart, the service must create a new waiter or resume directly from the durable record rather than pretending the old placeholder survived.

ONE PENDING DECISION RESOLVES EXACTLY ONCE: APPROVE AND REVALIDATE, REJECT AND CANCEL, OR EXPIRE WITHOUT EXECUTING

The approval path first verifies that the identifier exists and is still pending. It resolves the placeholder with an explicit approved value, rechecks the action arguments, executes once, and records the outcome. The rejection path resolves that same placeholder with an explicit rejected value, returns a cancellation result, records a normal human decision rather than a system error, and calls no sensitive tool.

These are registry fragments, not the complete endpoint. They validate the incoming decision and show one guarded settlement path; production code must also route timeout through that path, revalidate arguments after approval, claim execution durably, run the action, and record its outcome.

async function decide(
  approvalId: string,
  value: unknown,
): Promise<Decision> {
  const decision = parseDecision(value);
  const request = pending.get(approvalId);
  if (!request || request.status !== "pending") {
    throw new Error("late, unknown, or already decided");
  }
  request.status = decision;
  pending.delete(approvalId);
  request.resolve(decision);
  return decision;
}

A timeout (a limit on how long the system will wait) expires without approval. Duplicate and late decisions are rejected clearly, completed entries are removed, and cleanup happens after every outcome. The difficult edge is a race condition (a bug where the result depends on which of two events happens first): approval and timeout may arrive at nearly the same instant. Both languages therefore need one atomic transition (an indivisible state change that competing events cannot both win) from pending to one—and only one—final state.

Python resolves a Future with an explicit decision value; TypeScript retains the function that settles a Promise and calls it from the approval endpoint. Their cancellation details differ, but readers should test the same outcomes for approval, rejection, timeout, and repeated response.

Lesson 47

Self-Healing Dynamic Tool Correction

The problem: Eunomia may choose the correct tool but send one malformed argument, like a bad date or account reference. Hard failure wastes recoverable work, while silent rewriting can trigger the wrong action. Skill Reporter has the same correction-vs-safety trade-off for malformed report tool inputs.

A tool call (a structured request from the model to run a named function) must pass schema validation (checking that supplied values match required names, types, and formats) before execution. Format mistakes must be separated from permission denials, network failures, and internal failures because only the first category is a sensible target for automatic correction.

VALIDATE FIRST → EXECUTE ONLY A VALID AND PERMITTED CALL; OTHERWISE RETURN A PRECISE ERROR, CORRECT WITHIN A LIMIT, AND VALIDATE AGAIN

When validation fails, the tool returns a structured error (a failure response with specific fields that software can interpret). It names the invalid field and states the expected format. A safe value such as the displayed date may be returned so the model can see what needs changing; sensitive account, personal, or secret fields must instead be redacted or described only by their non-secret shape. “Tool failed” is not enough information to repair anything.

  const match = /^(\d{4})-(\d{2})-(\d{2})$/.exec(value);
  if (match) {

    const month = Number(match[2]);
    const day = Number(match[3]);

Lesson 53

Resilient Streaming Agent Responses

The problem: Eunomia should stream responses as they are produced, but mid-stream tool calls may block for approvals, retries, or failures. The connection must stay valid, typed, and truthful about state changes instead of fabricating completion. Skill Reporter has the same requirement when long report steps stream progress and checkpoint events.

A streaming response (sending a reply in small pieces as it is produced) uses a ReadableStream (a web interface that lets a server provide those pieces over time). Its stream controller (the object used to add events and close the stream) manages delivery. Ordinary text can appear immediately, but internal tool work is a different event type (a label that tells the receiver what kind of stream item arrived): raw, unchecked arguments must never be presented as completed work.

STREAM TEXT EARLY → ROUTE TOOL EVENTS THROUGH VALIDATION AND APPROVAL → RETURN ONLY VERIFIED RESULTS → EMIT SAFE FAILURES → CLOSE ONCE

The event sequence is explicit: open the connection, send ordered text chunks, emit a safe status event while a tool or approval is pending, emit the verified result or a clear failure, and close exactly once. Every tool passes a typed tool boundary (a checked interface that permits only the tool fields and value types declared by the application). Correctable format errors enter the bounded correction loop; sensitive valid calls enter approval. Streaming never weakens either check.

What 64 Real, Verified Lessons Taught Us

Real execution beats polished theory

The strongest lesson across all 64 lessons is simple: run the code and report what actually happened. A polished explanation cannot replace a real Python execution, a real TypeScript execution, and an honest account of the output. Expected output must never be quietly promoted into claimed output.

The useful findings were not limited to successful demonstrations. Outdated interfaces, environmental failures, timing problems, unsupported features, and different behaviour between the two languages were evidence too. Preserve the real error message and explain its cause. Report the bug that was found and fixed instead of rewriting the history as a flawless first attempt. Say plainly when the libraries, controls, or failure behaviour differ. A verified limitation is more valuable than an invented success.

Verify the explanation separately from the data

A model can return the correct records while attaching an incorrect self-reported field. A tenant identifier (a value that says which customer or account owns data) or a confidence score (the model's own estimate of how likely it is to be correct) may conflict with the retrieved result. One response can therefore contain two claims that need separate checks: whether the records, calculation, or tool output are correct, and whether the model's labels, explanation, ownership field, confidence, or summary are accurate.

A successful lookup does not prove that every generated field around it is trustworthy. Security, ownership, and policy decisions must come from independently checked application data, never from a model describing itself as authorized or confident.

Match verification strictness to the lesson

A deterministic algorithm (a fixed calculation that gives the same output for the same input) should match exactly across language ports. If Python produces 0.375, TypeScript should produce 0.375, digit for digit, unless a documented numerical rule explains the difference.

An LLM-based lesson (a lesson whose wording or choice depends on a language model) normally matches in direction rather than exact phrasing. Both implementations should reach the same practical conclusion, call the appropriate kind of tool, respect the same safety boundary, and produce compatible structured data, while their sentences and token order may differ.

The verification rule: with no model involved, demand exact values, ordering, counts, and state transitions. With a model involved, demand the same intent, safety behavior, evidence, and structured outcome. In a mixed system, check deterministic components exactly and model-generated components semantically. Never excuse an exact algorithmic mismatch as “model variability” when no model produced that value.

Knowing which category a lesson belongs to prevents weak testing on one side and unfair testing on the other.

The “should not trigger” case is part of the feature

Every safety or detection mechanism needs a positive test and a negative test. Proving that a dangerous request triggers a guard is only half the job; the system must also prove that a healthy request does not trigger it. An approval checkpoint should pause a sensitive action but not an ordinary read-only request. A correction loop should retry malformed arguments but not a valid call. A detector should flag its intended risky condition and leave a healthy case alone.

The same symmetry applies to recovery. A retry policy should recover from a temporary failure but stop on a permanent one. A streaming error handler should emit a failure event when needed but not corrupt a successful stream. A durable resume path should restore unfinished work but never replay completed work. False positives can make a safety feature unusable; false negatives make it ineffective. Both sides must be executed and verified.

Final reflection

Shipping a dependable agent is not mainly about producing an impressive answer. It is about making every boundary visible and testable: where data came from, where a model made a claim, where deterministic logic must match exactly, where a person must decide, where state must survive, and where failure must stop rather than disappear.

Across 64 lessons, the reliable pattern stayed consistent: build the smallest real version, run it in both languages, test success and non-triggering cases, preserve the actual evidence, and describe differences without smoothing them away. That discipline is what turns Eunomia from a conversational demonstration into a savings assistant that can be deployed, supervised, interrupted, resumed, corrected, and trusted within clearly defined limits.

COMPLETE TURN GRAPH: SERVING PATH + QUALITY PLANE + INDEPENDENT PROBES

Runtime breakdown from message to answer:

  1. The web client sends one message to POST /v1/turns, and the HTTP adapter first verifies the bearer token and builds the customer scope from the token alone; a body that tries to carry a customer id is rejected.
  2. Only then is the turn opened, and the client immediately receives a turn.accepted event carrying the turn id and trace id.
  3. An input screen catches known injection patterns and requests that cross the advice line (asking Eunomia to choose a product for the customer).
  4. The routing policy table maps the question type to its starting answer step (template, composed, or handoff) before any evidence is gathered, because the step decides what evidence to gather.
  5. The service's evidence planner, not the model, calls only the capabilities that question type and step need, through the ports.
  6. Each capability validates its input and output with Zod and returns an evidence id.
  7. The evidence bundle is frozen and stored, and evidence.ready tells the client which evidence ids exist.
  8. The chosen step produces a draft: a template fills fixed wording from evidence with no model call; the composed step asks the ModelGateway to write from evidence only.   9. The verifier checks every figure, date and claim in the draft against the frozen evidence.
  10. If verification fails, the turn drops one step and tries again; the last step is a person.
  11. Only verified text is streamed as answer.delta events, closed by one answer.final. A screened-out request ends instead with turn.declined or handoff.offered, and a hard error with turn.failed.
  12. The TraceSink records masked spans: step chosen, verifier verdict, evidence ids, timings, never raw balances or message text.

Ports and adapters: plain rules in the middle, the world at the edge

The problem: Eunomia can use strong models and still fail as a production system if identity, data access, money rules, model calls and delivery are tangled together in one handler. A change to one provider or store then risks every control at once. Skill Reporter has the same architectural risk when reporting logic and its data sources are wired directly together.

Eunomia is one TypeScript service plus a web client, and the service is arranged as ports and adapters (a layout where the core business code talks only to interfaces it owns, and separate adapter code plugs real systems into those interfaces). Think of a travel adaptor: the device (the domain) has one plug shape; the adaptor changes for each country (each provider or store). domain/ holds pure rules: deposit protection per banking group, product facts, money as whole numbers of pence, the routing policy table and the verifier's rules. answering/ holds the sequence runner, which uses those rules and the ports to run one turn. ports/ holds seven interfaces the core depends on. adapters/ holds the HTTP server, model providers, stores and telemetry. Outside the service, quality/ owns scenarios and the release gate, probes/ is an independent Python suite, and web/ is the Next.js client.

This is the architectural form of Lesson 1's type-safe boundaries and Lesson 2's dependency injection (the core is handed its collaborators by trusted startup code instead of creating them itself), and Lesson 30's monorepo orchestration keeps service, quality suite, probes and client changing together in one repository. Scoping every port call to the token's customer applies Lesson 54's tenant-isolation principle (keeping one customer's data separate from another's) without implementing its per-tenant vector shards. The routing policy table is Lesson 5's conditional routing made explicit and testable.

Where decision-first routing fits: Lesson 64 adds a decision-first routing layer before any model work. Here that layer is the routing policy table: a typed question type plus a confidence threshold picks the starting step before evidence is gathered.       events.send({ type: "turn.failed", turnId: turn.id, code: "TURN_FAILED", retryable: isRetryable(error) })
    } finally {
      events.end()
    }
  })

    const bundle = await deps.turns.evidenceFor(request.params.id, scopeFromToken(request.verifiedToken))
    return bundle ?? http.notFound()   // someone else's turn is a 404, never a 403 that confirms it exists

  })
}

The answer-mode sequence and the model gateway

The problem: if every question goes to the same model with the same freedom, Eunomia pays model cost and model risk even for questions ordinary code can answer exactly, and a provider outage takes the whole assistant down. Skill Reporter has the same problem when every report request is treated as a free-writing task for one provider.

Instead of several agent configurations, Eunomia has one answer-mode sequence (an ordered list of ways to answer, from the most predictable to the most human) with three steps. Template: a deterministic answer filled straight from evidence, used when the question type allows it, such as "when does my fixed-term deposit mature?". Composed: the model writes from the frozen evidence only, then the verifier checks every figure and claim; if the planned bundle falls short, the model may request one more capability call, which the service executes and re-freezes into the bundle before the model writes (a second evidence.ready then lists the full set of ids). Handoff: a person. A routing policy table in domain/ picks the starting step for each question type before any evidence is gathered, because the step decides what evidence to gather; the sequence runner in answering/ receives that starting step. A failed verification drops the turn one step; it never climbs back up. Think of a staircase where you may only step down: each step trades a little automation for a little more safety.

This turns Lesson 37's model cascade into a cascade of answer modes rather than model sizes, makes Lesson 11's routing a reviewed table instead of an improvised choice, and puts Lesson 64's decision-first routing at the very top of the turn. Lesson 50's fallback routing lives one level down, inside the gateway.

// service/src/domain/routing-policy.ts — pure, reviewed like code
export type Step = "template" | "composed" | "handoff"
/** TurnStore.open returns an OpenTurn; classification adds what the sequence needs to choose and render a step. */
export type RoutedTurn = OpenTurn & { questionType: QuestionType; confidence: number }

  confidence >= 0.8 ? ROUTING_POLICY[type] : "handoff"
const SEQUENCE: readonly Step[] = ["template", "composed", "handoff"]
export const oneStepDown = (step: Step): Step => SEQUENCE[Math.min(SEQUENCE.indexOf(step) + 1, SEQUENCE.length - 1)]

// service/src/answering/turn-runner.ts — the step is chosen first, because it decides what evidence to gather
export async function* runTurn(input: TurnInput, deps: AnswerDependencies) {
  const screened = screenInput(input.message)                             // injection and advice-line checks, no model involved
  if (!screened.ok) {
    yield* declineOrHandoff(input.turn, screened.reason, deps)            // turn.declined, or an "advice-line" review item (no evidenceId yet) + handoff.offered
    return
  }
  const route = classify(input.message)                                   // { questionType, confidence }
  const start = startingStep(route.questionType, route.confidence)
  const gathered = await planEvidence(route.questionType, start, input.scope, deps.capabilities, input.signal)  // the service calls the capabilities
  const evidence = await deps.turns.freeze(input.turn.id, gathered)       // frozen and stored before any wording
  yield { type: "evidence.ready", turnId: input.turn.id, evidenceIds: [...evidence.ids] }
  const routed: RoutedTurn = { ...input.turn, ...route }
  yield* answer(routed, start, evidence, deps, input.signal)
}

// service/src/answering/sequence.ts — receives the starting step; it can only step down
async function composeOrNull(deps: AnswerDependencies, turn: RoutedTurn, evidence: EvidenceBundle, signal: AbortSignal) {
  try {
    let reply = await deps.gateway.compose(composeRequest(turn, evidence, { mayRequest: true }), turn.budget, signal)
    if (reply.kind === "capability-request") {                            // at most one extra call per turn
      const added = await deps.capabilities.runRequested(reply.request, turn, deps.gateway, signal)  // Zod-checked; one Lesson 47 correction
      evidence = await deps.turns.refreeze(turn.id, evidence, added)      // new evidence id, stored before the model writes
      reply = await deps.gateway.compose(composeRequest(turn, evidence, { mayRequest: false }), turn.budget, signal)
    }
    return reply.kind === "draft" ? { draft: reply, evidence } : null
  } catch (error) {
    if (error instanceof GatewayUnavailable) return null    // a provider outage drops one step; it is not a failed turn
    if (error instanceof CapabilityRequestRejected) return null   // still malformed after one correction
    throw error
  }
}

export async function* answer(turn: RoutedTurn, start: Step, frozen: EvidenceBundle, deps: AnswerDependencies, signal: AbortSignal) {
  let step = start
  let evidence = frozen

  while (step !== "handoff") {
    const attempt = step === "template"
      ? { draft: renderTemplate(turn.questionType, evidence), evidence }   // draft is null when the evidence does not fit
      : await composeOrNull(deps, turn, evidence, signal)                  // null when the provider chain is down or the request was rejected
    if (attempt && attempt.evidence !== evidence) {
      evidence = attempt.evidence                                          // re-frozen with one requested result
      yield { type: "evidence.ready", turnId: turn.id, evidenceIds: [...evidence.ids] }
    }
    const draft = attempt?.draft ?? null
    const check = draft ? verifyDraft(draft, evidence) : { ok: false as const, problems: [step === "template" ? "no template fit" : "no usable draft"] }

    deps.trace.record({ kind: "step.tried", turnId: turn.id, step, ok: check.ok, problems: check.ok ? [] : check.problems })
    if (check.ok && draft) {
      yield* paceVerifiedText(turn.id, draft.text)
      yield { type: "answer.final", turnId: turn.id, mode: step, text: draft.text, citedEvidenceIds: draft.citedEvidenceIds }
      return
    }
    step = oneStepDown(step)
  }

  const kind = start === "handoff" ? "routed-to-person" : "last-step"     // the table chose a person, or every step was tried
  const ticket = await deps.reviewInbox.submit({ kind, turnId: turn.id, evidenceId: evidence.id })
  yield { type: "handoff.offered", turnId: turn.id, reason: "A colleague will check this for you.", reviewTicket: ticket.id }
}

The ModelGateway port hides providers behind one method. Its adapter holds a fallback chain (an ordered list of providers to try), a circuit breaker per provider (a switch that stops calling a provider for a cool-down period after repeated failures, like a fuse that trips instead of letting every request wait for a timeout), and a per-turn budget so a slow chain cannot run up unbounded cost or time. When the whole chain is unavailable, the gateway throws a typed error and the sequence drops to handoff. The request's abort signal is combined with each provider's timeout, so a customer who closes the page cancels the outstanding call instead of leaving it running.

/** Lesson 29's token bucket: take() waits until the provider's pace allows one more call, or rejects if the signal aborts. */
export interface TokenBucket { take(signal: AbortSignal): Promise<void> }

export function createModelGateway(chain: readonly ProviderAdapter[], clock: Clock, pace: TokenBucket): ModelGateway {
  const breakers = new Map(chain.map((p) => [p.id, new CircuitBreaker({ trips: 3, coolDownMs: 30_000, clock })]))

  return {
    async compose(request, budget, signal) {
      for (const provider of chain) {
        signal.throwIfAborted()                                              // the client left: stop trying providers
        const breaker = breakers.get(provider.id)!
        if (!breaker.isClosed()) continue
        if (!budget.canSpend(provider.estimateCostPence(request), provider.timeoutMs)) continue

        try {
          await pace.take(signal)                                            // Lesson 29: a token bucket keeps calls within the provider's pace
          const callSignal = AbortSignal.any([signal, AbortSignal.timeout(provider.timeoutMs)])   // disconnect or timeout aborts the call
          const reply = await provider.compose(request, callSignal)
          budget.spend(reply.usage.costPence)
          breaker.recordSuccess()
          return ComposeReply.parse(reply)   // structured output: a draft (text + claims + cited evidence ids) or one capability request
        } catch (error) {
          if (signal.aborted) throw error                                    // a disconnect is not the provider's fault
          breaker.recordFailure()
          budget.noteFailure(provider.id, error)
        }
      }
      throw new GatewayUnavailable(budget.failures())
    },
  }
}

Three coarse capabilities, and the domain rules behind them

The problem: model output can look valid while carrying unsafe arguments: another customer's identifier, an impossible term, a rate filter of 400 percent. Many fine-grained tools also give the model many chances to pick the wrong one or to do arithmetic it should not. Skill Reporter has the same risk when model-generated report arguments are not validated strictly.

There are exactly three read-only capabilities, each declared with Zod on both sides. The service's evidence planner calls the ones a question type needs before the evidence is frozen; the model never calls a store directly. On the composed step the model may request one further call through the same typed interface, and the service validates it, executes it, adds the result under a new evidence id and re-freezes the bundle before the model writes. readSnapshot() takes no arguments and returns one typed, already-scoped snapshot of the customer's holdings, maturities and protection. queryCatalogue({ access, minTermMonths, maxTermMonths, minRatePercent }) filters the approved product catalogue. lookupGuidance({ topic, question }) returns approved passages, each with a stable passage id. Every output carries an evidence id, which is what lets the verifier and the evidence route say exactly where a figure came from.

The capabilities are coarse on purpose. One snapshot call replaces a handful of small lookups, so the model cannot assemble a partial picture and fill the gap by guessing. This is Lesson 1's schema pattern and Lesson 2's injected dependencies turned into a security boundary: scope arrives from the verified token through the injected AccountReader, never from an argument. Domain refinements such as "the minimum term may not exceed the maximum" are Lesson 44's semantic guardrails (business rules beyond data shape). The design applies Lesson 52's least-authority principle without claiming its signed, per-action permission tokens.

Protection is computed by domain code, never by the model. The scheme limit applies per person per banking group (one licensed bank, which may sell under several brand names), so two brands in the same group share one limit. The function below works in whole pence so there is no rounding, checks that totals stay inside the safe integer range, and reads the limit from a versioned rule rather than a number written into the code. The model may explain the result; it cannot supply or change any input to it.

// service/src/domain/protection.ts — pure: no I/O, no clock, no model
export function protectionByGroup(
  holdings: readonly EligibleHolding[],
  rule: ProtectionRule,                 // { version, limitPencePerGroup } from versioned config
): readonly GroupProtection[] {
  const totals = new Map<string, number>()

  for (const holding of holdings) {
    const next = (totals.get(holding.bankingGroup) ?? 0) + holding.balancePence
    if (!Number.isSafeInteger(next)) throw new DomainError("BALANCE_OUT_OF_RANGE")
    totals.set(holding.bankingGroup, next)
  }

  return [...totals].map(([bankingGroup, eligiblePence]) => {
    const coveredPence = Math.min(eligiblePence, rule.limitPencePerGroup)
    return { bankingGroup, eligiblePence, coveredPence, uncoveredPence: eligiblePence - coveredPence, ruleVersion: rule.version }
  })
}

The verifier is the other half of the same idea. A composed draft comes back as structured output: the text plus a list of claims, each pointing at evidence ids. The verifier pulls every money amount, percentage and date out of the text and requires each to appear in the frozen evidence, requires every claim to cite evidence that exists, and runs Lesson 13's deterministic output scan for other customers' details and advice-line wording. It also requires the draft to cite at least one evidence id, and every cited id to exist in the bundle. If the model's one capability request carries malformed arguments, Lesson 47's bounded correction loop applies: the validation error goes back once, the corrected request is validated again, and a second failure drops the turn a step instead of retrying forever.

export function verifyDraft(draft: Draft, evidence: EvidenceBundle): Verification {
  const problems: string[] = []

  if (draft.citedEvidenceIds.length === 0) problems.push("no cited evidence")
  for (const id of draft.citedEvidenceIds) if (!evidence.ids.has(id)) problems.push(`cited id not in bundle: ${id}`)
  for (const figure of extractFigures(draft.text)) {            // "£1,250.00", "4.10%", "14 March 2027"
    if (!evidence.figures.has(figure.normalised)) problems.push(`figure not in evidence: ${figure.raw}`)
  }
  for (const claim of draft.claims) {
    if (claim.evidenceIds.length === 0) problems.push(`uncited claim: ${claim.id}`)
    for (const id of claim.evidenceIds) if (!evidence.ids.has(id)) problems.push(`unknown evidence id: ${id}`)
  }
  if (namesSomeoneOutsideScope(draft.text, evidence.scope)) problems.push("mentions another customer")
  if (crossesAdviceLine(draft.text)) problems.push("personal recommendation")

  return problems.length === 0 ? { ok: true } : { ok: false, problems }
}
Never ask the model to calculate a financial figure that ordinary code can calculate exactly. Let code gather the evidence, let the model ask for at most one more piece through the same typed interface and explain it, and use code to check that the explanation only repeats what the evidence says.
Capability contract: validate on both sides. Input validation protects the service from the model; output validation catches a broken store before its malformed result becomes persuasive prose; evidence ids let the verifier, the client and a reviewer all point at the same facts.

An optional MCP server shares guidance and the catalogue, never the customer

The problem: other internal assistants want the same approved guidance and product facts. Copying the capability code into each one causes contract drift, while giving each one direct store access widens the attack surface. Skill Reporter has the same integration drift unless shared contracts and narrow gateways are enforced.

The Next.js client renders typed turn events and shows its evidence

The problem: a chat page must reconcile acceptance, evidence, paced text, a final answer, a handoff, errors and dropped connections without ever making a half-finished turn look like a complete financial answer. Hand-built string handling drifts from what the server really sends. Skill Reporter needs the same typed event discipline for long-running report generation.

The client in web/ is a Next.js (React web framework) application. A server-side route in the client forwards the signed-in session's token to POST /v1/turns and passes the event stream back unchanged; it never adds a customer id of its own. In the browser, a small reader splits the stream into frames, parses each one with the published TurnEvent contract, and feeds it to a reducer (a function that takes the current screen state plus one event and returns the next state). Unknown or malformed events are dropped and counted, not displayed.

This is Lesson 53's error-aware event contract on the receiving side. Lesson 38's typed multimodal-event principle matters before Eunomia ever accepts images or files: every kind of content gets its own event type rather than a string with a magic prefix. And because answer.delta is paced verified text rather than live generation, the client never has to retract words, which Lesson 3's raw token stream would have made possible.

"use client"
import { TurnEvent } from "@eunomia/turn-contract"   // the contracts/turn/ workspace package; the service sends with the same schema

export const droppedEvents = { count: 0 }   // malformed frames are dropped and counted, never shown

export async function* readTurnEvents(response: Response): AsyncGenerator<TurnEvent> {
  const reader = response.body!.pipeThrough(new TextDecoderStream()).getReader()
  let buffer = ""
  for (;;) {
    const { value, done } = await reader.read()
    if (done) return
    buffer += value
    let end: number
    while ((end = buffer.indexOf("\n\n")) !== -1) {
      const frame = buffer.slice(0, end)
      buffer = buffer.slice(end + 2)
      const data = frame.split("\n").filter((l) => l.startsWith("data: ")).map((l) => l.slice(6)).join("\n")
      if (!data) continue
      let parsed: ReturnType<typeof TurnEvent.safeParse> | null = null
      try { parsed = TurnEvent.safeParse(JSON.parse(data)) } catch { parsed = null }
      if (parsed?.success) yield parsed.data
      else droppedEvents.count += 1
    }
  }
}

export function turnReducer(state: TurnView, event: TurnEvent): TurnView {
  switch (event.type) {
    case "turn.accepted":   return { ...state, turnId: event.turnId, status: "working" }
    case "evidence.ready":  return { ...state, evidenceIds: event.evidenceIds }
    case "answer.delta":    return event.seq === state.nextSeq
                              ? { ...state, draft: state.draft + event.text, nextSeq: state.nextSeq + 1 }
                              : state
    case "answer.final":    return { ...state, status: "answered", text: event.text, cited: event.citedEvidenceIds }
    case "turn.declined":   return { ...state, status: "declined", text: event.reason }
    case "handoff.offered": return { ...state, status: "handed-off", ticket: event.reviewTicket }
    case "turn.failed":     return { ...state, status: "failed", retryable: event.retryable }
  }
}

An independent Python probe suite proves the contract from outside

The problem: tests that run inside the service can inherit the same wrong assumptions as the service, and mocks keep passing after the real HTTP contract breaks. Skill Reporter has the same blind spot without an independent client that only sees what a real caller sees.

Eunomia's probes/ folder is a separate Python suite. A contract probe (a test that checks a promise the public API makes, such as "every turn ends with exactly one ending event", by calling it the way a real client would) talks to any running environment over HTTP only, chosen by a base URL and a test credential. It shares no code with the service: not the Zod schemas, not the fixtures, not a helper. The client holds only public HTTP calls and its own reading of the wire contract; fixtures name which test customer signs in; the tests state user-visible promises. A stub upstream (a controllable stand-in for the account, catalogue and guidance stores and for the model providers, which counts every call it receives) can inject latency, errors and malformed payloads on request.

A different language makes accidental imports impossible, but language alone does not prove independence. The suite is independent because it uses only public contracts, its own fixtures, and observable behaviour. This applies Lesson 26's principle of verifying the real running system from outside (there through a browser, here through HTTP calls), and Lesson 24's process orchestration is how CI starts the service, the stub and the probes in the right order and waits for /readyz before the first probe runs.

quality/ turns answer quality into versioned, pinned evidence

The problem: unit tests prove that a schema rejects bad input; probes prove that the HTTP contract holds. Neither proves that an answer after a prompt or model change still shows the right figure, cites the right passage, stays on the right side of the advice line, and reads clearly. Skill Reporter needs the same layer to catch quality regressions that types and contracts miss.

quality/ holds scenario files grouped by risk: money facts, the advice line, privacy, injection and tone. Each scenario is a list of checkable properties (shows this figure, cites a passage, never names another customer, declines advice) plus any rubrics (written scoring rules) that a judge model applies. Properties are checked by code first because they are cheap and exact; rubric judges run after, and a judge is allowed to gate a release only once its scores agree well enough with human labels on a calibration set. Every run writes a run manifest (a small file that pins exactly what was tested): model, provider chain, and the hashes of the prompt, templates, routing policy, capability schemas and scenario set.

The harness loop has four steps. Snapshot: restore the scenario's fixture state in the stores, so every run starts from the same known world. Replay: run the turn through the real HTTP surface, exactly as a client would. Assert: check properties against the turn and its evidence bundle, then run the calibrated rubric judges. Archive: store the evidence bundle, events, verdicts and manifest id together, so any failure can be reopened later. Then a deterministic hash decides which passes also go to the review inbox; every failure always goes.

import { createHash } from "node:crypto"

export async function runScenario(scenario: Scenario, run: RunContext): Promise<ScenarioResult> {
  await run.fixtures.restore(scenario.fixture)                                       // 1. snapshot
  const turn = await run.client.streamTurn(scenario.turn, { as: scenario.signedInAs }) // 2. replay (real HTTP)
  const evidence = await run.client.evidenceFor(turn.turnId)

  const properties = scenario.properties.map((p) => checkProperty(p, turn, evidence)) // 3. assert, exact first
  const rubrics = await run.judges.score(scenario.rubrics, turn, evidence)
  const result = { scenarioId: scenario.id, manifestId: run.manifest.id, turn, evidence, properties, rubrics }

  await run.archive.store(result)                                                    // 4. archive
  if (!passed(result) || sampledForReview(run.manifest.id, scenario.id, run.reviewShare)) {
    await run.reviewInbox.submit({ kind: "quality-run", turnId: turn.turnId, evidenceId: evidence.id, manifestId: run.manifest.id })
  }
  return result
}

/** Same manifest + scenario always lands on the same side of the line, so reviewers see a stable sample. */
export function sampledForReview(manifestId: string, scenarioId: string, share: number): boolean {
  const digest = createHash("sha256").update(`${manifestId}:${scenarioId}`).digest()
  return digest.readUInt32BE(0) / 0x1_0000_0000 < share
}

Lessons 10 and 19 supply evaluation-driven development and judge calibration against human-labelled examples; reviewers' labels from the inbox feed that calibration set. Lesson 55's deterministic sampling is the hash above: re-running the same manifest picks the same passes, so two people reviewing "the sample" are looking at the same turns. A strong production turn can become a new scenario only after redaction, deduplication and a person's approval; a run's manifest can become the new approved baseline only after the gate passes (Lesson 56's last-approved baseline rule) and then only after a window of consecutive passing runs on main (Lesson 57).

Evaluation rule: never let the same uncalibrated model write the answer, judge the answer, and approve its own release without independent human labels. That is one opinion wearing three badges.

Continuous integration blocks quality regressions, not just build failures

The problem: a change can compile, pass unit tests and pass every probe while still dropping a figure, weakening the advice line, or making answers harder to read. Ordinary CI stays green through that. Skill Reporter has the same release risk without a quality gate tied to promotion.

The pipeline on GitHub Actions has four stages. Checks: lint (static code-quality checks), types, unit tests and build. Probes: start the built service and the stub upstream, wait for /readyz, run the Python suite. Quality gate: on a pull request, pick scenario groups from the paths changed against origin/<base branch>, using full git history (a style-only change in web/ runs none; a change to the prompt, routing table, templates, capabilities or provider chain runs the groups that depend on it; any change to domain/ runs money facts); on a push to main, run the full scenario set with no path filtering. Then compare against the last approved manifest. Production: a protected environment with a required reviewer.

This is Lesson 25's eval gate made selective, Lesson 30's shared pipeline across one repository, and Lesson 56's approved-baseline comparison. The required reviewer applies the broad human-oversight principle from Lessons 12 and 39, but it is not their durable per-action checkpoint; write actions, which would need that, are deferred.

CHECKS → PROBES → QUALITY GATE (PATH-SELECTED ON PRS, FULL ON MAIN) → PROTECTED PRODUCTION WITH A REQUIRED REVIEWER

Branch protection makes the workflow a required status check, so a pull request cannot merge unless it succeeds; that rule lives in the repository settings, outside the YAML. The production environment has a required reviewer, so a named person must approve before the deploy job starts, and the same approval records the run's manifest as a candidate. The approved baseline in quality/manifests/approved.yaml moves to that candidate only after a window of consecutive passing runs on main (Lesson 57); one approval never moves it on its own. When the window is met, quality:promote opens a pull request under a bot identity that updates approved.yaml, so the baseline moves only through that reviewed change, merged like any other.

on:
  pull_request:
  push:
    branches: [main]

jobs:
  checks:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm ci
      - run: npm run lint && npm run typecheck && npm test && npm run build

  probes:
    needs: checks
    runs-on: ubuntu-latest
    steps:

      - run: npm ci && npm run build

      - run: python3 -m unittest discover -s probes/tests -t probes
        env:
          PROBE_BASE_URL: http://localhost:8080
          PROBE_CREDENTIAL: ${{ secrets.PROBE_TEST_CREDENTIAL }}   # a test customer's credential, never a real one

  quality:
    needs: probes
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with: { fetch-depth: 0 }
      - run: npm ci && npm run build
      - run: ./scripts/start-probe-env.sh     # the real HTTP surface the scenarios replay through
      - name: Select scenarios
        run: |
          if [ "${{ github.event_name }}" = "pull_request" ]; then
            npm run quality:select -- --base "origin/${{ github.base_ref }}" --out artifacts/selected.json
          else
            npm run quality:select -- --all --out artifacts/selected.json    # push to main: full set, no path filtering
          fi
      - run: npm run quality:run -- --selection artifacts/selected.json --manifest-out artifacts/manifest.yaml
      - run: npm run quality:gate -- --against quality/manifests/approved.yaml --report artifacts/gate.json
      - uses: actions/upload-artifact@v4
        if: always()
        with:
          name: quality-gate-report
          path: artifacts/

  deploy:
    needs: quality
    if: github.ref == 'refs/heads/main'
    environment: production
    runs-on: ubuntu-latest
    env:
      GH_TOKEN: ${{ secrets.QUALITY_BOT_TOKEN }}   # a bot identity; a pull request opened with the default token would not trigger the required checks
    steps:
      - uses: actions/checkout@v4
      - uses: actions/download-artifact@v4
        with: { name: quality-gate-report, path: artifacts/ }
      - run: npm ci
      - run: ./scripts/deploy.sh
      - run: npm run quality:candidate -- --manifest artifacts/manifest.yaml   # the approval records a candidate in the run archive, not the baseline
      - run: npm run quality:promote -- --window 5 --open-pull-request    # after 5 consecutive passing runs on main, opens a PR that updates approved.yaml

The gate checks two things per risk group. A floor is an absolute minimum pass rate; an allowed regression is the most the pass rate may fall below the last approved manifest. A tone pass rate of 0.93 may clear its floor of 0.90 and still block if the approved run reached 0.97 and the allowed regression is 0.02. Money facts, privacy and the advice line are zero-tolerance groups: one wrong figure, one other customer named, or one personal recommendation blocks the change whatever the average says. Promotion follows Lesson 57: the approved manifest only moves after a window of consecutive passing runs on main, never after one lucky pass, and then only when the promotion pull request that updates approved.yaml is reviewed and merged.

Delivery rule: the baseline is an approved manifest, never "whatever main produced most recently". A failed run cannot lower the bar for the next one.

What ships in the first production-shaped release

The first release is read-only. It includes the five routes with token-derived scope; typed turn events with an explicit ending; three Zod-declared capabilities that return evidence ids; deposit protection per banking group computed in pence by domain code; the routing policy table and the template, composed and handoff sequence; a verifier that checks every figure and claim against frozen evidence; a model gateway with a fallback chain, circuit breakers and a per-turn budget; masked tracing through the TraceSink; an evidence route and a review route; an optional read-only MCP server for guidance and the catalogue; risk-grouped scenarios with calibrated judges, run manifests and hash-sampled review; independent Python probes; and a quality gate in front of a protected production environment. The snippets in this chapter show the ports, the turn route and event contract, the sequence, the gateway, the capabilities, the protection rule, the verifier, the MCP adapter, the client reader, a probe, the scenario and harness, and the pipeline. Store adapters, template wording, the review inbox's own screens, and rollback operations are named boundaries rather than full examples here. Write actions (moving money, opening, closing or changing accounts) are deferred to a later release with its own per-action approval design.

The operating loop is concrete. Every answer carries a turn id and a trace id, and its evidence can be fetched again. A customer (through the review route), the sequence runner (at the last step, or when the routing table hands off), the input screen (for advice requests) and the quality harness's sampler can each send a turn to the review inbox. A reviewer's label can become calibration data, and an approved, redacted turn can become a new scenario. A required status check runs the affected scenario groups, compares them with the approved manifest, and blocks a material regression. Production promotion passes a required reviewer and records the manifest as a candidate; the approved baseline moves to it only after a window of consecutive passing runs on main, so an operator always knows exactly which model, prompt and schemas to return to. That closes the path from Lesson 1's first schema to Lesson 57's rule of promoting only after a window of consecutive passing runs.

The finished system: Eunomia is useful because the model can read a customer's question, ask for one more piece of evidence when the planned bundle falls short, and explain holdings, products and guidance in plain words. It is trustworthy because identity, schemas, pence arithmetic, the routing table, frozen evidence, the verifier, traces, independent probes, human review and the release gate surround that reasoning at every boundary. Skill Reporter ships under the same boundary model: the capabilities are domain-specific, but the safety and verification controls are shared.
The capstone lesson: production AI architecture is not a larger prompt. It is a chain of small, inspectable contracts that lets a probabilistic model contribute where judgement helps, while ordinary software stays in charge of identity, money, evidence and release.
